# SOP 2：硬件与基础运行环境信息采集

## 1. 任务目标

独立采集实验所使用的硬件规格、系统环境、驱动、运行时和资源限制，形成可复用、可追溯的环境档案，供多个模型实验共同引用。

本 SOP 只调查硬件与基础软件环境

## 2. 采集原则

1. 区分物理硬件、操作系统可见资源、虚拟机资源和容器资源。
    
2. 区分硬件标称规格、系统实际可用资源和现场测量值。
    
3. 未知字段标记为 `unknown`；明确不支持的字段标记为 `not_supported`；无法访问的字段标记为 `not_accessible`。
    
4. 记录信息来源、采集时间、工具版本和原始命令输出。
    
5. 不得根据设备名称或理论规格猜测实际配置。
    
6. 不得为了采集信息而擅自修改系统配置或重启设备，安装大型依赖要做好隔离使用后要卸载干净。
    
7. 不采集与任务无关的敏感信息，例如密码、令牌和私人密钥。
    

## 3. 硬件采集清单

### 3.1 设备身份

记录：

- 主机名或匿名化机器 ID。
    
- 设备厂商、型号、设备类型及板卡版本。
    
- 芯片型号及硬件修订版本（若可获取）。
    
- 物理机、虚拟机、容器、云实例或开发板类型。
    
- 采集时间及时区。
    
- 宿主机与容器的关系（若适用）。
    

### 3.2 CPU

记录：

- CPU 厂商、完整型号和微架构（若可获取）。
    
- CPU 架构及指令集。
    
- 物理核心数。
    
- 逻辑 CPU 数。
    
- 当前可用 CPU 数。
    
- CPU 频率及频率范围（若可获取）。
    
- NUMA 拓扑（若适用）。
    
- CPU affinity、容器 CPU quota、cpuset 限制。
    
- CPU governor、功耗模式及温度（若可获取）。
    

必须区分物理核心数、逻辑 CPU 数和当前可用 CPU 数。

### 3.3 内存与存储

记录：

- 系统 RAM 总量和当前可用量。
    
- 内存类型、通道数及理论带宽（若可获得）。
    
- 实际内存带宽测量值（只有执行了相应测量才填写）。
    
- Swap 总量及使用量。
    
- zram 是否启用。
    
- cgroup 或容器内存限制。
    
- CPU 缓存容量（若可获取）。
    
- 模型或实验文件所在磁盘、文件系统及可用空间。
    
- 共享内存或专用内存限制（若适用）。
    

### 3.4 GPU、NPU、FPGA 及其他设备

只采集设备信息，如需运行验证，只执行采集信息用的轻量验证，不跑负载测试。

对每种可见设备记录：

- 厂商、型号和硬件版本。
    
- 设备类型及数量。
    
- 可获取的计算单元、核心数量或资源规格。
    
- 显存、共享内存或片上存储容量（若可获取）。
    
- 驱动、固件及设备运行时版本。
    
- 设备是否可被当前系统访问。
    
- 官方资料来源及相关限制说明（若可获取）。
    

对于 FPGA，记录器件型号以及官方或现有工具报告中的 LUT、FF、BRAM、URAM、DSP、时钟规格。若没有对应工具报告，不得将设计实际占用量推测为已测得资源。

### 3.5 操作系统

记录：

- OS 名称、发行版和版本。
    
- 内核版本。
    
- 系统架构。
    
- 系统启动时间（若有必要且可获取）。
    
- 容器运行时和容器镜像信息（若适用）。
    
- 当前用户权限和可访问的系统信息范围。
    

### 3.6 软件基础环境

记录当前已有的相关软件版本：

- Python 版本。
    
- C/C++ 编译器版本。
    
- 包管理器及环境管理工具。
    
- 已安装的推理框架及版本。
    
- 已安装的运行时及版本。
    
- 设备驱动和固件版本。
    
- 关键动态库版本（若可获取）。
    
- 相关环境变量中影响设备可见性、线程配置和资源限制的设置。
    

只记录环境现状，不执行编译或推理性能验证。

### 3.7 运行限制与背景负载

记录：

- CPU affinity 和资源配额。
    
- 内存限制。
    
- 进程及线程限制。
    
- 文件描述符限制（若适用）。
    
- 后台任务和系统服务对资源的占用概况。
    
- 当前是否存在其他实验或服务竞争 CPU、内存、GPU 或 NPU 资源。
    
- 访问设备、驱动、系统信息时遇到的权限限制。
    

不得为了清理环境而终止其他用户任务或修改系统服务。

## 4. 采集执行步骤

### 步骤 1：识别设备

确认机器身份、设备类型、CPU、内存、存储和可见加速器。

### 步骤 2：检查系统环境

获取 OS、内核、系统架构、容器信息和资源限制。

### 步骤 3：检查基础软件

获取已有编译器、Python、推理框架、运行时、驱动及固件版本。

### 步骤 4：交叉验证

对 CPU 型号、逻辑 CPU 数、内存总量、可用内存及资源限制等关键信息进行交叉核验。

必须明确标记信息属于：

- 官方规格。
    
- 系统报告。
    
- 工具报告。
    
- 现场测量。
    
- 未验证。
    

### 步骤 5：归档

保存结构化设备档案、软件版本清单和原始命令输出。不得覆盖既有档案；不同机器或不同采集时间应使用独立档案。

## 5. 命令选择原则

根据操作系统选择已有工具，不得假设所有系统安装相同命令。

Linux 可优先检查：

- `uname -a`
    
- `cat /etc/os-release`
    
- `lscpu`
    
- `nproc`
    
- `free -h`
    
- `df -h`
    
- `findmnt`
    
- `ps -eLf`
    
- `/proc/meminfo`
    
- `/proc/self/status`
    
- `/proc/self/cgroup`
    

Windows 可优先检查：

- `Get-ComputerInfo`
    
- `Get-CimInstance Win32_Processor`
    
- `Get-CimInstance Win32_OperatingSystem`
    
- `Get-CimInstance Win32_PhysicalMemory`
    
- `Get-Volume`
    

命令仅为候选方案。执行前检查工具是否存在，并在权限允许的范围内采集。

如果运行于容器，应说明结果可能仅反映容器视角，而非宿主机完整配置。无法访问宿主机时必须明确标记。

## 6. 交付目录

建议采用以下结构：

hardware/

- `device.json`：设备身份及硬件规格。
    
- `system.json`：OS、内核、系统架构和资源限制。
    
- `software.json`：基础软件、驱动、固件和运行时版本。
    
- `resources.json`：内存、CPU、存储及设备资源信息。
    
- `sources.md`：官方文档和信息来源。
    
- `raw_logs/`：原始命令输出及工具报告。
    

所有文件应包含采集时间、工具版本和档案版本。

## 7. 最终输出要求

Agent 必须交付：

1. 硬件规格报告。
    
2. 操作系统与基础软件版本报告。
    
3. CPU、内存、存储和可见加速器信息。
    
4. 当前系统及容器资源限制。
    
5. 信息来源和原始采集日志。
    
6. 未采集字段、权限限制和待确认事项。
    

最终报告必须区分官方规格、系统报告和实测数据。不得把硬件信息推导为模型性能结论，也不得执行量化或模型 Benchmark。

## 8. 与模型性能测试的关系

本 SOP 生成的硬件档案由其他实验按需引用。后续 Benchmark 应保持测试硬件和基础环境一致，只评估模型运行表现；如果机器或资源限制发生变化，应重新采集档案，按需扩大 Benchmark 的采集范围后需要额外标注。
