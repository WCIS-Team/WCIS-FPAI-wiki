# 板端直播链路与硬件仲裁

> 记录时间：2026-11-03。依据为板端 `192.168.1.113`（root/fmsh，内核 5.4.52）实读 + 仓库 `repos/FPAI30TAI图像FPGA` 对照。
> 板载现役构建是 `camera-low-latency-20261103-v2-live`（8091/8092）与 `recording-low-latency-20261103-v2-live`（8093），
> 已晚于仓库 `release/540p-r2`（2026-10-31）；`lan_stream/VPU_LIVE.md` 中大量 10-21 描述是旧状态，判断现役以板端为准。

## 当前板端状态

| 项 | 实读结果 |
|---|---|
| 监听端口 | 只有 22；**8091/8092/8093 全不通** |
| `wcis-face-photo.service`（8091） | `inactive (dead)`，`enabled`，被 ExecCondition 跳过 |
| `wcis-sdi-vpu-view.service`（8092） | `activating (condition)`，卡在 ExecCondition |
| `wcis-face-recording.service`（8093） | `inactive (dead)`，`enabled` |

即：语音栈活着，视觉三服务被一道 handoff 门挡住没起来。原因见下文「抢占与 blocked」。

## 怎么启动直播链路

现役是四个 systemd 单元分工：

| 端口 | 单元 | 实际进程 |
|---|---|---|
| 8091 | `wcis-face-photo.service` | `serve_photos.py`（人脸主页 + H.264 直播服务端），`ExecStartPre` 跑 `boot_prepare.py` |
| 8092 | `wcis-sdi-vpu-view.service` | `vpu_live_server.py`（预览/观看端，只读共享内存） |
| 8093 | `wcis-face-recording.service` | `recording_service.py`（录像，`--mode off`） |
| — | `wcis-face-storage.service` | 挂 eMMC 人员库（`/mnt/wcis-emmc`） |

启动链：`wcis-face-storage` 挂 eMMC → `wcis-face-photo` 的 `ExecStartPre` 跑 `boot_prepare.py`（只读校验 BOOT/DTB/uEnv、配 eth0、写 `boot-proof.json`）→ `serve_photos.py` 构造 `CameraOwner`（读 `models.json`、校验模型散列、`npu.lock`/`camera.lock` 排他）→ 启动原生 `wcis_camera_owner` → 采集 SDI→PL→PS、NEON 交织 UYVY、ffmpeg `h264_v4l2m2m` 硬编 + HLS 分片写 `/dev/shm` → 8092/8093 只读共享内存。

**当前要救活**：先解开卡死的 handoff，再让三个单元启动。见「抢占与 blocked」的解除命令。注意 `run_sdi_vpu_capture.py` 是旧独立采集 worker 的启动器，不是 r2 现役 owner 路径。

## 模型不可用时直播链路是否存活

不能一句「活着」概括。r2 是**单 owner 合一**：采集、VPU 编码、模型推理都在同一个原生进程 `wcis_camera_owner` 里，共享同一 SDK 会话；8092/8093 只是读 `/dev/shm` 的消费端，自己不产帧。

| 情形 | 直播 | 依据 |
|---|---|---|
| **A. 启动期模型不可用**（模型文件缺失/散列不符/加载失败/SDK 打不开）→ owner 起不来 | **一起挂**：无帧源，8092 无画面、8093 无输入；但 8092/8093 的 HTTP 端口本身不退出，只回 503/无帧 | `camera_owner_runtime.py` 读 `models.json` 并逐个校验散列；owner 启动命令把 `models.json` 作为 argv[1]；`serve_photos.py` 构造 owner 失败则 8091 起不来 |
| **B. 运行期单次识别失败**（owner 已起、某次 forward 报错/坏图） | **画面继续**：预览只看 owner 的 `state['ready']`，不看模型；只有 `/api/health` 报 unavailable、`/api/recognize*` 报错 | `serve_photos.py` 预览端点读 `state['ready']`；`model_ready` 只用于 health |

**为什么从「模型挂、直播活」变成情形 A**：这是 2026-10-21 的单 owner 合并带来的取舍。此前是双进程——独立的 `wcis-sdi-camera-live` 采集服务 + `wcis-face-photo` 模型服务，模型进程「每次硬件工作结束关闭 SDK」，靠请求级互斥暂停采集、跑 NPU、再恢复。那条老架构里模型挂不影响采集服务，所以「直播还活」。10-21 改成单一原生进程同时持有 SDK/分配器/VPU，识别期间不再停采集，代价是模型加载变成 owner 启动的一部分，于是成了情形 A。判断必须按 r2，不能按 10-21 以前的旧架构。

## 临时图片落在哪里

直播链路**不落盘**，逐帧画面与 HLS 分片都在 `/dev/shm`（tmpfs 内存）：owner 工作区 `/dev/shm/wcis-owner-<session>/`，内含 `latest.frame`、`status.json`、`hls/`（`init.mp4`、`seg-*.m4s`、`index.m3u8`），owner 停止时 cleanup 删除。`/snapshot.jpg`、`/api/camera/preview.jpg` 是从内存应答的 HTTP 路由，不是磁盘文件。

落盘的只有持久产物：① 录像 MP4/索引写到 `/mnt/wcis-emmc/wcis-face/recordings`（`mode=off` 默认不写）；② 上传照片识别时的 `uploads/<key>.jpg` 与 `-aligned.png`；③ 登记原图人员库；④ owner 关闭时拷到应用目录的日志/fault 副本（非图片）。

## 录像写入 eMMC 的实现与开关

实现是独立 PS 层 Python 服务 `recording_service.py`（类 `Storage`/`Segment`/`Recorder`），从现役帧发布接口取帧，**不持有 SDK/PL/VPU**。单元 `wcis-face-recording.service` 监听 8093，落盘 `--storage /mnt/wcis-emmc/wcis-face/recordings`（eMMC 是 `/dev/mmcblk1`，UUID `67104a06-...`，挂 `/mnt/wcis-emmc`；强制 ext4+UUID 校验、禁止回落 SD）。分段 `--segment-seconds 60`（或 256 MiB/事件边界切段），格式为 H.264 流拷贝 remux 成可 seek 的 MP4；配额 4 GiB、预留 512 MiB、达限不自动删；回收站 `.trash` 软删可恢复；自动清理默认关闭。

**当前是 off（关）**：unit 的 `ExecStart` 写死 `--mode off`，交接事务的 `original_recording_mode` 也是 `off`，仓库各阶段记录同样写「保留现场 off」。服务即便拉起也只是待命，须经 8093 的 `/api/mode` 切到 `auto`/`manual` 才真写盘。

## 模型的接口在哪

最直接一层是 8091 的 HTTP 接口（`serve_photos.py`）：`/api/health`、`/api/camera/status`、`/api/camera/preview.jpg`、`/api/camera/stream.mjpg`、`/api/camera/h264/live.mp4`、`/api/camera/h264/live-status`、`/api/gallery`；识别类 `POST /api/recognize`、`/api/enroll`、`/api/recognize-camera`（空请求体可用）；删除类 `DELETE /api/gallery/...`。

推理入口：`serve_photos.py` → `model_backend_runtime.py` → `model_backend/face_pad.py`（YuNet 身份 + MobileFaceNet 特征 + MiniFASNet PAD）。单 owner 形态经 `CameraOwner.infer_camera` → `owner.command(op='forward')` → `wcis_camera_owner.cpp` → `owner_npu::forward`。NPU actor 参考在 `ps_app/vendor/include/ai_example/*_npu_actor.hpp`。接口速查文档是仓库的 `docs/api-index.md` 与 `docs/interface.md`。

## 抢占与 blocked

被争用的「核」是 iCraft SDK + SDI 摄像头 + VPU 这一整套只能被一个进程独占的硬件。现役仲裁是**视觉↔语音交接**（`/usr/local/lib/wcis-vision-handoff/vision_handoff.py`，板端 2026-11-03 装）：

- 语音（ASR/TTS）要占硬件时，`run` 起受监管任务 `wcis-vision-voice.service`；`pause()` 依次停掉 `wcis-face-photo`、`wcis-sdi-vpu-view`、`wcis-face-recording`，核验相机 owner 的 SDK 正常关闭回执（`sdk_closed`/`sessions_released`/`exit_code=0`），释放 `npu.lock`/`camera.lock`，并记一笔事务到 `/var/lib/wcis-vision-handoff/state.json`。
- 事务 phase 走 `pausing→paused→voice_running→voice_finished→restoring→restored`。只要 phase 属于 BLOCK_START（`pausing`/`paused`/`voice_running`/`voice_finished`/`blocked`），`permit-start` 返回 false → 视觉服务的 `ExecCondition` 失败 → systemd 跳过启动。
- 语音任务结束，`ExecStopPost` 调 `_recover`：起 8091 → 等新帧与 `h264/live-status` 就绪 → 起 8092/8093 → 还原录像 mode。

**怎么抢的**：这不是并发抢占，而是 **stop/start 式**——先把视觉三服务停掉、确认 SDK 关闭，再让语音跑，跑完再把视觉拉回来。所以语音一起来，直播就断；语音结束，直播才恢复。

**blocked 自锁是什么**：本次 boot 一笔 token `217394...` 的交接里，语音任务 `voice_exit_code=1`，恢复时 `closed()` 发现 `wcis-sdi-vpu-view.service` 仍是 `activating`（它自己的 ExecCondition 又因 `permit-start=false` 过不了），于是抛 `Visual services did not stop`，`phase` 被置为 `blocked`。两边互相等：sdi-vpu-view 想起要 `permit-start=true`，但 blocked 让它 false；而 blocked 的解除又依赖 sdi-vpu-view 真正 inactive。这就把整条链路锁死在「都没起来」的状态。

解除：
```bash
python3 /usr/local/lib/wcis-vision-handoff/vision_handoff.py status
python3 /usr/local/lib/wcis-vision-handoff/vision_handoff.py recover --token 217394a8f4bb46028b9987893ab5a6fc
# 或 reboot（新 boot_id 让 permit-start 放行），再 systemctl start 三个单元
```

## 改成多服务并交 HA4FPAI 调度

**结论：多服务可以做在 HTTP/业务层，但硬件层必须保持单一所有者。** HA4FPAI 当前是语音栈（`klar-voice-gateway` + `klar-nlu-engine` + `klar-console`），角色是「被控设备」的客户端——它通过 HTTP 调 8091/8092/8093，自己不持有 SDK/摄像头/VPU。若把它提为调度者，要点：

1. **谁来开硬件只能有一个**。`wcis_camera_owner` 必须仍是唯一打开 iCraft SDK、SDI、`/dev/video0` 的进程；多服务只能做它的 HTTP/控制面消费者。多个进程各自 `open("/dev/video0")` 或各自 `CreateFromJsonFile` 就是重演 10-21 之前的抢核，历史上曾导致板上 PS 无响应。
2. **把「抢占」换成「排队/租约」**。现在 handoff 是停服务式的抢占；若不想「抢行」，应由单一所有者实现请求队列：人脸/直播/录像/语音都向它提交请求，owner 串行执行（或按优先级），谁都不用被 kill。这样语音占用时视觉不是「被停掉」，而是「排队等待」。
3. **统一仲裁者，别留两个**。现在系统里有两套仲裁：HA4FPAI 执行器自己发 HTTP，加上独立的 systemd handoff。两套并存正是 blocked 自锁的土壤。要么把 handoff 收进 HA4FPAI 的统一调度，要么保留 handoff 但让它只做「队列」不做「停服务」，二选一。
4. **可接受的折中**：保持单 owner + 多个只读消费者（8092 预览、8093 录像、8091 人脸），HA4FPAI 只做请求调度与优先级，不做硬件归属切换；这样「多服务」只是接口拆分，不产生新的抢核。

一句话：**多服务 + HA4FPAI 调度是可行的，但「别抢行」的前提是 HA4FPAI 成为唯一仲裁者、硬件仍单 owner；否则就是把 10-21 已经修掉的抢核问题重新引回来。**
