# 构建打包与部署

> 依据：`scripts/prepare_case.tcl`、`synth_blocks.tcl`、`elaborate_case.tcl`、`repair_mig_ooc.tcl`、`package_boot.tcl`、`package_boot.ps1`、`verify_boot_payload.py`、`case/ip_patch/`、`case/fpai_demo_vivado.xpr`、`docs/build-20261013.md`、`docs/release-runbook.md`、`release/540p-r2/`。只写设计与实现。

## Vivado 构建流程（PL 位流）

**定位**：在厂商案例副本上重建整板位流；构建纪律是"教程工作流 + 脚本化准备 + 产物自证"。

**结构与接口**：Vivado 2018.3 + 厂商 JFM 补丁工具包（`JFM_Kits`，环境变量 `JFM_PATH`）；工程 `case/fpai_demo_vivado.xpr`（顶层 `ai7030_edif_top`，器件 `xc7z030ffg676-2`，`case/fpai_demo_vivado.xpr:10`）。案例改动只进 `case/` 副本，原文件 SHA256 记录在 `docs/source_manifest.json` 与 `docs/case_changes.patch`。

**特色设计**：

- **prepare_case.tcl 是唯一工程准备入口**，顺序固定（`scripts/prepare_case.tcl`）：
  1. 只接受 `case/` 下的副本工程，且校验器件为 `xc7z030ffg676-2`，否则报错（`:6-14`）；
  2. 设 `ip_repo_paths` 到 `case/PS_AI IP` 并刷新目录（`:15-16`）；
  3. `config_ip_cache -disable_cache` + 把 `ip_output_repo` 改到副本内 `case/ip_cache`——原 XPR 保留了指向 Downloads 的绝对缓存路径，必须改回本副本（`:17-18`）；
  4. 以 **LATE 处理顺序**追加完整版 SDI 参考时钟覆盖 `constraints/fmql30tai_full_sdi_refclk.xdc`（U6/U5 覆盖案例默认的 Lite R6/R5）（`:19-25`）；
  5. 补入自研 RTL（rate gate、sdi monitor、face customop 五件）（`:26-33`），顶层固定 `ai7030_edif_top`（`:34`）；
  6. 校验 `JFM_PATH` 存在且为无空格 ASCII，然后 source JFM 的 `ip_patch/run.tcl` 并 `add_hook_tcl_to_prj` 安装六件厂商 hook（`:41-48`）；两个案例引用但不存在的 hook 文件（implementation_place_pre/post.tcl）先行移除引用（`:35-40`）。
- **JFM hook 机制**：`case/fpai_demo_vivado.xpr:826-861` 把补丁挂在每个构建步骤上——synth_design 前 `synthesis_pre.tcl`（跑 `pre_patch_check` + `pre_synthesis_patch` + `runEco`，`case/ip_patch/process_control/synthesis_pre.tcl:8-13`）、opt/route/write_bitstream 前后各一；`case/ip_patch/run.tcl:8-44` 的 `copy_patch` 在首次构建时把补丁 EDIF/工具复制进工程目录，使补丁随工程自包含。
- **OOC 全开 + 关 IP cache**：教程要求全部 IP 单独综合（OOC）、关 IP cache、GUI 直接 Generate Bitstream，不手动依次点 Run Synthesis/Run Implementation/Generate Bitstream（`README.md:280-282`）。XPR 中 `IPCachePermission=disable`（`fpai_demo_vivado.xpr:26`），impl_1 策略为 `Performance_NetDelay_high` + place directive 2 + phys_opt directive 2 + route directive 1（`fpai_demo_vivado.xpr:844-861`）。
- **repair_mig_ooc.tcl 修复 MIG 的 OOC 构建准备**（`scripts/repair_mig_ooc.tcl:10-19`）：调用共享的 `ooc_helpers.tcl` 中 `wcis_rebuild_ooc_ip mig_7series_0`——关 cache、重定向 `ip_output_repo` 到本工程、开 `GENERATE_SYNTH_CHECKPOINT`/`SYNTH_CHECKPOINT_MODE=Singular`、`reset_target`+`generate_target`+重建并等待 `mig_7series_0_synth_1` 完成（`scripts/ooc_helpers.tcl:3-36`），再跑厂商 `pre_patch_check`，最后 reset 失败的顶层 synth_1。成功标志 `WCIS OOC REPAIR PASSED` + `WCIS PROJECT PRECHECK PASSED`；不改 DDR 参数、引脚或时序库，且要求 GUI 单进程操作。
- **分层验证脚本**：`synth_blocks.tcl` 对新模块做 OOC 逻辑综合（含针对性 CDC 约束：只切 `request_sync_reg[0]/ack_sync_reg[0]` 第一级，payload 用 `set_max_delay -datapath_only 6.0`，`scripts/synth_blocks.tcl:10-21`）；`elaborate_case.tcl` 做 `-rtl` 展开 + SDI 约束校验（`scripts/elaborate_case.tcl:4-5`）；`build_case.tcl` 从源变更重建 synth_1/impl_1 并在 open_run 后跑 `validate_sdi_constraints.tcl`（`scripts/build_case.tcl:16-18`）。三者都明确声明"不等于整板时序收敛"。
- 位流生成后由 JFM 工具做 DISABLE_ICAP/VCCM 增补：`increment_bit_cfg_v3 ... -disable_icap` 产出 `ai7030_edif_top_disable_icap.bit`（`case/procise_run_disable_icap.tcl:1-2`），后续打包一律用这颗修补位流。

## Procise 打包（BOOT.bin）

**定位**：位流不是交付物，BOOT.bin 才是；打包由复旦微 Procise 完成，且打包结果必须自证。

**结构与接口**：Procise 2025.1.1，`set_device JFMQL30TAI676H`；输入为修补位流 + 三个 PS 载荷（FSBL251210_ddr400_demo.out / bl31.elf / u-boot），BIF 顺序 FSBL → PL bit → BL31 → U-Boot，`[fsbl_config] apu_x32`（`scripts/package_boot.tcl:4-25`）。

**特色设计**：

- **BIF 重写而非复用**：厂商 BIF 里有指向 Downloads 的绝对路径，直接复用会"悄悄打包旧厂商位流"——所以打包脚本在本目录现写 `wcis.bif`，用相对路径逐个复制输入（`scripts/package_boot.tcl:13-26` 的注释与实现）。
- **打包后立即 dump 自证**：`create_boot_image wcis.bif BOOT.bin -fmql` 成功后马上 `dump_boot_image BOOT.bin boot-image-dump.txt -fmql`，并落 `procise-package-status.txt` 完成标记（`package_boot.tcl:28-39`）。
- **package_boot.ps1 解决 GUI 子系统进程问题**：Procise 是 Windows GUI 子系统可执行，脚本模式下裸调用可能提前返回；PS1 显式 `Start-Process -Wait -PassThru`，重定向 stdout/stderr，检查退出码 + 完成标记的 LastWriteTime 必须晚于启动时刻（`scripts/package_boot.ps1:10-21`）。
- **verify_boot_payload.py 的载荷证明**：解析 .bit 头（`a/b/c/d` 元数据段 + `e` 载荷段），解析 FMSH 头（0x24 魔数、0x98 分区表、固定四分区），把位流有效载荷做 32 位字节序互换后与 BOOT PL 分区逐字节比对，允许后缀只有空或 `00000020` 配置 NOP；产出 manifest 含四个分区名、双 SHA256 与 `timing_passed=false` 等显式未签收位（`scripts/verify_boot_payload.py:28-52`）。离线发布包校验（`scripts/verify_offline_release.py:30-36`）进一步要求候选与回退镜像 FSBL/BL31/U-Boot 三分区逐字节一致、PL 分区必须不同。

**关键参数**：BOOT.bin ≈ 7,023,552 B（`docs/build-20261013.md:10`）；四个分区固定为 FSBL/PL/BL31/U-Boot（`scripts/verify_jpeg_boot.py:10`）；DTB/uEnv 不随普通 PL 更新变化。

## 发布基线（540p-r2）与清单冻结

**定位**：软件发布的真值不是"某个目录"，而是"冻结清单 + 文件对应表 + 只读校验工具"三件套。

**结构与接口**（`release/540p-r2/`）：

| 文件 | 内容 |
|---|---|
| `app-manifest.json` | 主应用 39 项受管文件（32 直接源文件 + 1 重组首页 + 1 构建收据 + 2 历史 HTML + 3 原生程序，`docs/release-source-map.md:47`） |
| `recorder-manifest.json` | 独立录像服务 7 个运行依赖；明确不把主应用里的同名副本当录像入口（`docs/release-source-map.md:59-73`） |
| `services-manifest.json` | 四个 systemd 单位文件（photo/view/recording/storage） |
| `startup-manifest.json` | 启动前置三件：`boot_prepare.py`、`deployment.json`、`mount_face_store.py`（各带 SHA256） |
| `site-template.html` | 首页不变部分模板，由 `assemble_camera_site.py` 插入 `camera_panel.html` 与版本号 |
| `source-map.json`、`owner-build.json` | 39 项来源映射与 owner 原生程序构建收据 |

**特色设计**：

- **首页是组装品**：正式服务的 `--site` 指向应用下 `site/`；首页 = `site-template.html`（不变部分）+ `npu_photo/camera_panel.html`（摄像头区块）+ 版本号，由 `scripts/assemble_camera_site.py` 离线组装，模板标记各出现恰好一次、版本号限字符集、输出用 `xb` 独占创建拒绝覆盖（`scripts/assemble_camera_site.py:5-29`）。组装结果与现役首页 SHA256 `6c04bfed…` 逐字节一致（`docs/release-source-map.md:51-53`）。
- **verify_app_release.py 只认外部清单**：按传入 manifest 逐文件 SHA256 校验，拒绝越界路径、重复项、符号链接、空清单；不检查清单外文件、不证明服务/模型/BOOT 健康（`scripts/verify_app_release.py:21-40`、`docs/release-runbook.md:60`）。清单冻结后禁止用新散列覆盖旧期望来"凑通过"（`docs/release-runbook.md:48`）。
- **来源分级**：`direct_source`（本地源文件）/ `assembled_site` / `preserved_artifact` / `native_binary`（含构建收据三方串联：源码包散列 → 包内 cpp → 板端二进制散列，`docs/release-source-map.md:43-57`）。
- 快照语义：`release/540p-r2` 是 2026-10-31 的冻结基线，后续版本必须另开目录新清单（`release/540p-r2/README.md`），录像服务后续独立升级走 `release/recording-idle-20261031/`（`docs/recording-idle-compression-20261031.md:36`）。

## 板端服务布局与切换顺序

**定位**：三个视觉服务 + 一个存储服务构成现役服务矩阵；切换顺序与关闭证据是发布协议的一部分。

**结构与接口**（`docs/release-runbook.md:29-44`）：

| 对象 | 入口 |
|---|---|
| 主清单 | `/root/wcis-face/video-stream-current.json`（app/files/verification） |
| 主应用 | `/root/wcis-face/apps/camera-h264-20261030-r2`，页面 = 其 `site/` |
| 8091 | `wcis-face-photo.service`（`serve_photos.py`，owner 由 `--camera-owner-sha256` 指定） |
| 8092 | `wcis-sdi-vpu-view.service`（只读浏览，共享 owner） |
| 8093 | `wcis-face-recording.service`（独立录像） |
| 存储服务 | `wcis-face-storage.service`（ExecStop 卸载 eMMC；普通发布不停它） |
| 启动前置 | `deployment.json` 的 app 必须与主清单一致 |

**特色设计**：

- **启动前置 boot_prepare.py**：照片服务 `ExecStartPre` 运行——只读挂载 SD 检查 BOOT/DTB/uEnv、把 eth0 写回 192.168.1.113/24 与网关 192.168.1.1、写启动证明（`docs/release-runbook.md:44`、`docs/ps-ethernet-negotiation-20261024.md:64`）；它不是只读诊断工具，不能手动为"检查"而执行。
- **切换顺序即协议**（`docs/release-runbook.md:85-104`）：记录 owner PID/session/boot → 依次 stop recording/view/photo（不用 kill -9）→ 从刚运行的应用目录读 `<停止前PID>-owner-stop.json`，必须 sdk_closed=true、camera_pending=false、exit_code=0 才算安全关闭 → 写入候选服务单位/主清单/启动前置（同目录临时文件写完 rename，整组失败即恢复整组备份）→ `daemon-reload` → 先起照片服务等健康 → 再起浏览与录像。
- **就绪判定用专用工具**：`wait_visual_ready.py` 显式传入本次 boot_id，有界 45 s，只做 GET：要求同一 owner 会话的 encoded 与 frame_id 持续推进、960×540 H.264、模型/硬件准入 ready、录像输入 ready 且 off/idle；端口未监听与启动失败区分，失败非零退出（`scripts/wait_visual_ready.py:8-45`）。
- **回退**：恢复备份的服务单位/主配置/启动前置，旧应用保持原目录不被新目录冒充；回退不删新增 MP4/人员资料/失败记录；"配置已恢复/服务已启动/媒体已验证"三种状态分开记录，不合并为一个成功（`docs/release-runbook.md:112-117`）。
- **故障隔离语义**：隔离标记 `/root/wcis-face/hardware-review-required.json` 按 boot_id 比较，不删除标记解锁；无法证明安全关闭时不自动重启旧版硬件（`docs/release-runbook.md:41`、`:93`）。

## 交叉编译与软件部署

**定位**：板端只运行不编译；aarch64 产物全部在学校服务器独立任务目录交叉编译。

**结构与接口**：

- 工具链：GNU Arm 10.3.1（AArch64）+ CMake + Ninja + iCraft SDK 3.39.0（板端与交叉两端版本一致）；服务器构建全部在 `D:/yzd/tmp/<task>` 独立目录，共享工具只读，编译 TMP/TEMP/TMPDIR 定向到任务目录（`docs/server-build.md:26`、`docs/build-20261013.md:43-45`）。
- `scripts/build-heartbeat.sh` 是单文件原生构建范本：用 `aarch64-none-linux-gnu-gcc.exe -static -std=c11 -Os -Wall -Wextra -Werror -fstack-protector-strong -Wl,-z,relro,-z,now`，先校验脚本自身必须位于任务目录才执行，产物落同目录并立即 readelf+sha256（`tools/heartbeat/build-heartbeat.sh:4-10`）。
- 部署脚本模式（`scripts/deploy_*.py`）：SFTP 上传候选到板端任务目录 → 板端 Python 校验（本地/远端双份 SHA256、目标 BOOT 散列、启动分区未挂载、硬件进程未运行）→ `copy` 用 `xb` 排他创建 → fsync → `os.replace` 原子替换 → 失败自动从备份回滚 → 卸载启动分区 → 才请求重启（`scripts/deploy_face_platform_boot.py:20-63`）。
- 应用部署前置检查（`scripts/board_deploy_preflight.py:3-9`）：身份/进程/参考例程/存储挂载/配置文件五类只读快照落 JSON。

**特色设计**：

- **发布与构建解耦**：`release/540p-r2/owner-build.json` 只记录"源码包散列 → 包内 cpp → 板端二进制散列"三方一致的收据；未追溯完整构建环境的原生程序明确标注"不声称从当前源码逐字节可复现"（`docs/release-source-map.md:57`）。仅改 Python/页面不冒称重新交叉编译（`docs/release-runbook.md:77`）。
- **原生程序进主应用清单**：`wcis_camera_owner`/`wcis_face_cached`/`wcis_face_pl_retained` 以 `native_binary` 类型与 Python 源文件同表管理（`docs/release-source-map.md:43-45`），模型与 BOOT 不随普通应用发布改动。
- **验收记录分层**：编译、校验、服务切换、板端推理、浏览器、重启、长稳分别记录，不相互替代；全部完成后 acceptance.json 才置 passed=true 并更新主清单 verification（`docs/release-runbook.md:108-110`）。

## 各脚本职责速查

| 脚本 | 职责 | 边界声明 |
|---|---|---|
| `prepare_case.tcl` | 打开副本工程、关 IP cache、重定向 ip_output_repo、追加 LATE 参考时钟覆盖、补自研 RTL、安装 JFM hooks | 不替换已安装时序库 |
| `elaborate_case.tcl` | 全案 RTL 展开 + SDI 约束校验 | 无综合/实现 |
| `synth_blocks.tcl` | 新模块 OOC 综合 + CDC 约束 + 资源/时序报告 | 非整板实现 |
| `repair_mig_ooc.tcl` | MIG OOC checkpoint 重建 + 厂商 pre_patch_check + reset 顶层 | 不改 DDR 参数/引脚/时序库 |
| `build_case.tcl` | 源变更后重建 synth/impl/位流 | 时序需另行审查 |
| `package_boot.tcl` + `.ps1` | 重写 BIF、复制 PS 载荷、Procise 打包 + dump 自证 | 打包成功不签收时序 |
| `verify_boot_payload.py` / `verify_jpeg_boot.py` / `verify_offline_release.py` | FMSH 分区解析、PL 载荷逐字节比对、PS 分区一致性 | 不部署、不上板 |
| `assemble_camera_site.py` / `verify_app_release.py` / `wait_visual_ready.py` | 离线组页、清单校验、有界就绪等待 | 不连接板卡/不碰硬件 |
| `deploy_*.py` | 候选上传、双端 SHA256、原子替换、失败回滚 | 每个脚本绑定固定任务路径，不整目录重跑（`docs/release-runbook.md:23`） |
