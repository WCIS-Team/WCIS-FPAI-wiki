# 录像与页面

本页拆解事件录像链路：`recording_service.py` 的 Storage/Segment/Recorder 三层结构、60 秒分段与配额/回收站/自动清理、H.264 分片的 remux MP4 落盘、8093 管理页面与回放，以及它和 8091/8092 的关系。录像服务是**零硬件**的纯 PS 进程——不打开 SDK/PL/VPU，只消费单所有者已编码发布的媒体（`npu_photo/recording_service.py:1-5` 模块声明）。

## Storage：有身份挂载上的配额账本

`npu_photo/recording_service.py:43` 的 `Storage` 只管“能不能再写”：

- **挂载身份强校验**：`findmnt -J` 解析 target/UUID/fstype，必须与配置的 `--mount/--uuid` 完全一致且为 ext4；录像根目录必须在挂载点之下且不等于挂载点本身。`guard()` 每次写入前复读 `st_dev`——eMMC 掉挂载立即报“no SD fallback”，绝不静默换盘。
- **记账式配额**：`used` 从既有 `rec-*` 文件长度求和起步，`account()` 加减、`admit()` 门槛判断；配额默认 4 GiB（`--quota-mib` 限 64..16384），另有磁盘安全预留 `reserve=512 MiB` 与单次写入 1 MiB 余量（`admit()`，`:70-75`）。**达到配额只停止新录像并保留已有文件**，不做自动删除；配额计入回收站与未完成文件。
- 实例互斥：`.recorder.lock` `flock(LOCK_EX|LOCK_NB)`，一台板上只允许一个录像服务（`recording_service.py:356-357`）。

## Segment：一次连续分段的落盘单元

`recording_service.py:78` 的 `Segment` 对应一个 `rec-<UTC时间戳>-<12位hex>` 文件组，随输入 codec 分两种格式：

- **H.264 路线**（`frame.codec=='h264'`）：视频文件是 `.mp4`，开头先写该流的 fMP4 `init.mp4`（`_h264_init`，`:94-95`）；后续每帧写入的是一个完整 fMP4 fragment 的字节（`.frames.jsonl` 每行记 `offset/length/captured_at/captured_end/samples/duration/frame_id_basis`，并区分 `source=PS_VPU_H264`、`timestamp_basis` 与可选的 `capture_time_basis=native_raw_input_journal` 源帧号字段）。
- **旧 MJPEG 路线**：`.mjpeg` 是 JPEG 帧连续拼接，索引行记 `offset/length/boot_id/session/frame_id/captured_at/received_unix`。
- 关闭流程 `finish()`（`:114`）是本组件的特色：
  1. 视频/索引双 fsync；
  2. H.264 时执行 **stream-copy remux**：`ffmpeg -i .mp4.part -c:v copy -movflags +faststart -f mp4 .mp4.ready`（`:124`）——把按段追加的 fMP4 重建为可 seek 的标准 MP4，不做第二次视频编码；`admit` 检查 remux 后字节数，fsync 后 `rename` 为正式 `.mp4` 并删除 `.part` 原件，账本按差额调整；
  3. 索引改名、写 `.json` 完成记录（`durable_json` = tmp + fsync + replace + 目录 fsync，`:28-40`），并再次 `account`。
- `abandon()`（`:143`）只关文件不发布完成记录——异常残片保持 `.part` 可识别，**失败的 fsync 永不冒充完整录像**。
- 分段边界由写盘线程判定（`_writer`，`:306-343`）：`captured_at - part.started >= segment_seconds`（默认 60 秒，限 1..300）、事件 id 变化、session `(boot_id, session)` 变化、或单段 256 MiB，任一命中即 `finish('segment_or_event_boundary')` 后开新段。

## Recorder：预滚环形缓冲与事件状态机

`recording_service.py:152` 的 `Recorder` 在内存里维护三个队列，用一条写盘线程消费：

- **环形预滚 `ring`**：无论是否在录，新鲜帧都进环；按“时间早于 `pre=2` 秒”或总量超 `byte_limit=16 MiB` 或帧数 ≥300 淘汰（`ingest()`，`:252-254`）。触发录像时先把环里 2 秒整体 `enqueue`——**人脸出现前的画面被保留**。
- **写盘队列 `pending`**：上限 16 MiB/600 帧，满则丢新帧并 `dropped+1`（`_enqueue`，`:269`）；`_writer` 常驻线程按 0.1 秒节拍写，`wake` 事件即时唤醒。
- **去重与断流统计**：`last_key=(boot_id, session, frame_id)`，重复帧直接丢弃；frame_id 跳跃计入 `source_gaps`；跨 session 清空全部缓冲并复位事件（`:237-247`）。
- **模式与触发状态机**（`command()`/`detection()`/`ingest()`，`:181-267`）：
  - `mode ∈ {off, auto, manual}`；`auto` 模式下，后台检测线程每 0.5 秒 POST 一次 8091 的 `/api/recognize-camera`（空体，走请求合并），检测结果经 `detection()` 准入：帧龄 ≤3 秒、boot/session 一致、face_count 为非负整数；`captured_at ≥ arm_at 且 face_count > 0` 就把 `deadline = now + tail(5s)`——**任意人脸都触发，不要求身份匹配或防伪通过**；触发健康度 `trigger_healthy` 用“最近检测 <5 秒”表达，检测 409 忙碌只记 `detection_error` 不算故障。
  - 状态串 `state`: `error` > (`recording`/`finishing` 若有活动分段) > `starting` > `armed`（auto 已布防）> `idle`；`manual` 在 `deadline` 之外恒为 wanted。
  - 事件切换（event id）、session 切换、手动/自动切换都会把当前段封掉重开；关闭时排空队列后 `finish('shutdown')`，收尾状态落 `service-stop.json`。
- `status()`（`:277`）一次性暴露：模式/状态、源与格式（`PS_VPU_H264`→`H.264 / MP4`，否则 `PS_VPU_JPEG`→`MJPEG + timestamp JSONL`）、队列字节/上限/高水位、丢帧数、源帧号跳跃、预滚字节数、配额使用、磁盘剩余——页面全部直接消费这些字段。

### 输入准入

`ingest()` 对两种源都有硬校验（`:226-236`）：H.264 fragment 必须来自 `source=camera`、分辨率 `(960,540)|(1920,1080)`、`vpu_enabled=true`、带 `_h264_init`、`captured_end` 新鲜 ≤4 秒、samples ≤300、体积 ≤8 MiB；JPEG 必须 960×540、SOI/EOI 完整、≤5 MiB、帧龄 ≤2 秒。测试图或 PL 预览源冒充不了这条链。

### H.264 分片的接入

`capture()` 线程（`:387-404`）用 `Frames.read_if_changed()` 轮询发布产物；codec 为 h264 时改用 `H264Segments`（`lan_stream/h264_fragments.py:41`）：读 manifest → 只追新段号（**序号必须严格 +1，缺片直接 RuntimeError**）→ 解析每段的 `tfdt` 时间与 `trun` sample 数 → 时间基换算 `captured_at = h264_origin + offset`；外部 FFmpeg 路线再读 `.capture.json` 把片段映射回**真实采集时刻与源帧号**（`capture_time_basis=native_raw_input_journal`）。也就是说录像侧的时间索引存的是采集时刻，而不是 MP4 名义 PTS。

## recording_library：目录、回放与回收站

`npu_photo/recording_library.py:28` 的 `Library` 管已完成的录像：

- **listing**（`:93`）：glob `rec-*.json`，逐条 `_summary` 校验（state=complete、三个必需文件齐全）后按 `first.received_unix` 倒序分页（每页 ≤50）；损坏记录计数为 `invalid_records` 而不是让整页失败；日期筛选按 Asia/Shanghai 日界换算 UTC 时间戳；`trash=1` 视图只列有删除标记的。
- **帧级回放 `frame()`**（`:243`）：按 `at`（秒，≤301）在 `.frames.jsonl` 索引里 `bisect_right` 定位行，校验 offset 连续、长度 4..5 MiB、时间单调、总行数=帧数、offset 终点=视频文件长度——**索引与媒体不一致即拒绝**；索引按签名缓存（≤2 段、每段 ≤10000 行/16 MiB），原始 MJPEG 不转码直接 seek 读取。
- **软删除/恢复**：`delete()` 只在 `.trash/` 写 `{id, deleted_at, purging:false}` 持久标记（`:128-134`），原文件全部保留、仍占配额；`restore()` 删标记。回收站内容禁止回放/下载（`opened()`，`:225`）。
- **永久删除 `purge()`**（`:198`）：必须已入回收站、无活动读者（`readers` 计数互斥）；先把 `purging:true` 持久化，再逐后缀删文件并逐笔 `account(-size)`，全删完才删 journal 标记——**中断后重启按 journal 继续清理**（构造函数恢复逻辑，`:45-47`），半删文件不会被误恢复。
- **自动清理 `maintain()`**（`:301`）：默认关闭；策略 `{enabled, days, trash_days}`（1..365，`set_policy` 需显式确认字段），启用后每 60 秒检查：录像满 `days` 天自动入回收站、回收站满 `trash_days` 天永久删除；只处理**完整记录**，不碰活动 `.part`，不按空间压力缩短保留期。
- 存储视图 `storage_usage()`（`:136`）把文件分组为 active/trash/unfinished（含压缩工作目录），另给配额、磁盘容量、压缩副本统计与“当前可用于继续录像” = `min(配额剩余, 磁盘剩余-预留) - 1 MiB`。

## recording_compression：闲时压缩

`npu_photo/recording_compression.py:35` 的 `IdleCompression` 在后台为 H.264 录像生成轻有损副本（profile `x264-crf18-medium-v1`），设计原则是“**原片永不改写，只有全验证通过的更小副本才发布**”：

- **空闲判定 `idle()`**（`:94`）：录像 state 必须是 `idle/armed` 且写盘队列为空、无 error；除自己 pin 住的输入外有任何读者（回放/下载）即暂停；录像被移入回收站抛 `Interrupted`；否则读 `/proc/stat` 采样 CPU——总忙碌占比 >15% 或 1 分钟 load >0.8 都算忙。连续空闲满 60 秒才开工。
- **低优先级调度 `command()`**（`:147`）：子进程 `taskset -c <单核> nice -n 19`，每约 1 秒内只放行 0.15 秒（SIGSTOP/SIGCONT 占空比 0.15/0.85）；每个暂停窗口做配额复查、输出大小预算（`-fs` + 读取检查）、总时限 6 小时。失败清理时先 terminate→SIGCONT→wait→kill，保证暂停中的子进程能退出。
- **候选与压缩**：只枚举完整、非回收站、`format=h264_mp4` 的录像（旧 MJPEG 明确排除）；小于 256 KiB 跳过（重压可能反而变大）、宽高超过 960×540 跳过。`libx264 -crf 18 -preset medium` 单线程重编码后做全套校验：帧数与摘要一致、尺寸一致、逐帧 PTS 与源时间线差 ≤1 ms、`ffprobe` 全帧解码、`ssim` 滤镜整体 SSIM ≥0.98、体积至少缩小 10%——任一不过即保留原片不发布。
- **发布与账本**：副本先 fsync，发布瞬间复核“原片指纹未变且未被移入回收站”，再 `replace` 为 `<id>.compressed.mp4`；结果写 `.compression.json`（`state/bytes/original_bytes/potential_saving_bytes/ssim/frames`），源指纹进 `source` 字段做幂等。副本纳入软删除/恢复/永久删除与配额账本；页面文案明确“保留原片，实际释放 0 B”。

## 8093 页面与回放

### HTTP 面

`recording_service.py` 的 Handler 路由（`:415-555`）：

| 路径 | 作用 |
|---|---|
| `GET /`、`/recording_panel.js` | 管理页面（单文件内嵌 CSS） |
| `GET /api/status`、`/api/storage`、`/api/compression`、`/api/retention` | 四个状态读数 |
| `GET /api/recordings?page&limit&from&to&trash` | 分页列表（含未完成文件计数） |
| `GET /api/recordings/{id}/frame?at=` | MJPEG 按时间取帧（`X-Frame-Time` 头） |
| `GET /api/recordings/{id}/video`、`/compressed` | MP4 播放，支持 HTTP Range 206 分段（64 KiB chunk 流式转发） |
| `GET /files/{id}.{mjpeg\|mp4\|frames.jsonl\|json\|compressed.mp4}` | 原样下载 |
| `POST /api/mode`、`/api/trash`、`/api/restore`、`/api/purge`、`/api/retention`、`/api/compression` | 控制（JSON ≤1 KiB、同源 Origin 校验） |

防呆：ID 严格匹配 `rec-[0-9]{8}T[0-9]{6}Z-[0-9a-f]{12}`；`/api/purge` 要求 `confirm == id`；启用保留删除策略要求 `confirm='delete_after_retention'`；媒体读写共享 `BoundedSemaphore(2)`，满则 429。错误分层：ValueError/KeyError→400，FileNotFoundError→404，RuntimeError/OSError→503。

### 前端 recording_panel

`recording_panel.html` + `recording_panel.js`：

- 顶部三键 `auto/manual/off`；状态行每 1 秒轮询 `/api/status`，存储与压缩每 5 秒、列表每 10 秒错峰刷新（`poll()`，`recording_panel.js:69`）。
- 回放双轨（`openPlayer`，`:41`）：`h264_mp4` 用原生 `<video>` 拉 `/video`（压缩版拉 `/compressed`），隐藏进度条；旧 MJPEG 用按采集时间的**帧级回放**——`display(at)` 逐帧 fetch JPEG + `Image.decode()`，播放时钟 `performance.now()` × 速率（0.5/1/2 倍）推进，网页显示上限约 10 帧/秒，下载仍含全部帧；版本号 + AbortController 防串台。
- 删除/永久删除走页面内 `<dialog>` 确认；回收站视图提供恢复/永久删除；存储面板六格数字 + 配额进度条；保留策略与压缩开关各有显式确认文案。

### recording_embed 嵌入

`recording_embed.js:2`：在 8091 主页面的摄像头面板之后插入一个 iframe，把端口改写为 8093、清空 query/hash；带“单独打开录像页面”外链。跨网络访问需 8091 与 8093 同时可达。

## 与 8091 / 8092 的关系

- **数据面**：录像只读消费 8092/8091 同源共享的发布产物——`Frames(args.control)` 指向单所有者的控制文件，H.264 分片目录在 owner 的 `/dev/shm/wcis-owner-*` 工作区里。识别触发反向依赖 8091 的 `/api/recognize-camera`（带请求合并），形成“8091 出检测 → 8093 出录像”的闭环；两个方向都不新开硬件所有者（`recording_service.py:1-5`、`docs/api-index.md:47`）。
- **生命周期**：`wcis-face-recording.service` 独立启停，崩溃/升级不影响 owner；它没有硬件所以只影响录像。8091 健康接口把 `camera_input` 与录像解耦，`/api/health` 的字段与 8093 `/api/status` 的 `source_ready` 各自独立。
- **端口**：8091 = 照片/摄像头 owner 服务；8092 = 只读预览（MJPEG/H.264 HLS）；8093 = 录像管理。三者共享同一采集 owner，端口映射以 `docs/api-index.md` 为准。
- **格式演进**：旧录像（`.mjpeg + .frames.jsonl`）与新录像（`.mp4 + fMP4 索引`）在同一个 Library/页面里并存，按各自格式回放；`frame_id_basis`、`capture_time_basis` 等字段区分两种时间来源，互不冒用。
