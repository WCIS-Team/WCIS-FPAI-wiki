# 三仓库Git历史重建SOP

## 范围与前提

只重建 WCIS-Team 下 WCIS-FPAI（main）、WCIS-FPAI-repos（master）、WCIS-FPAI-wiki（main）。保留原 GitHub 仓库身份及转移建立的旧地址跳转；不在个人旧地址新建同名仓库。保留本地当前内容和既有忽略目录，HA4FPAI、视频及更深层子模块的历史不变。授权与文件排除依据见 [[状态源与决策记录#D-1793967893 · 三个组织仓库从当前文件快照重建根历史|状态源与决策记录——D-1793967893]]。

本次脚本、旧引用、bundle、Git 元数据和结果清单位于主库本机 `workenv/history-reset-20261106/`，不提交公开仓库。备份含旧历史，仅在本机留存。

## 执行步骤

1. 检查三库 HEAD、索引、工作区、全部远端分支标签、规则集、保护、PR、Release、fork 和 Pages。记录工作树独有提交。操作期间停止其他会话对这三库的提交推送。
2. 保存引用、索引和工作树列表；为所有引用、当前 HEAD 及独有工作树 HEAD 创建 bundle 并执行 bundle verify。切换时另保存完整旧 Git 元数据；嵌套模块的元数据继续保持原路径可用。
3. 对照现有 tracked 清单生成独立临时索引，保留原 blob 与文件模式，避免重新 add 导致行尾和过滤器改变。只改明确排除文件、具名忽略规则、本次文档和主库两个子模块指针。
4. 用 `git commit-tree <tree>` 创建无父提交的新根。在独立新仓库中只获取该新提交及其可达对象，核验 `git rev-list --count --all` 为 1，`git rev-list --parents -1 HEAD` 不含父 SHA。
5. 先生成代码库和文档库新根，再把主库两个 gitlink 指向它们。用 diff-tree 检查允许变更清单，核对文件数量、blob、模式、超过 100 MiB 的文件和 LFS 指针；检查文档结构与站点装配。
6. 对实时远端 SHA 再次核对，使用带明确旧 SHA 的 `--force-with-lease=refs/heads/<branch>:<old-sha>` 逐库替换默认分支；子库先推、主库后推。若 SHA 已变，立即停止重新比较，不能改用无条件 force。其他旧分支和标签只按事先检查的清单处理，不使用 mirror 推送。
7. 保留现有工作文件，将本地三库活动 Git 元数据切换到只含新历史的副本，保留配置、钩子及嵌套 modules 原路径。将旧工作树关联到保存的旧元数据，并阻断其旧历史推送。切换前后比对文件字节；不能用共享目录 hard reset 或 clean。
8. 检查本地 HEAD 与 origin 跟踪分支相同、工作区干净、各库可达提交数 1；递归子模块 SHA 正确，远端获取和旧个人地址跳转成功。全部结果写入本机操作目录。

## 通过判据与日常使用

三个远端默认分支各自仅有一笔根提交，本地三库与远端一致。主库 gitlink 指向两颗新的子库根提交，递归拉取可获得所需提交。忽略目录、两个排除的厂商文件和嵌套子模块原工作内容仍在本机。旧工作树及其独有提交仍可在本地恢复副本读取。

之后直接在原来的三个目录修改、commit、push，新提交自然接在新根之后。仍须先推子库，再更新并推主库 gitlink。不要把旧备份中的分支、标签或提交 merge/push 回来。旧克隆应切换到新历史；最稳妥的是另行重新克隆，保留旧目录中的未提交内容再按文件迁移。

文档检查基线若已有错误，记录实际读数和本次新增页检查结果，不把历史重建解释成修复全库链接。站点工作流原为停用时，不擅自启用或触发发布。

## 恢复与清除边界

优先用保存的 bundle 或旧 Git 元数据在隔离目录读取历史及找回文件，不覆盖当前工作目录。恢复旧文件应经过公开范围检查后，作为新历史上的新提交；恢复整个旧远端历史会重新暴露被移除的材料，必须另获授权。

本操作只替换正常 Git 引用与本地活动历史。GitHub 旧 PR 引用、缓存、外部 fork、下载件、他人 clone 和既有站点产物可能仍含旧材料，须另行审查。当前仓库没有分支标签不代表这些副本全部消失。
