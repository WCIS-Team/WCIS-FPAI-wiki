# KV常驻设备侧实测

> **本页回答什么问题**：能不能把 ERNIE decode-only 那颗的 36 条 KV 缓存钉在设备侧（PL DDR），让每步上行 40.000 MiB／下行 36.197 MiB 的 KV 不过 CMA——机制成不成立、数值对不对、时间赚不赚。这是 [[NPU调用链]] §7.5 末尾那句"CMA 还能优化吗"的封口实测。
> **分工（一个事实只写一处）**：本页是**五档跑通读数＋两档撞门禁、两道厂商门禁原文、复现命令**的正本，第十节是 `enableTimeProfile` 的归因正本；§7.5 只留结论与"判不做"；`wiki/man/` 不作自著页校验（D-61），所以那张表必须自著成页。板端件的登记＝[[板端我方代码与产物台账]] §卅（行 #233–#236）＋§卅一（#237 起；#233 那颗已加 `E41PROF` 旋钮、大小与 md5 已就地更正）。分段计时的口径正本＝台账 §廿八；三个编译开关的档位对照＝台账 §廿九；**读回量能砍多少（窄读，已实装进现役 daemon）是另一件事，正本在 [[窄读KV回抄实测]]**。
> **证据分级**：A＝板上现读（日志／终端／`md5sum`）；B＝由 A 推导，算式同段给出；C＝外推、未实测；D＝听说。**没执行的步骤一律写成"未执行"**。

## 一、TL;DR

1. **机制成立**：`ZG330Backend.userConnectNetwork` 绑 36 条 present 输出 ＋ `Session.forward(inputs, outputs)` 收用户自建 chunk，`apply` 通过、图跑通、`CmaFree` 全程不动（B 档 130,660 kB 一次没掉）。⇒ "KV 不出设备"这条路**能走**。
2. **数值判死**：past 与 present 共用一块（in-place）从第 4 步起锁死在 token 23，`argmax` 只对 **4/12**、`top1−top2` 间隙只对 **1/12**；设备内两块＋`copyFrom` 只对 **3/12**。**只有 past 继续从主机喂的那一档（J）与现役 12 步逐位全等（12/12 ＋ 12/12）**。⇒ 一旦 KV 真常驻设备，这颗 decode-only 图就出静默错数。
3. **时间净亏**：省下的读回只有 **29.15～39.47 ms/步**，`forward` 却涨 **128.15～147.50 ms** ⇒ 整步净亏 **+88.71～+115.53 ms**（＋18.5 %～＋24.1 %）。**涨在哪儿已取证（11-03，第十节）**：62 条里 `hard` 分毫未变（ΣΔ＝0.00）、memcpy 也没跟着主机边界字节走（ΣΔ＝+2.1 ms），**+99.2 ms 的 `other` 里 94.5 % 落在 `op_id 0` 这一条**（0.697 → 94.430 ms）⇒ 不是"搬 KV 搬慢了"。
4. **两道厂商门禁**（都运行时抛、原文照录在第五节）：两条数 `forward` 的每个输出张量 `phy_addr % 4096 == 0`；`userConnectNetwork` **只接受 `plddr` 上的 chunk**，绑 CMA/`udma` 区直接拒。⇒ **想省 CMA 就只能常驻 PL DDR，而那条路更慢**——这就是"还能优化吗"的答案。
5. **判定：不做，现役链不动。** 回滚成本为零（纯驱动侧探针，现役 `e41_chatd.py` 一个字节没改）。

## 二、这轮改的是什么（机制与真实边界）

现役驱动（台账 §廿八／`e41_ocm.py` 同序）：每步把 40 条 `[1,8,512,128] fp16`（1,048,576 B／条）从主机 numpy 写进运行时自己的输入段，跑完再把 36 条 present 读回主机，主机侧做 padfix（`slot0=slot1`）再切槽。

探针 `e41_kvres.py` 换四件事，四个旋钮独立（`E41KV`／`E41PAD`／`E41REG`／`E41DEAD`）：

| 环节 | 现役 | 探针设备侧做法 |
|---|---|---|
| present 落点 | 运行时 OUTPUT 段 | `reg.malloc(1048576, False, 4096)` 一块 → `userConnectNetwork(ck_out, out_vid)` → `Tensor(spec.tensorType(), ck_out)` 进 `outs` |
| past 来源 | 主机 numpy | `Tensor(spec.tensorType(), ck_in)`——**同一块 plddr 地址直接当输入**（见下面"past 绑不了"） |
| KV 搬运 | 主机读回 36 MiB | `ck_in.copyFrom(0, ck_out, 0, 1048576)` ×36（设备内） |
| padfix | 主机 `slot0=slot1` | `ck.copyFrom(h*131072, ck, h*131072+256, 256)` ×8 head ×36 块 |

**这两条 API 的文档出处（B，原文照录，厂商包 `docs/`）**：`Session.forward(inputs, outputs)`——"输出 tensor 可指定为 PL 或 PS"，适用场景明写含"**环形网络，输入输出地址相同**"（`docs/xrt/index.html` §1.3.2）；`ZG330Backend.userConnectNetwork(memchunk: MemChunk, v_id: int)`——"用户配置网络输入/输出数据段的 memchunk，用于连接多网络在 etm 上的输入和输出"，`:note 在apply前调用`（`docs/zg330backend/index.html` §2.3＋板上 introspect 到的 docstring 全文）。签名与 docstring 都在板上直接读到（A，`dir()`／`__doc__`）。**文档说的是"多网络之间"复用段，我方这轮把它单网络自 use 来钉 KV——这条路文档没写过，实测结果见第四节。**

**一条必须先讲清的结构限制（A）**：`userConnectNetwork` 只能绑**有数据段**的 v_id。后端 `value_info` 共 **1,409** 条，里面有 logits（v_id 6087）和 36 条 present，**没有那 40 条 past 输入**（v_id 2…41）——绑它们直接 `IndexError: _Map_base::at`（板上现读：`/mnt/data/ernie/kv/C_nors.stdout:32`，栈停在 `_connect` 里的 `userConnectNetwork(ck, pvid)`）。⇒ **past 侧根本不需要"绑"**：给它建一个 `Tensor(dtype, chunk)` 就是把输入指到自己的 plddr 地址。这修正了我动手前的设想（"36 条各绑一次输入＋一次输出"）：实际只有输出侧 36 次绑定 ＋ 输入侧 36 次自建张量。

**paddr 侧直证绑定生效（A）**：B 档 `ALIGN sample` 里 v130／v287／v2572／v2724 的 `phy` 与 chunk `beg` **完全相等**（4096／1,052,672／35,655,680／36,704,256），而对照档 A2（不绑）同一批 v_id 落在 862,851,072／867,065,856／843,636,736／842,588,160＝运行时自己的段。⇒ 图真的读写到用户 chunk 上了，不是"绑了个寂寞"。

## 四、数值：12 步逐 token 指纹

oracle＝台账 §廿九 那批 8 档全同的 12 步链（`ocm1.stdout` 直取）：

```
argmax  [4, 23, 23, 23, 2969, 93919, 4, 93963, 93919, 253, 172, 177]
gaps    [5.9297, 1.0, 2.6016, 0.8984, 0.3359, 6.7578, 0.0938, 5.7188, 0.5703, 1.5312, 7.625, 0.0156]
```

| 档 | 本轮 argmax 链 | 第一个分叉步 | gap 链（前 4） |
|---|---|---|---|
| J | 与 oracle **逐位全等**（含 gaps） | 无 | `[5.9297, 1.0, 2.6016, 0.8984]` |
| A2 | `[4, 10, 7, 93937, 94149, 94081, 14879, 29135, 36395, 94397, 2, 22]` | **step 0**（`top1` 19.6094 vs 20.0938） | `[6.7891, 1.0391, 1.2344, 3.6172]` |
| B | `[4, 23, 23, 23, 23, 23, 23, 23, 23, 23, 23, 23]` | step 4 | `[5.9297, 1.0859, 2.0938, 0.6406]` |
| E | `[4, 23, 23, 7725, 93919, 4, 93937, 93919, 8636, 14879, 23, 1300]` | step 3 | `[5.9297, 0.9062, 2.5312, 0.6094]` |
| F | `[4]×12`（全锁 token 4） | step 1 | `[5.9297, 2.6094, 2.9688, 3.8281]` |

**四条读法**：

1. **B 的失败形状正是"原地覆盖"**：present 写回 past 同一块时，后面还要读的槽被写掉 ⇒ 从 step 4 起锁死在 23，**不崩、不报错**。这坐实了 §7.5 上一版列为"最高风险"的那条预判。
2. **E 排掉了覆盖、仍然不等**（step 3 起偏，`argmax` 3/12）⇒ 差异不只在原地覆盖，**past 从用户 chunk 读**这件事本身在这颗图上就没有等价路径。E 比 B 更接近现役（前 3 位 `5.9297／0.9062／2.5312` 与 oracle 同量级），但"接近"不是"对"。
3. **F 全锁 4** 是**反向确认 padfix 必需**：`copy` 模式关掉 `slot0=slot1` 后，第 0 步那格全零 pad 毒化缓存（[[ERNIE-4.5-0.3B-PT]] §9.6 记的那个坑），链一步都走不出去。
4. **A2 是本轮最该记住的坑**：`forward(inputs, outputs)` 传进去的 37 个用户 chunk **一个都没 `userConnectNetwork` 绑过**——结果 step 0 就与 8 个现役档全部不同（`top1` 19.6094 vs 20.0938，`argmax` 1/12），且**运行时零警告零报错**。⇒ 两条数接口"绑"与"读"必须成套；不绑就等于读一块没人写的内存。**这条与 KV 常驻无关，是接口用法**，任何后续走 `forward(inputs, outputs)` 的代码都得避开。

**判据的偏离（照实记）**：她给的判据是"63 步 oracle 逐 token 对"。本轮跑的是**同一条 12 步 `PREFIX` 的逐位指纹，63 步未执行**。理由＝B/E 的分叉分别出现在第 4／第 3 步、A2 出现在第 0 步，且对照档 J 在同样 12 步里已 12/12 全等——63 步不可能翻转"错数"这个结论。**没跑的就是没跑**，谁要翻案请先跑 63 步（第八节命令里换 `STEPS=63` 即可）。

## 五、两道厂商门禁（A，运行时抛出的原文）

1. **两条数 `forward` 的输出必须 4 KB 物理对齐**。第一批三档（`A_ctrl`／`B_kvres`／`C_nors`）全数撞死在这条上，原文：
   `Check failed: (phy_addr % 4096 == 0) is false`／`output tensor physic addr: 880703552` 与 `911321152`（`hardop.cpp:107`；两个地址 `mod 4096` 都＝**2,112 B＝0x840**）。
   根因＝`Tensor.mallocOn(region)` **没有对齐旋钮**、按 64 B 粒度落。**解法（A）**：`reg.malloc(byte_size, False, 4096)` 先拿 chunk，再 `Tensor(dtype, chunk)` 建张量；`_connect` 之后 `ALIGN asked=4096; outputs not phy-aligned=0/37`，五个跑通的档全过。
   对齐参数本身确认可用（`_align_probe2.py` 板上现读，空载连分四块）：`align=1`→`0x1000`；`4096`→`0x301000`；`65536`→`0x410000`（`mod 65536＝0`）；`2097152`→`0x600000`——全部 `mod 4096＝0`。**注**：这条 CHECK 文本是本轮终端现读，那一批的 stdout 已在改版时被覆盖，未留盘（复现＝用 `mallocOn` 重跑 A2 那档）。
2. **`userConnectNetwork` 只接受 `plddr` 上的 chunk**。`E41REG=udma`（＝CMA 里那块 128 MiB）两档 G／H 在 `apply` 之前抛：
   `Exception occurs at line 1127 in file .../zg330backend-src/source/zg330backend.cpp` ＋ `Exception info : userConnectNetwork can only support memchunk on plddr...`（`/mnt/data/ernie/kv/G.stdout:62`／`H.stdout:62`，板上现读）。
   区身份自查（A）：`defaultMemRegion().same_as(getMemRegion("plddr"))=True`，与 `udma`／`ocm` 都 `False`。⇒ **CMA 侧的内存不能被绑成网络输入输出**。想"KV 常驻在 CMA 所以不占 PL DDR"这条路被厂商从 API 面关掉，不是我方不会写。
   `E41REG=ocm`（I 档）未执行。

**顺带答掉 §7.5 的风险 3**：PL DDR 上自行申请够不够？**够**——B／J 各申请 36 块 × 1,048,576 B ＝ 37,748,736 B（36.000 MiB），E／F 各 72 块 ＝ 75,497,472 B（72.000 MiB），四档 `apply` 全部成功（45.2～49.6 s）。`apply` 后 `SEGMAP phy` 合计 **880,697,344 B＝839.9 MiB**（WEIGHT 778,268,672／INSTR 45,383,680／INPUT 18,890,752／OUTPUT 38,113,280／FTMP 40,960），五档与 11-01 那轮**逐字节相同**⇒ 申请用户 chunk 不改变段分配。

## 六、时间账：省了多少、亏了多少

跟对照档 J 逐段相减（全是 med-of-12，同轮同机）：

| 档 | `forward` | KV 段 | 整步 `step_total` | 百分比（÷480.01） |
|---|---|---|---|---|
| B | **+128.15**（525.45−397.30） | **−39.47**（3.38−42.85） | **+88.71** | ＋18.5 % |
| E | **+130.48**（527.78−397.30） | **−29.15**（13.70−42.85） | **+101.56** | ＋21.2 % |
| F | **+147.50**（544.80−397.30） | **−32.43**（10.42−42.85） | **+115.53** | ＋24.1 % |

- `forward` 那三项的百分比＝`128.15÷397.30＝32.3 %`、`130.48÷397.30＝32.8 %`、`147.50÷397.30＝37.1 %`。
- **三段相加不等于整步**（B：+128.15 − 39.47 ＋ argmax 0.46 ≈ +89.14 vs 实测 +88.71）：中位数不可加，整步是中位、分段也是中位，各档各自取的第 6／7 个样本不是同一步。差 0.43 ms 就是这件事，**不去抹平**。
- **归因边界（B）**：唯一旋钮是"past 输入从主机段换成用户 plddr chunk"（J vs B／E／F，其余全部相同），所以 `forward` 变慢**归到这一步**。至于**为什么**慢——是 DMA 拿不到批量描述符、还是 36 条输入各自独立描述符、还是 PL DDR 上那段地址的 bank 冲突——**本轮没取证**（`enableTimeProfile` 在 §廿八 已用过，本轮没开）。

**顺带翻出 §7.4 一条口径冲突（未归因）**：本轮 `Watchdog` 从建会话前一直采样到收尾，B 档连 `apply`（46.5 s）带 12 步都没看到 `CmaFree` 低于 130,660 kB；而 §7.4 记的现役对话链是 `apply` 期谷底 1,532 kB、会话存活期按着 100+ MiB。**两个路径测出两种账**，候选解释＝`.raw` 参数上传路径不同（`lazyLoadParamsFromFile` 何时真正搬权重）／同窗占用方不同——**都没验**。**但"借 126 MiB"没被本轮否掉**：同板 20:50 UTC 复查时 `CmaFree` 只剩 3,544 kB（板上当时只有 `klar/` 两颗进程、无 `e41_`、且零进程映射 `udmabuf`），⇒ 确实存在一条**探针之外**的路径能把 CMA 按到只剩 3.4 MiB；占用方未归因，读数记在 [[板端我方代码与产物台账]] §卅 收尾与 [[NPU调用链]] §7.4。**"串行是唯一无风险优化"不受影响**，但那条起跑门禁（`CmaFree ≥ 126 MiB`）在 20:50 那一刻过不了。

## 七、判定

**不做。** 三个理由按轻重排：

1. **数值不对**（第四节）。静默错数是最坏的一类失败——它不报错、只是锁在同一个 token 上，线上表现为"模型卡住重复"，比崩难查。
2. **就算数值修对了也不赚**：净亏 88.71～115.53 ms/步。
3. **省下的 CMA 不解决问题**：串行门禁（`113.txt` ＋ 起跑前 `CmaFree ≥ 126 MiB`）已经把 CMA 冲突消掉了；用 21～24 % 的减速去换本来就不冲突的 100 MiB，没有收益面。

**现役链零改动**：`e41_chatd.py`／`e41_ocm.py`／位流／DT／内核都没碰，探针件全部独立新文件（台账 §卅 #233–#236）。

## 八、复现

板端件（台账 §卅）：`/mnt/data/ernie/e41_kvres.py`＋`/mnt/data/ernie/kv_run.sh`，产出落 `/mnt/data/ernie/kv/`。**板上禁止编译**（AGENTS.md 第二节第 4 条）；这两件是纯 Python／sh，直推直跑，没有构建步。

```sh

env E41KV=bindonly E41PAD=host E41DEAD=host E41RESET=1 E41P_CFG=J \
    E41P_STEPS=12 E41P_OUT=/mnt/data/ernie/kv/J.txt \
    E41P_OUTJSON=/mnt/data/ernie/kv/J.json \
    python3 -u /mnt/data/ernie/e41_kvres.py

# 多档串跑（一档一进程，apply 不可重入）：B=in-place E=设备copy J=对照
```

## 十、`enableTimeProfile` 归因（11-03 22:00–22:03 UTC 板钟，两档各 8 步）

这一节答上面那条"机制未取证"，顺带核掉 [[板端我方代码与产物台账]] §28.4 里挂着的 `op_id 9930` 那颗 58.8 ms。**口径沿用 §28.4：profiler 自己会改时间分布（它把 `waitForReady` 搬进 `forward`），所以只看构成占比，绝对值不当性能数用。**

**两档怎么选**（`narrow_run.sh` 的 `PJ`／`PB` 两档，脚本＝#233 加了 `E41PROF=1` 那一版）：

| **PJ** | `E41KV=bindonly E41PAD=host`（present 绑 plddr、past 仍从主机喂、读回照旧） | 上 **40.000** ＋ 下 **36.197** ＝ **76.197 MiB** | `CHAIN` 前 8 步＝oracle 前 8 步（A，链有效） |

### 10.1 判定一：`op_id 9930` **不是** KV 主机边界搬运——§28.4 那条 C 级推断判否

- 两档跨主机边界的字节数差 **72.000 MiB/步**（算式 `76.197 − 4.197`＝`75.497 MB`）。按 §廿八 电池解出的 `r = 1108.7 MB/s`，这该值 **68.1 ms**（算式 `75.497 ÷ 1108.7`）。
- **实测 memcpy 桶几乎没动**：PJ late → PB late 全部 62 条逐条相加，**ΣΔ ＝ +2.14 ms**（＝SUM 的 115.0 → 117.2）。方向还是**反的**（PB 更高）。
- **9930 自己**：memcpy **56.161 / 57.534**（PJ early/late）对 **56.624 / 56.612**（PB early/late）⇒ 同一条在两档之间差 **0.9 ms（1.6 %）**，而它的 `hard` 是 **30.147 / 30.150**（分毫不差）。
- ⇒ **"这 58.8 ms 是每步 36 MiB 上行"判否（B）**。附带一条更基本的：**profiler 的 memcpy 桶不跟随主机边界字节数**——它要么只计设备内部的 op 级复制，要么主机边界那趟 DMA 根本不进这三桶。§28.4 写的"与 642 MB/s 量级吻合"是**巧合**，此处公开更正。
- 9930 到底是什么，**仍未证**：它的 `op_id` 与图 JSON 的 `op_id` 零命中（§28.4 已记），49.8 % 的 memcpy 占比、`hard` 恒定 30.15 ms、每条 present 家族（9913–9929）各 3.4–3.7 ms 这些读数都对不上一个已知名字。

### 10.2 判定二：常驻档 `forward` 涨的那 100 多毫秒**全在一条目怀里**，与搬运无关

- **`hard` 逐条不变**：62 条里最大 |Δ| ≤ 0.01 ms、**ΣΔ ＝ 0.00** ⇒ NPU 硬件计算量与 KV 在哪侧无关（A）。
- **`other` ΣΔ ＝ +99.24 ms**，其中 `op_id 0` 一条就 **+93.73 ms**（**0.697 → 94.430 ms**，135.6×），占 94.5 %（算式 `93.73 ÷ 99.24`）；剩下 5.5 ms 散在 9913–9929（×1.04–1.18）与 4xx/5xx/6xx 家族（×1.09–1.27）。
- 墙钟同向：`med_forward` PJ **395.66** → PB **503.85**（+108.19 ms），与 `other`＋`memcpy` 的合计涨幅（+101.3 ms）同量级（B）；§三 里非 profiling 的 B/J 两档差的是 +128.15 ms——**同一机制、不同绝对值**，profiling 本身改了分布（§28.4）。
- ⇒ **第六节"归因边界"那句"机制未取证"到此结束**：慢的不是搬 KV，是 past 输入换成用户 plddr chunk 之后，**被记在 `op_id 0` 名下的那一步运行时动作**（是什么动作**未证**——`op_id 0` 的身份与图 JSON 零命中，A2 档"绑与读不成套就静默错数"那条坑也指向同一个未取证区域）。

### 10.3 顺带：9930 的字节数与"已写入历史的长度"无关

`past_len` 从 1–2（early dump 在第 2 步后）走到 1–8（late 在第 8 步后），9930 的 memcpy 只从 56.161 变到 57.534（**+1.4 %**）；PB 那档 56.624 → 56.612。若这条复制按已填槽数走，early 该远小于 late。⇒ **它搬的是编死的 512 槽几何，与实际历史长度无关**（B，per-forward 语义沿用 §28.4 的 A 级判据）。

**这一条对下一颗档的意义（11-03 已判完，本节不复制读数）**：砍 `max_seq_len` 的推算收益（≈70 ms/步）原来挂在"每步上行 40 MiB"上，那个说法 10.1 已经判否；之后它只能挂在"9930 固定搬 512 槽"上——**这句现在升成 A**：重编了两颗更短 cache 的件（E42 NS=256／E43 NS=128，五段编译、本机 iCraft CLI，判过＝产物齐＋日志零 `[F]`／`[E]`／`fatal`），上板同场对照，9930 的 memcpy ＝ **57.100／28.670／12.212 ms per forward**，随窗口线性（每槽 0.111～0.129 ms，折成带宽两算式都落在 ~660 MB/s）。⇒ 上面那句"编死的 512 槽几何"要读作"**编死的 `NS` 槽几何，`NS` ＝ parse toml 的 `max_tokens_length`**"。产品窄读档实测一步 **437.77 → 295.38 → 230.27 ms（−32.53 %／−47.40 %）＝2.284 → 3.385 → 4.343 token/s**，比那条 ≈70 ms 的推算大得多；数值三途全过（63 步 oracle 回放三份 JSON 与 11-02 归档那颗**逐字节相同**）。全部读数、代价、以及"**为什么连 `other` 桶也随窗口缩**仍未取证"在 [[编译窗口裁剪实测]]。**产品件没换**（NS 直接砍上下文容量，daemon 的 `MAX_SLOTS=511` 与 `host_gen.py` 的 `if past_len >= 512` 本轮一律未动）——**等她裁**；`E41REG=ocm` 那条**未执行**。
