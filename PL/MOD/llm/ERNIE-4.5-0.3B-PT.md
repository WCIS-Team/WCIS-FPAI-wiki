## 三、为什么是它（对照现役那颗 Qwen3-0.6B）

1. **图干净得多**（A，pipeline §3）：210 节点／130 初始化器／38 入／37 出／13 种算子，Qwen3 是 520／256／58／57／15。ERNIE **没有 `Reshape`（Qwen3 112 颗）与 `Split`（28 颗）两整类，也没有 per-head QK-Norm** ⇒ Qwen3 线上"把 norm 换进 `com.microsoft` 域"那整步省掉。
2. **KV 红利只拿到一半**（A 编译面／B 算式）：按原生 2 KV head 推，缓存是 36×2×512×128×2 B＝**9.0 MiB**（对照 Qwen3 的 56.0 MiB＝1/6.22）；但平铺债把每张抬成 `[1,8,512,128]`＝1,048,576 B，36 条真缓存＝37,748,736 B＝**36.0 MiB**，再加 4 条必须喂的死输入 ⇒ **每步喂入 41,943,056 B ＝ 4＋12＋40×1,048,576 ＝ 40.0 MiB**（A，三个步目录逐目录实测）。**门 4 的 CMA／带宽预算按 8 头算，不按 2 头算**（CMA＝板上那块连续内存池）。
3. **件确实小**：`.raw` 1,054,488,148 B vs Qwen3 那颗 1,603,399,624 B ⇒ **0.658**（小 34.2 %，算式 A）。
4. **风险面**：`(16 Q／2 KV／head_dim 128)` 这个组合以前是零读数，10-30 晚编完之后**有读数是 1332 上 NPU／41 落 host**（A，§四第 3 条）；opset **22**（Qwen3 现役 21）第一次进这道工序、KV 第 4 轴是**符号轴** `kv_cache_dim`——这两条当时是"必经未知"，现在都已落地（改元数据到 opset 17、符号轴改回定长 128，A，pipeline §6 第 1／2 步）。

## 六、已知缺陷：首步中毒，以及它的修法（不重编）

- **现象**（A）：PC 侧 7 步链，首步对 HF fp32 的 `cos`＝**−0.253818**，第 1～6 步 0.9876～0.9972 ⇒ 断点精确落在"槽 0 是全零 pad"那一步。把 pad 槽填随机数（`mk_padrand.py`）＋逐层读数（5 例×18 层 `slot0_maxabs` 全 0.0）⇒ **图真的会去 attend 那格全零**，不是被 mask 掉。**与编译无关**：ORT 替身（把 IR 元数据改回去、用 onnxruntime 跑同一张图）对同一输入给同样坏的值。
- **排除掉的一条路**（A）：`SLOTS` 从 512 缩到 256／128／64／16，14 例的 `cos`／`maxabs`／`rank`／`top1` **逐位相同** ⇒ 病根不在 512 槽的几何，**改窗口这条路死，而且不需要重编**。
- **修法**（纯驱动约定）：token 0 连喂两次，每次前向之后把**槽 1 复制进槽 0**。残差＝token 0 在后续整条链里带双份权重。
- **收益**（A，替身面 120 题）：裸提示 `top1==HF` 23→**40**（`cos` 中位 0.9781→0.9910）、chat 面 11→**56**（`cos` 中位 0.7853→**0.9956**）；贪心 24 token 长链 3 条样本的平均一致位 裸 0.125→0.389、chat 0.083→0.292。
- **编译件上的复核**（A，10-31 新跑，`eval/compiled_padfix/`）：8 步，三条控制全过（step0 与不修链**逐字节相等**；不修 7/7、修复 8/8 每步 argmax 与替身完全一致；替身预测的首 token 位移 23→23 ＝ 编译件实测）。首步 argmax **4→23**（与 HF 同）；但对 HF 打分 `TV` 0.03192→**0.02512** 变好、`cos` 0.992162→0.983253 与 `maxabs` 1.857→3.090 变差 ⇒ **一个提示不足以判"一定更好"**，收益判据取上面那 120 题面。
- **代价**：本机 Host 后端（PC 上的 CPU 前向，不是 NPU）13.17 vs 11.557 s/步 ＝ **慢约 12 %**（多一步前向＋每步 40 次槽复制，A）。**板端代价已测（2026-11-01，A）**：0.42 vs 0.42 s/步，**看不出差别**——NPU 前向太短，40 趟 2 MiB 槽复制与多一次前向（0.42 s）都被抹平在单步粒度里。
- **默认值已定（2026-11-01，板上 A/B）**：板端驱动**默认开**（`E41_PADFIX=1`）。同一提示，开会给通顺输出（55 token 到 eos），关会退化成时间戳循环；判据见 [[板端我方代码与产物台账]] §25.4。PC 侧那 60 题编译件面仍未跑（见 `pipeline.md` §12 第 5 条）。

## 九、板端对话入口（2026-11-01 晚）

**这台模型现在能直接对话了**：桌面 `ERNIE对话.py`（双击开），分词解码在本机做，板上 `e41_chatd.py` 常驻回复。模型只 `apply` 一次（约 95 s 冷启动），之后每问一轮只付前向——实测 **0.47 s/步**，"你好，你是谁？" 37 token／23.4 s、"什么是光合作用" 38 token／25.2 s，都以 eos 收尾。

- **协议**：unix socket 上的 JSON 行（`{"ids":…,"max_new":N}` → 若干 `{"tok":…,"sec":…}` → `{"end":…}`），中继走 ssh；每轮把整段对话重放一遍，轮与轮之间缓存清零，互不污染。
- **分词为什么现在在 PC 侧**：板上 `tokenizers` 0.13.3 加载这颗 `tokenizer.json` 会报 `ModelWrapper`（现场读数，成因未取证——我原先写的"新版字段"已被 #220 的对照直读否证，板上 Qwen3 那颗键集合同款），所以现役链路是"喂 id、出 id"。**这不等于板上做不到**：降级 json／纯 Python 实现这颗分词两条路都未执行，见 [[板端我方代码与产物台账]] §25.5。
- **占用**：控制台连上时把 `113.txt` 写成 `test==on`，正常退出恢复原值；守护在最后一个客户端断开后空闲 300 s 自退。
