# 窄读KV回抄实测

> **本页回答什么问题**：ERNIE-4.5-0.3B decode-only 那颗每步把 36 条 present KV **整块**读回主机（36.197 MiB），能不能只读新写的那一槽（72 KiB）——省多少、数值对不对、能不能进现役驱动。**11-03 已实装进 `/mnt/data/ernie/e41_chatd.py`。**
> **分工（一个事实只写一处）**：分段计时与 `read` 成本电池的正本＝[[板端我方代码与产物台账]] §廿八；板端件登记＝同页 §卅一；"KV 常驻设备侧"那五档与 `enableTimeProfile` 归因＝[[KV常驻设备侧实测]]；结论挂载处＝[[NPU调用链]] §7.5。本页只写**窄读链内验证＋实装**这一件事，不复制上面三处的表。
> **证据分级**：A＝板上现读（日志／终端／`md5sum`）；B＝由 A 推导，算式同段给出；C＝外推、未实测；D＝听说。**没执行的步骤一律写成"未执行"**。

## 一、TL;DR

1. **赚到了，5.6 %**：同一条生产步序、同一颗件、两个进程各 12 步——整块读那档 `step_total` 中位 **463.10 ms**、窄读那档 **437.35 ms** ⇒ **省 25.75 ms/步（5.56 %）**，吞吐 **2.159 → 2.287 token/s（＋5.9 %）**（A，算式见第三节）。
2. **数值零风险**：窄读填满缓存后，与同一批 present 张量的**整块重读**逐片段比对，**36 条张量 × 8 头 × 512 槽＝147,456 个 256 B 片段零差异**（A，第四节）。链子与间隙对 §廿九 的 oracle **12/12 全等**（A）。
3. **`forward` 一点没动**：392.27 → 392.63 ms（＋0.36 ms＝＋0.09 %）⇒ 这 5.6 % 全部来自读回段，与算子调度无关（A）。
4. **现役 daemon 已换成窄读**：`e41_chatd.py` 板上 **13,007 B／`3d35ea8e4357c2e5d388bc3b03791e09`**（旧件同目录留底 `e41_chatd.py.b13995c6`，12,051 B）。A/B 各起一个进程、同一条 12 token 提示、`max_new=16`：**生成的 17 个 token id 逐位全等**（A，第五节）。
5. **一个读数坑（别拿 daemon 的 `sec` 当收益证据）**：`step()` 里 `dt` 在**读回之前**就打了快照，所以每 token 的 `sec` 两档都是 0.42，**窄读省的钱不落在这个字段上**；只有回合总 `sec`（13.9 → 13.3 s）看得到。这是现役 `e41_chatd.py:144` 的既有语义，不是我改出来的。

## 二、这 5.6 % 在整步里的位置

§廿八 把一步拆成六段，并给出两条口径线：`PRODUCTION_DT_EQUIV`＝`forward+waitForReady+reset`（＝现役 daemon 报的 `dt`），`POST_DT_TAIL`＝`read_logits+read_kv+argmax`（＝**只动读回这一类优化能碰到的全部空间**）。

| 段 | 整块读 W（ms） | 窄读 N（ms） | 差 |
| --- | --- | --- | --- |
| `forward` | 392.27 | 392.63 | +0.36 |
| `waitForReady` | 25.25 | 25.30 | +0.05 |
| `reset` | 0.02 | 0.02 | 0 |
| `read_logits` | 0.32 | 0.32 | 0 |
| **`read_kv`** | **37.65** | **12.86** | **−24.79** |
| `argmax` | 8.13 | 8.30 | +0.17 |
| `step_total` | **463.10** | **437.35** | **−25.75** |
| `PRODUCTION_DT_EQUIV` | 417.518 | 417.924 | +0.41 |
| `POST_DT_TAIL` | 46.107 | 21.503 | −24.60 |

- **算式**：25.75 ÷ 463.10 ＝ **5.56 %**；1000÷437.35＝2.2866、1000÷463.10＝2.1594、2.287÷2.159−1＝**＋5.9 %**（B，分子分母都是上表 A 档读数）。
- **中位数不可加**（照实记，不做平滑）：N 档六段中位之和 439.43 vs `step_total` 中位 437.35（Δ 2.08 ms）；W 档 463.64 vs 463.10（Δ 0.54 ms）。
- **读回占 `POST_DT_TAIL` 的 81.7 %**（37.65÷46.107）⇒ 这一类的天花板本来就是读回，`argmax` 那 8 ms 窄读碰不到。

## 三、链内两档（`e41_narrow.py`，A）

探针把 §廿八 电池预测的窄读**放进现役步序**跑：单参数 `Session.forward(self._tensors())`、`dev.reset(1)`、logits 整块读、padfix、`argmax` ——与 `e41_chatd.py:135-160` 同序，只差读回那一行。两档各起一个进程（`apply` 不可重入）。

| 档 | 读法 | 装载 | `apply` | 备注 |
| --- | --- | --- | --- | --- |
| W | 整块（现役原样） | `json+raw` 53.4 s | 43.6 s | 起手 `CmaFree` **3,968 kB** |
| N | 窄读＋每步 `AUDIT` | `json+raw` 54.1 s | 50.5 s | 起手 `CmaFree` 112,324 kB |

- **对照 §廿八 的预测**：电池预测窄读净省 **26.07 ms/步**，链内实测 **24.79 ms**（＝预测的 95.1 %）；窄读绝对值电池 9.11 ms vs 链内 **12.86 ms**，多的 **3.75 ms** 是每条张量的 `t.offset()`／numpy 视图／padfix 这些 Python 侧动作（电池那档是纯读循环）——**这一段没再拆细，标 B**。
- **§7.4 那条起跑门禁（`CmaFree ≥ 126 MiB`）这两场都没过**（W 起手只剩 3,968 kB），而 12 步照样跑通、数值逐位对 ⇒ **这条门禁至少对"纯 host 侧 KV 往返"这条路不是必要条件**（A 级读数，**只到"这两场没挡住"为止，不等于 CMA 不重要**）。
- **数值**：两档的 `argmax` 链与 `top1−top2` 间隙对 [[板端我方代码与产物台账]] §廿九 的 12 步 oracle **都是 12/12 全等**（A）。

## 四、正确性：为什么"只读一槽"是安全的（A＋B）

前提＝**每步 present 只有 `past_len` 那一槽变**。这个前提以前只在"链子逐 token 对得上"这一间接证据上成立。本轮直接核：窄读填完后，把同一批 present 张量**再整块读一遍**当参照，逐 256 B 片段比。

- **比的是什么**：36 条张量，每条 `[1,8,512,128] fp16`，切成 `[head, slot, 256 B]` 视图 ⇒ 每条 8×512＝4,096 片段、合计 **147,456 片段**（算式 `36×8×512`）。
- **读数**：`AUDIT slot=12 tensors_with_diff=0/36 identical=yes` ⇒ 第 12 步时，**窄读攒出来的整份缓存与设备里那份逐字节相同**，包括从没被窄读碰过的 499 个槽（它们与设备值一致，说明设备侧确实不改历史槽）。
- **轴序**：`[batch, head, slot, head_dim]` ⇒ 一槽新 KV 在每条张量里是 **8 个不连续 256 B 片段**，偏移 `(h*512 + slot) * 256`。这就是电池里那 288 次碎片读的来源，也是它没跌进"连续行"那条捷径的原因（slot-major 重编＝§28.3 的 D 档，她 11-01 裁放着不做）。
- **槽号口径**：daemon 里 `past_len = i + POS_OFFSET − (1 if PADFIX and i≥1 else 0)`，读回的槽就是这个 `past_len`；`MAX_SLOTS=511 < 512` ⇒ 实装里加了一条 `past_len >= kv_depth` 就抛的门禁（防的是"以后重编出更短 cache 时静默越界"，不是现在能走到的分支）。

## 五、实装与 A/B（A）

改动只有 `step()` 读回那一段＋`__init__` 里建视图，**其余一行没动**（`diff` 只出现这两处，见台账 §卅一）。旧件先落盘再替换：

| 件 | 板上路径 | B | md5 |
| --- | --- | --- | --- |
| 现役（窄读） | `/mnt/data/ernie/e41_chatd.py` | 13,007 | `3d35ea8e4357c2e5d388bc3b03791e09` |
| 留底（整块读） | `/mnt/data/ernie/e41_chatd.py.b13995c6` | 12,051 | `13995c641b4808d33891ce1ffdb734a8` |

A/B 跑法（`ab_chatd.sh`，两档**各自一个 socket**、档间等到板上没有 `e41_chatd` 进程再起下一档）：同一条 `ids=[4,23,23,23,2969,93919,4,93963,93919,253,172,177]`、`max_new=16`。

- **OLD**：pid 19738、`apply_s` 47.1 s、`end.ids` 17 个、`reason=limit`、回合 `sec` **13.9**。
- **NEW**：pid 19880（＝自己起的进程，jsonl 第一行是 `{"status":"starting"...}`）、`apply_s` 46.6 s、`end.ids` **与 OLD 逐位全等**、`reason=limit`、回合 `sec` **13.3**。
- **回合差的换算**：0.6 s ÷ 29 步（`len(walk)=13` ＋ 16 次生成，`total=len(walk)+max_new`）＝**20.7 ms/步**，比探针的 25.75 ms 小；`sec` 只到 0.1 s 分辨率、单样本 ⇒ **这一条只当"方向一致"的交叉核对（B），性能数以第三节 12 步中位为准**。
- **第一次 A/B 作废（照实记）**：`E41_IDLE=2` 下 NEW 在 OLD 退出前就连上了**同一个旧 daemon**，两档跑的都是整块读。判据＝NEW 用时 14 s（冷装载要 ~100 s，不可能）。已改成每档独立 socket ＋ 起档前 `wait_clear`，上面读数是重跑的那一场。

`forward` 里那 41.8 % 的 `other` 与 `op_id 9930` 那颗 ~57 ms 的 memcpy，**本轮用 `enableTimeProfile` 对两档做了归因**，读数与判定在 [[KV常驻设备侧实测]] §十，结论两句：**"58.8 ms＝KV 上行"判否**（B），**砍 `max_seq_len` 能不能砍到它 ⇒ 11-03 已立案跑完**（两颗更短 cache 的件 E42／E43 上板同场对照，`9930` 随窗口线性缩，窄读现役路径一步 437.77 → 295.38 → 230.27 ms）——**读数在 [[编译窗口裁剪实测]]，本页不复制**。两句要给后来人的：**省下的钱不落在这页的 `read_kv` 段上**（窄读的回抄量与窗口无关，三档 `read_kv` 都是 ~13 ms），它落在设备侧的 `forward` ⇒ **这两块优化空间互不重叠，可以叠加**；换窗口＝砍上下文容量（NS 就是能存的槽数），是产品取舍，**等她裁**。
