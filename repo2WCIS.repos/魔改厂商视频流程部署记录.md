# 厂商视频流程部署

**（SDI 相机 → PL → NPU → HDMI → PC 预览）**

**这一页管什么**：把厂商那条"SDI 摄像头进板、PL 取图、NPU 推理、HDMI 送显、再往 PC 出预览"的视频链在悟净（FMQL30TAI／ZG330）上**部署起来、判得出活死、并且知道哪些坑已经踩过**。

**判级口径**：A＝板上实测原文；B＝厂商源码或文档直证；C＝推断／机制未查；D＝外部素材、平台标注不明。**写在这页的每个数字都带级**。

## 二、链拓扑与每段的归属

```
SDI 相机（3G-SDI 1080p，实测交图 30.06 fps，A）
  → XS1 → LMH0344 解串 → PL rx_sdi（GT/CDR）        ← 全设计只有 1 路 SDI 输入
  → PL ImageMake（整数步长缩放＋裁剪，基址 0x80000400）
  → PL DDR（给 NPU）／PS DDR udma chunk（给显示）
  → SDICameraInputActor（轮询 0x40080058 取帧，没有 V4L2）
  → NPU yolov5s/v8（icore，npu=0x40000000）＋ CPU 后处理与画框（OpenCV，RGB565 帧上画）
  → RGB565HDMIDisplay::show（写 0x40080054）→ HDMI
  →（我方）LivePump：cv::resize + cv::imwrite → /tmp/live.jpg → mjpeg_server :8090
```

| 环节 | 实现在哪 | 关键约束 |
|---|---|---|
| 输入物理层 | **只有一路**：`XS1 → LMH0344 → SDI0_RX → DP0＝管脚 AB3/AB4`（RTL＋xdc＝A；"这对线＝DP0"＝B 级惯例）。**换到板上其余三个 SDI 输入口必然全 0** | 别再试别的口（[[确认摄像头是否识别]]） |
| 缩放／裁剪 | **PL，整数步长**：`RATIO_W=CAM_W/NET_W`、`RATIO_H=CAM_H/NET_H` 是 C++ 整数除法（`et_device.hpp` 的 `preprocess_plin`，写 `0x40080020/0x24`，B） | 见第四节 |
| 色彩／格式 | **PL**：格式寄存器 `0x78` 在 RGB565 与 YUV422 间二选一（B） | —— |
| 推理 | **NPU 硬核**，不是 VPU（B） | [[NPU调用链]] |
| 后处理＋画框 | **CPU**（`post_detpost_plin`＋OpenCV） | "完全 FPGA 实现"这话要打一半折（A，源码级） |
| 送显 | **PL** | —— |
| 硬编（可选档） | **VPU**＝`/dev/video0`，`mve@f0020000`，china,linlon-v5，走 `amvx.ko`（A） | 官方 YOLOv5 流程**完全不碰它** |

**全程没有 V4L2、没有 `/dev/video*` 相机、没有 `/dev/fb*`、没有 `/dev/dri`、没有 DRM**（A）。所以"系统识别到摄像头了吗"这个问法在这块板上不成立，只能按取证 §十 那张四步检查表逐段判。

## 三、部署前置（缺一项就别起链）

1. **位流里有 NPU，也有 `rx_sdi`**。NPU 是 PS 通往 PL 的**唯一 AXI 端点**——位流没它时，进程一摸 `0x4000_0000` 窗口就整机楔死、零 printk（A，台账 §十九 与 [[PS-PL_AXI_HP口与复位语义]]）。开机门禁＝`md5sum /mnt/boot/BOOT.bin` 必须是含 NPU 的那颗；**但 `/mnt/boot` 挂不挂随开机变**，目录里看到的 `AA.bin`／`BOOT_NEW.bin` 是根文件系统的东西、不是"位流没了"（A，10-14）。另一会话每次发布都重核 boot 哈希 ⇒ **点火前当场再 md5，别用上一次的结论**。
   - 判"位流是不是那颗带 SDI 的设计"，取证 §十 第 2 步原本写的"读 BOOT.bin 头部位流名字段"**实测不可用**（厂商几颗 `BOOT.bin` 都解不出设计字符串，只有裸 `.bit` 在 0x10 自报 `ai7030_top;UserID=…`，A）⇒ 改成**逐窗口比对**（64 字节高熵窗口＋`.bit`→`.bin` 字内字节序反转）；现装 `aca4612b…` 与本地 `ai7030_edif_top.bit` **21/21 全中** ⇒ 带 `rx_sdi` 的份就在 PL 里，不用再动 BOOT.bin。
   - `cat /sys/class/fpga_manager/fpga0/state` 只能说"PL 处于 operating"，**不回答配进去的是哪颗设计、有没有 NPU**（C：没有任何取证把 `state` 与位流身份挂钩）。
2. **依赖库在位**：`libicraft_{xrt,xir,utils,hostbackend,buyibackend,zg330backend}.so` 与运行时用户态加载的 `libaxizg330aiu.so`（561,528 B，属 `icraft` 包，自己 `open("/dev/mem")`＋`open("/dev/udmabuf0")`，A）。**`ldd` 全解析≠能跑**（坑 1）。
3. **udmabuf／CMA 前提**：`u_dma_buf` 模块在、`/dev/udmabuf0` 在（A）。板上 993 MB 里 **256 MB 是 CMA 池**，`MemAvailable` 不能当起跑门禁（A，[[板端内存上限与心跳日志]]）。
4. **静态第三方依赖**（交叉编译侧）：`/ModelzooDeps/aarch64/Static` 里的 aarch64 OpenCV＋yaml-cpp，来自 `IcraftMdzThirdParty.deb`；板上 rootfs **零条 `libopencv_*`** ⇒ 一律静态链（A）。
5. **没有 HDMI 显示器时的观测手段**：只有两条——接显示器，或用我方插桩版走厂商 `memchunk.read()` 把 `display_data_` 编成 JPEG 推出来（后者必须交叉编译）。**直读 `/dev/udmabuf0` 和只看 `0x40080058` 的 bit0 都不算判据**（A，取证 §十 作废表：VTC 模式下连续三次采样 4 MB 逐字节相同而帧均值在跳；只编程 0 号通道时四路 `+0x58` 恒读回 `0x1`）。

**两个 yaml 键不能当开关用**（A，源码直证）：
- `detpost: true` **不生效**——分叉只看网络 JSON 里有没有 `DetPostNode`/`DetPostZGNode`；这个值只被打印一遍，没有任何消费者。
- `conf` **同时改硬件**：`updateDetpost` 把新值回写进 DetPost 算子的 `data_thr`，再在 CPU 侧对 `sigmoid(obj)×sigmoid(cls)` 二级串联筛。**⇒ 跨模型档比"每帧检测数"是无意义的**（各档自带 `data_thr` 就不同：`[-15,-18,-19]` vs `[-14,-17,-19]`）。工作点建议见 [[板卡镜像实测取证#十三、conf 门限扫描（D-31 队列第 ② 项，2026-10-04 实测）|取证——十三]]。

## 五、起链与停链

**现役入口＝`/root/live_start.sh`（台账 #190，4,236 B／`0ca000c0…`）**，`sh /root/live_start.sh start|stop|status` 一条顶三条。它内部展开的还是台账 §一 那套管道（老命令留着是因为它写清了每个必需项的原因）：

```sh
cd /root/plin_demo/PLin+SingleNet+HDMI && setsid sh -c \
  'sleep 21600 | env HDMI_LIVE_EVERY=3 HDMI_LIVE_SCALE=0.5 HDMI_LIVE_QUALITY=60 \
   ./sdicamera+yolov5+hdmi configs/ZG/sdicamera+yolov5+hdmi.yaml 2>&1 \
   | python3 /root/rotlog.py --out /tmp/live.log --max 16000000' \
  < /dev/null > /dev/null 2>&1 &
```

| 项 | 为什么必需 | 级 |
|---|---|---|
| `sleep 21600 \|` | demo 的 `main()` 结尾是 `std::cin.get()`，**stdin 一 EOF 就直接 stop 退出**；同时它就是**看门狗**——时长到点整条链自己停，属预期行为 | A |
| 两层 `setsid`（demo 一层、`mjpeg_server.py`／`h264d.py` 各一层）＋`</dev/null` | 从 SSH 的 `exec_command` 起后台，进程要活得比那条会话久 | A |
| `rotlog.py --max 16000000` | 不装它，厂商那套 debug 日志以约 **2 MB/分钟**涨（实测 20 分钟 46 MB），而 `/tmp` 就在根分区上 | A |
| `HDMI_LIVE_EVERY/SCALE/QUALITY` | 三个"预览档位"旋钮：每 N 帧推一张／缩放系数／JPEG 质量。现役 960×540·q60·10 fps（`EVERY=3` 恰好整除采集侧 30.06 fps）；实测 `enc_us` 25.4 ms、25.5～27.1 kB/张、demo %CPU 134→95 | A |
| `LIVE_CFG`／`LIVE_BIN` | 换 yaml／换二进制。**不设 `LIVE_CFG` 就落回厂商相机 yaml**（＝回滚路径） | A |
| `LIVE_MODE` | `jpeg`（默认，实测能播的那条）／`hls`（见第七节，**判不可播**） | A |
| `LIVE_FPS` | 默认 **30**；相机是 1080P25 时必须改 25，否则泵按 30 切段、时间戳也按 30 打 ⇒ **播快 20 %** | A（`live_start.sh:26-28`） |

**开机自启**：`/etc/rc.local` 第 42–44 行（台账 #191，改前备份 `/root/rc.local.bak-live-20261014T054955Z`）。想不起链＝`touch /root/live.disabled`。**已知缺口**：rc.local 那三行不带 `LIVE_CFG`，所以重启后一定落回相机 yaml——10-14 08:41 UTC 第一次带钩子的重启实测自启通了（jpeg 档一套＋看门狗都在），但黑屏，因为输入侧 `data_in_num=0`（A）。恢复＝`LIVE_CFG=configs/ZG/vtc-test.yaml sh /root/live_start.sh start` 先自证 PL→PS 通路。

**VTC 正控**：`vtc: true` 那一轮是**检查表第 3 步**，用来证明"板侧 PL→PS DDR→NPU→显示缓冲是好的"，画面是测试图形、`last_results size` 恒 0，**不能当"摄像头识别成功"的证据**（A，10-05 差分：同一颗二进制 10 分钟内两轮只差 yaml 一行——VTC 轮 0 错误 80 fps，SDI 轮 0 帧）。

**停链**：`live_start.sh stop`／PC 侧 `board-live-stop.py`（先抓 `live.log` 尾部取证再 `pkill`，验 8090 已释放，最后清 `/tmp/live.*` 含 `live.jpg`）。停止期抛 `terminate called ... IcoreActor: Failed to pop from input queue` **是正常现象、不是故障**（A）⇒ 判这一轮跑得好不好只看运行期间的 `ps_frame_ok` 与 reset 计数。

## 六、判活／判崩

**判活按模式分两套**（A）：

| 模式 | 判据 | 读数位置 |
|---|---|---|
| `jpeg`（现役） | `/tmp/live.stat` 那行的 `unix` 在不在走；PC 侧看 `curl :8090/stat` 的 `age_s`（＝现在减 `live.jpg` 的 mtime），几秒内＝活，几分钟以上＝demo 已退 | `/tmp/live.stat` 一行 `sent= jpeg_bytes= enc_us= out= src= q= pid= unix=`，**每 30 次出图才重写一次** |
| `hls` | 泵 `state`（`seq/fps/frames/drops/dead`）在走，**且** `.ts` 段大小不为 0 | `/dev/shm/h264/state`、`/dev/shm/h264www/` |

**"有画面但是死的"这一句话对应三种不同成因，只有 stat 与日志尾巴能区分**（A）：

1. **看门狗到点**（2026-10-01 03:35 北京首次发生）：demo 与 rotlog 正常退，`mjpeg_server.py` 不跟着退、把最后一帧供了 7 小时+。
2. **异常带走 demo**（10-05 17:51 UTC）：`ZG330 ImageMake Timeout after 1000 ms, data_in_num=92800` → `et_device.hpp:1270` 抛 `Check failed` —— 这一处**被 catch 住了**，进程继续；**1.1 s 后** `Session::forward` 抛 `sync failed in op_id:685's output_tensor`，**这一处没人 catch** → SIGABRT 整个 demo。"ImageMake 超时导致后续 op 同步失败"这条因果＝**B**（相邻 1.1 s＋op 685 的输入正是 ImageMake 产出缓冲，无寄存器级证据）；"什么让 ImageMake 搬不满一张图"＝**C，仍未取证**。
3. **进程活着但 stat 冻住**（10-05 21:47:04）：pid 仍在、`live.log` 照写，`live.stat` 冻在 21:47:01、`ImageMake Timeout` 累计 4203 次 ⇒ 判据由此修订为**"stat 停更即按不可用"**（A，取证 §十八）。

**上游侧的三种 `data_in_num` 签名互不相同，别混成一类**（A，取证 §十八）：`92800`＝640×352 满图 225,280 的约 41%（搬进来一部分）；`32000`＝同样"部分"、比例更低；`0`＝**一个字节都没到**（另一类故障：相机／制式／线那一侧）。

**判"这颗模型在不在用 NPU"别看 `ps`**：用 `/proc/*/map_files` 里 `udmabuf` 的计数（A，取证 §十八用它证明评测开始时 NPU 空闲、直播链已死 35 分钟）。**网页 200 也不等于直播活着**——`/` 一直 200，只有 `/snap.jpg` 会 503。

**两条作废的判据**（都实测过，别再走）：`ls /dev/video*` 找相机（那颗是 VPU）；直读 `/dev/udmabuf0` 看字节变不变；`0x40080058` bit0＝1 当"帧到了"。

**板侧观测边界**（A，10-10）：内核**零温度读数**（无 thermal_zone／无 hwmon）⇒ 过热判不了；无 `kern.log`／`syslog`；`dmesg` 是环形缓冲（本轮起点只剩 697 s）⇒ "开机以来没有 X"这种负断言不成立。

## 七、编码与出流（可选档，现状：HLS 判不可播，JPEG 档能用）

**厂商 YOLOv5 流程与 VPU 完全不碰**（A，源码级）⇒ 硬编不是"打开某个配置"，是我方自己写的 actor。能力面／格式清单／66 条控制的正本在 [[我方在板外设#7.4 缺什么（这三条缺项决定了率控，A）|我方在板外设 §7.4～7.8]]，这里只留部署口径：

| 结论 | 级 |
|---|---|
| 率控在用户态**打不开**：`bitrate_mode`、`gop_size`、`header_mode` 三个控制 ID 在本驱动 `VIDIOC_QUERYCTRL` 直接 EINVAL＝不存在，`VIDIOC_S_PARM` 无 handler（ENOTTY）⇒ 码率完全由画面内容定 | A |

## 九、回滚与"别动现役"

- **尺寸档回滚**：不设 `LIVE_CFG` 重跑起链脚本即回 640×352（A）。
- **模式回滚**：`LIVE_MODE=jpeg` 就是能播的那条；hls 档在 #195 那行修掉之前不要当交付面。
- **不自启**：`touch /root/live.disabled`；rc.local 那三行是独立标记块，随时整块删。
- **现役链现在处于"待用"**：她 10-14 判"暂时用不到"＝**原样常驻**，不要主动 `stop`、不要改默认档、不要写 `live.disabled`（这是决定，不是技术状态）。
- 板载编译只允许**单文件小工具**（`sdi_probe`／`sdi_stat.py` 这类）；整套 demo 别想在板上编——993 MB 内存、匿名页额度只有 700～825 MB。
