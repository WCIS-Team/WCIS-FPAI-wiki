# 单所有者摄像头与H264直播

本页拆解 `ps_app/src/wcis_camera_owner.cpp` 及其配套运行时：一个原生进程独占 iCraft SDK 设备、分配器与 VPU，摄像头采集、FAC1 预处理、NPU 推理命令全部串行经过它；H.264 预览由 FFmpeg `h264_v4l2m2m` 硬编 + HLS/fMP4 分片对外发布，8092 只读共享同一份 `/dev/shm` 发布产物。

## 单原生所有者进程 Owner

### 定位与职责

`Owner`（`ps_app/src/wcis_camera_owner.cpp:44`）是板端唯一允许打开 iCraft SDK 的常驻进程：持有 `Device::Open("axi://zg330aiu?npu=0x40000000&dma=0x80000000")`（`open()`，`wcis_camera_owner.cpp:205`）这一个设备句柄、同一套内存分配器，以及 VPU 编码器实例。摄像头 DMA、FAC1（PL CustomOp）、NPU 模型、VPU JPEG/H.264 编码都在这一个进程内完成；Python 侧（`npu_photo/camera_owner_runtime.py:51` 的 `CameraOwner`）只做进程托管、校验和命令收发，**不触碰 SDK**。

### 接口/数据通路

- 进程入口契约（`main`，`wcis_camera_owner.cpp:563`）：`argv` 依次为模型 manifest、boot_id、工作目录、运行秒数、模式（`vpu`/`no-camera`/`pl-preview`）。启动即校验：boot_id 必须与 `/proc/sys/kernel/random/boot_id` 一致；工作目录必须是 `/dev/shm/wcis-owner-<session>`（tmpfs 隔离工作区）；环境变量传入的两把锁 `WCIS_NPU_LOCK_FD`、`WCIS_CAMERA_LOCK_FD` 必须能 `flock(LOCK_EX|LOCK_NB)`（`wcis_camera_owner.cpp:569`）。
- Python 托管（`camera_owner_runtime.py:90-117`）：打开 release 的 `npu.lock` 与 `/root/wcis-camera-preview/camera.lock` 两把文件锁后 `Popen` 并 `pass_fds` 传给子进程；启动回执必须满足 `protocol=2`、`single_sdk_owner=true`、`device_opened=false`（就绪时尚未开 SDK，会话惰性创建）。
- 命令通道：stdin 单行 JSON 命令 → stdout `WCIS_OWNER_RESULT ` 行 JSON 回执（`emit`，`wcis_camera_owner.cpp:28`）。命令集：`latest`（快照）、`begin`/`transform`/`verify`/`forward`（帧租约生命周期）、`release`。Python 读线程 `_pump`（`camera_owner_runtime.py:138`）按行解析进 `queue.Queue(maxsize=2)`，日志另存 `native-stdout.log`（上限 4 MiB），防止无请求时 stdout 堵死。

### 特色设计

- **启动前全量校验**：可执行文件 SHA-256、`models.json` 与每个模型 `json`/`raw` 文件的 SHA-256 与 manifest 内记录逐一比对（`camera_owner_runtime.py:76-88`）；`verification.json` 的 `pipeline_id` 必须等于 `yunet-mf-<precision>-npu:sha256(models.json)` 且 `all_passed`，否则拒绝服务——只有通过验证的模型发布才允许对外供图（`serve_photos.py:50-52` 同样把关）。
- **发布准入证明**：`CameraOwner` 启动前读 `camera-control.json` 的 boot 证明与 `/root/wcis-face/video-stream-current.json`，要求 `verified_boot_id` 与当前 boot 一致、release 路径一致（`camera_owner_runtime.py:65-69`）；每次 `guard()`（`:121`）复读 boot_id、隔离标记与进程存活。
- **优雅关闭**：`close()` 只关 stdin 用 EOF 排空在途 VPU/DMA 并 `wait(timeout=35)`，注释明确“never SIGKILL this owner”（`camera_owner_runtime.py:264-280`）；停止回执另存 `<pid>-owner-stop.json`，不受日志容量影响。

## 命令串行化与故障隔离

- Python 侧 `command()` 用**非阻塞** `busy` 锁：已有一条命令在途直接抛错“do not queue”，绝不排队旧帧（`camera_owner_runtime.py:160-170`）；8091 的照片/人员库操作再由 `serve_photos.py:243` 的全局 `busy` 锁串行，冲突返回 409。
- C++ 主循环只做 `poll(STDIN)` + 分发（`wcis_camera_owner.cpp:545-548`），所有 SDK 调用都发生在主线程；采集在独立线程，但采集线程只 memcpy 预映射的 UDMA 指针、不调用 SDK/分配器（`wcis_camera_mmio.hpp` 仅开放 2 个写偏移）。
- 每条命令回执都带 `frame_id`/`frame_token`/`single_owner=true`/`device_closed=false`，Python `FrameWorker.command`（`camera_owner_runtime.py:34-41`）逐项核对，防止串帧或设备被别的路径关闭。
- 任何异常走 `fault()`（`wcis_camera_owner.cpp:70`）：把 `boot_id`、`phase`、`automatic_retry=false` 写进 `/root/wcis-face/hardware-review-required.json` 与持久目录副本后 `std::_Exit(3)`；`guard()`（`:76`）在每次命令前检查同一 boot 的隔离标记——**硬件故障后不自动重试 SDK**，需人工审查。

## 摄像头采集：双 UDMA 缓冲与 MMIO 契约

### 定位与职责

把 SDI 1080p 输入按 30 fps 上限采成 PS 可见的原始帧（默认 960×540 RGB565），供识别与编码两个消费方共享；采集线程独立于 SDK 命令线程。

### 接口/数据通路

- 寄存器基址 `CAM=0x40080000`（`wcis_camera_owner.cpp:69`）。`configure_camera()`（`:298`）先读固件魔数 `0x0c=0x20230218` 与 busy 位，再在 `udma` 内存区 `malloc` 两块 `CAMERA_BYTES` 缓冲，要求 64 字节对齐、落在实测窗口 `0x30100000..0x38100000`、互不重叠；随后按表写入 PS 取帧分支寄存器（`0x18/0x44/0x08/0xb4/0x5c/0x60/0x64/0x68/0x78/0x6c`）并逐字回读校验。注释说明：厂商构造函数会顺带打开旧 PL→ImageMake 分支（`CAM+0x18=1`），这里显式清零、只配置文档化的 resizePS 寄存器。
- 单次采集 `capture()`（`:341`）：`arm_camera` 写目标地址 `0x50=addr>>3`、触发 `4=1`，并**当场观察本次请求把 DONE（0x58 bit0）清零**——避免模型调用横跨整个 DMA 传输后把上一次的完成误认为本次完成（`:327-331`）；`drain_camera` 用 `wcis::wait_capture` 等 DONE，2 秒超时即 fault、不重试。读完缓冲 A 前**先对 B 提交下一次请求**（`:347` ping-pong 提前取帧），CPU 复制前后有 `CameraMmio::before_copy()` 的 `dmb sy` 屏障。
- `CameraMmio`（`ps_app/src/wcis_camera_mmio.hpp:10`）：直接 `mmap /dev/mem` 摄像头页，读限 `0x130` 内 4 字节对齐偏移，写只允许 `0x04`（触发）与 `0x50`（地址）两项，首尾 `dmb sy`——这是“固定摄像头孔径，不是通用寄存器工具”的窄接口。
- 采集线程按 `capture_due = started + 1/fps` 帧距调度（`:416-423`），`WCIS_CAMERA_FPS` 限 1..30；启动时两块缓冲各做一次“CPU 映射 vs SDK 读回”逐字节比对（`capture(true)` 两次，`:415`），通过后 `mapping_verified=true` 才允许线程直读。
- 1080p H.264 路线改用 `DirectCamera`（`ps_app/src/wcis_direct_capture.hpp:5`）：同样的窗口/对齐/重叠检查与 PS 分支寄存器表（但 `0x7c=1920` 行宽、`0x78=1`），双缓冲 `pause()`/`resume()` 保证命令边界处采集完全静止（`:54-56`），`peek()` 只发布最新不可变 `DirectFrame`。

### 关键参数/状态机

- `meta()`（`wcis_camera_owner.cpp:80`）发布的 status 字段固定了口径：`timestamp_basis=capture_request_lower_bound`（帧时间取“采集请求时刻”这一保守下界，另记 `capture_completion_observed_at`）、`capture_mode=preallocated_ping_pong`、`capture_scheduler=independent_worker`（外部分支为 `on_demand`）、`sdk_calls_on_capture_thread=false`。
- 计数器 `captured/encoded/commands/camera_requests/camera_drained` 全部原子，停止回执要求“请求数 = 处理帧数 + 排空 1 帧”可对账。

## frame lease 帧租约

### 定位与职责

一帧图像上传 PL DDR 后，在多次 PL 变换/多次 NPU 前向之间**原地复用**：源只上传一次，检测、逐脸对齐、PAD 全部读同一块保留内存。租约协议在 `npu_photo/src/frame_lease.h:27`。

### 接口/数据通路

- 布局：`[64B 头守卫][对齐后的源图 pitch*h][640*640*4 输出区][64B 尾守卫]`，上限 `MAX_BYTES=64 MiB`、必须落在 SDK 分配窗口 `WINDOW=0x08000000` 内（`frame_lease.h:15-16`）。
- `begin` 命令（`wcis_camera_owner.cpp:480`）：校验源几何（w/h ≤8192、pitch 8 对齐、`pitch ≥ w*bpp`）、以 `0xa5` 初始化整块、上传源到偏移 64、用 SDK 在**指定基址**精确 `malloc` 并回读校验（`frame_lease.h:57` `Reservation` 要求“SDK did not reserve exact frame interval”才算成功）。摄像头 960×540 RGB565 帧保留模型会话缓存；更大的照片租约先 `release_sessions` 再分配且不缓存（`:488-494`），维持单帧内存预算。
- `OwnedFrame::check()`（`:32`）：每次 PL/NPU 操作前后重读头尾守卫（魔数 `FAC1_FRAME_V1` + token + id/w/h/pitch，尾守卫整体 `XOR 0x5a`），并遍历分配器全部 MemChunk 检查**无任何其他分配与保留帧重叠**。
- `verify` 命令（`:514`）：把 DDR 里的源整块读回与上传文件全量比对（`full_source_equal`），是可选的显式校验路径；`release` 释放租约与内存。Python 侧每个 job 的 `frame_token` 由 uuid 生成，跨命令绑定（`pl_preprocess.py:124-125`）。

## PL FAC1 变换的完成判定

`owner_pl::run_transform`（`ps_app/src/wcis_owner_kernels.hpp:159`）把缩放/补边/对齐统一成一次“描述符 + START”的 PL 操作，寄存器基址 `REG=0x400c2000`、ID 魔数 `0x46414331`（FAC1）。特色在于完成判定：

1. START 前把输出区初始化为 `0xa5` 并**读回确认可见**（建立本次输出的新边界，`:183-190`）；
2. 描述符 15 字（帧 id、源/输出地址、pitch、(h,w)/(ch,cw)/(dh,dw)、rgb565/replicate/border 标志、6 个 inverse Q16.16 仿射系数）逐字回读（`:192-193`）；
3. START 后等 `REG+4` 的 DONE 位，同时校验错误位、帧 id、输出像素数（`:197-199`）；
4. DONE 之后**继续轮询读回，直到每个像素的 alpha 字节都被 PL 写为 0** 才交付（`:204-212`）——FAC1 原生写端口没有 DDR 写响应，DONE 返回与 CPU 读到完整输出之间存在窗口，多读同一次操作、不重提交；
5. 任何一步失败写隔离标记退出，不接受部分结果。

## camera_interlock：准入与快照（兼容路径）

`npu_photo/camera_interlock.py:14` 的 `CameraInterlock` 是单所有者之前的 SDK 准入协议，现仍在 `--camera-control` 模式与 owner 启动证明中使用：

- `guard()`（`:27`）：核对 `boot-proof.json` 的 boot_id 与 `BOOT.bin` SHA-256、检查当前 boot 隔离标记。
- `snapshot()`（`:57`）：读采集工作区的 `latest.frame` 包（4 字节小端长度 + JSON 元数据 + JPEG），校验 source/boot/pid/state、1.5 秒新鲜度、960×540 尺寸与 JPEG SOI/EOI，附 `age_at_admission_s` 与 SHA-256。
- `request()` 上下文（`:136`）：先拿 `camera-admission.lock` 排除所有其他照片请求 → 停掉旧采集服务并核对退出回执（exit_code 0、session 匹配）→ **试探性加锁 `npu.lock`** 确认硬件锁确实空闲 → yield 推理 → finally 里重启服务；warm_process 模式改用文件握手（`pause.request`/`paused.json`/`resume.request` 带 token 与 pid，`:106-134`）实现不停进程的暂停/恢复。任何异常路径写隔离标记（`quarantine`）。

## 请求合并：share_inflight_only

`npu_photo/camera_requests.py:7` 解决多客户端同时打 `/api/recognize-camera` 的竞争：

- 第一个到达者成为 leader 执行完整识别；后来者登记为 follower，共享同一 `threading.Event` 等结果，`deepcopy` 各自一份响应。
- 最多 8 个等待者（超限 429）、跟随等待上限 15 秒（超时 503，**不取消**正在访问硬件的 leader）。
- 完成后 `self.current=None`，**下一轮请求取新帧**——已完成请求永不当缓存用。
- 每份响应注入 `camera_delivery={shared,wait_ms,result_delivery_age_ms}`；对 PAD 证据把 `frame_age_ms` 加上交付延迟，超过 `max_age_ms` 即改标 `stale`（`:44-48`），防止旧帧的防伪结论被当作新鲜证据转发。

## H.264 硬编码与 HLS 分片

现役部署是**外部 FFmpeg 路线**（540p），仓库同时保留**集成 VPU 路线**（540p NV12 / 1080p UYVY 直送，`WCIS_PREVIEW_CODEC=h264` 且不经外部 FIFO）。两条路线共用同一套 HLS 媒体读取层。

### 外部 FFmpeg 路线（部署形态）

- `serve_photos.py:60-65`：当 `WCIS_PREVIEW_CODEC=h264` 且 540p 时构造 `ExternalH264`（`lan_stream/external_h264.py:92`），它创建 FIFO `video-input.fifo`、拉起两个 FFmpeg 子进程并把环境变量注入 owner：
  - 编码器：`-f rawvideo -pixel_format uyvy422 -video_size 960x540 -framerate 30 -i <fifo> -c:v h264_v4l2m2m -pix_fmt uyvy422 -num_output_buffers 6 -num_capture_buffers 4 -b:v 2M -g 30 -bf 0 -flush_packets 1 -f h264 pipe:1`（`:120-124`）——像素仍由板上 VPU（MVX）硬编，FFmpeg 只是 V4L2 封装；缓冲数是本驱动实测值，不用默认 16。
  - 封装器：`-f h264 → -c:v copy -f hls -hls_time 1 -hls_list_size 12 -hls_segment_type fmp4 -hls_flags delete_segments+independent_segments+temp_file`（`:125-130`）——只复制封装，不做第二次编码。
- owner 侧 `raw_mode`（`wcis_camera_owner.cpp:238`）：`h264_input` 线程从 `DirectCamera` 取最新 1080p 帧，NEON（`vld2q_u8`/`vrhaddq_u8`，`:403`）把 UYVY 行交织成 NV12→UYVY 打包（亮度直取、色度相邻两行均值），写进 FIFO（`raw_write`，`:107`，poll 写超时 3 秒）；每帧在 `raw-inputs.jsonl` 流水journal记录 `{input_index, frame_id, captured_at, synthetic}`，每 1800 帧轮转保留当前/前一文件。
- **VPU 先于 SDK**：`prime_h264_before_sdk()`（`:158`）在打开 SDK 之前用 60 帧合成灰图（`frame_id=0`，journal 标 `synthetic`）让编码器真实产出，等到 `WCIS_RAW_FIRST_OUTPUT` 非空才置 `h264_pause` 并开 SDK——规避“SDK 先开再启 VPU”的 MMU 故障形态。`ExternalH264._wait_reader`（`:144`）持有 FIFO 写端直到首帧输出，防止对编码器过早 EOF。
- **真实采集时间台账**：`Journal`（`external_h264.py:19`）顺序消费 `raw-inputs.jsonl`（要求 input_index 连续、frame_id 单调）；监控线程 `_observe`（`:233`）对每个完成的 HLS 段用 `timing()` 解析 fMP4 的 `tfdt`/`trun` 得到 sample 数，按“整数 sample 计数”而非名义 PTS 定位到 journal 行，把该段的**真实起止采集时刻与源帧号**写进 `seg-XXXXXXXXX.capture.json`——编码器名义时间戳从不冒充采集时刻。状态心跳 `external-video.json`/`packager.json` 每 0.2 秒观察、新帧立即发布、无新帧每秒刷新。

### 集成 VPU 路线

- `H264Encoder`（`ps_app/src/wcis_owner_h264.hpp:15`）：继承厂商 `vpu::Encoder`，`/dev/video0` V4L2 stateful MPLANE，输入 UYVY（1080p 直送）或 NV12（540p），输出 `V4L2_PIX_FMT_H264`，6 个缓冲；控制字：Main Profile、Level 4.1、无 B 帧、无重排序、P 帧距 `fps-1`、I/P QP 26/28、码率 1080p 4 Mbps / 540p 2 Mbps、恒定码率模式（`VIDIOC_S_MVX_RATE_CONTROL`）。
- `h264_nals()`（`:6`）手写 Annex-B 起始码扫描，分出 SPS/PPS 参数集与 VCL/IDR；输出线程（`wcis_camera_owner.cpp:135`）要求**首帧必须是 IDR**，用首个 IDR 的 pts 作时间原点建 `H264SegmentPublisher`。
- `H264SegmentPublisher`（`ps_app/src/wcis_h264_segments.hpp:6`）：按 IDR 切 GOP，写 `raw-XXXXXXXXX.h264.pending` + `.json.pending`（sequence/start/end/origin/frames/fps），close 后 rename 成正式名（原子发布），窗口保留最近 16 段；IDR 间隔超 300 帧即故障。首个编码帧发布后把 `latest.frame` 写成哨兵 `H264_HLS`。
- `H264Packager`（`lan_stream/h264_packager.py:38`）：轮询读取 owner 的 GOP 文件，用板上 FFmpeg `-c:v copy -movflags frag_keyframe+empty_moov+default_base_moof -video_track_timescale 90000` 打成 fMP4，`split_mp4()`（`:15`）把 `mfhd` 序号改写为本 owner 的段号、`tfdt` 重定基到 `start-origin`（90 kHz），再原子发布 `init.mp4`/`seg-XXXXXXXXX.m4s`/`index.m3u8`（滑动窗口 12 段）与 `packager.json` 心跳。命令边界可与 SDK 协同暂停（`pause_h264_for_sdk`，`wcis_camera_owner.cpp:199`：等输入线程 idle 且 `encoded==submitted` 再放行 SDK 命令，钩子挂在 `owner_npu::before_exclusive/after_exclusive`）。

## 8092 只读预览与 8091 的媒体共享

### 定位与职责

`lan_stream/vpu_live_server.py`（默认 8092）是**零硬件**的只读浏览服务：只读 owner 控制文件与 `/dev/shm` 发布产物，与 8091 共享同一采集 owner，绝不起第二个采集/编码进程。8091 自身也通过 `/api/camera/h264/*` 直接复用同一媒体读取函数（`serve_photos.py:120-128`），所以浏览器从任一端口都能取到同一份流。

### 会话状态机 Frames

`Frames`（`vpu_live_server.py:30`）每次 `read()` 走同一条身份链：

1. 控制文件给出 `{source, boot_id, pid, session, directory}`，目录必须形如 `/dev/shm/wcis-*`；
2. boot_id 与 `/proc/sys/kernel/random/boot_id` 比对，`status.json` 的 boot/source/pid 再比对，`process_alive` 检查 `/proc/<pid>`；
3. 按 `codec` 分派：`h264` → 用 `status.h264_encoded_at` 判 2.5 秒新鲜度；`raw_*_external_test` → 读 `external-video.json`，核对 width/height、编码/封装双进程存活、4 秒新鲜度；JPEG → 读 `latest.frame` 包，2 秒新鲜度 + JPEG SOI/EOI。
- `read_if_changed()`（`:37`）用控制文件 stat + 帧文件 stat 组成 token 去重，健康复查固定 4 Hz——录像轮询靠它跳过重复包读。

### HLS 媒体读取与播放器

- `h264_media.py:20` `manifest()`：先验 `packager.json` 心跳（同 session/pid、无 error、4 秒内），再解析 `index.m3u8`（≤32 KiB、`EXTINF` 时长 0<d<10、≤16 段、文件名严格 `seg-XXXXXXXXX.m4s`）；外部路线还要求每段有归属本 session 的 `capture.json` 且 `first_frame>0`——**灰图预热段被天然排除**。最后从 `init.mp4` 提取 `avcC` 得出 `avc1.XXYYZZ` codec 串返回给浏览器。
- `media()`（`:53`）：文件名白名单正则、拒绝符号链接、单文件 ≤8 MiB。
- `h264_player.js:4` `H264Player`：MSE 播放器，按 session 绑定（换会话整段重建），fetch manifest → `MediaSource` + `SourceBuffer` → 追加 `init.mp4` → 顺序追加分片（序号必须连续，断号即报“视频片段中断，正在重连”）；冷启动只取最后 2 段、seek 到缓冲起点实现秒开；追上实时后 `currentTime=end-1` 抑制漂移，超过 20 秒后 `buffer.remove(0, t-15)` 回收缓冲；250 ms 轮询 manifest。
- 并发治理：8092 的 `/stream.mjpg` 与 8091 的 MJPEG 各用 `BoundedSemaphore(4)` 限 4 路预览，编码为 H.264 时 MJPEG 路径直接 410 指向 HLS 清单；页面按 `codec` 在 MJPEG 图与 MSE `<video>` 之间切换（`H264_PAGE`/`PAGE`）。

### PL 预览旁路

`--camera-pl-preview-url` 模式下（`serve_photos.py:39-42,129-136`），连续预览由 PL JPEG/WJP1 UDP 接收器对外供图，8091 对 `/api/camera/status|stream.mjpg|preview.jpg` 做 302 重定向；PS 只在识别请求时按需采单帧（`capture_mode=on_demand`）。H.264 与该模式互斥（`wcis_camera_owner.cpp:246`）。
