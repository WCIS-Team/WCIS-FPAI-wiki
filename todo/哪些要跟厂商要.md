## 一、含 NPU 的位流：要么给器件库实现数据，要么直接给 DCP

**【问什么，可直接发出】**

> 我们在悟净 30TAI 板上用 Vivado 2018.3.1 自己跑"PS＋AI_Mate＋我方视频逻辑"的综合实现，卡在同一个地方：把 `AI_Mate.edif` 链进 `ai7030_edif_top` 之后 `opt_design` 报 `ZGolo/pl_araddr[*]` 等 **109 个 FDCE 无驱动**（Opt 31-430 / Opt 31-67），ERROR 级消息无法降级。已经确认 PS7 与 EDIF 的 `pl_*` 接口连接完整、BD 重新生成结果字节一致。想请你们给其中一种：
> ① 你们做这颗 EDIF 时用的 **PS7 器件库实现数据**——`unisim.btl`、`unisims/PS7.btl`、`xc7z030ai.paspd`、`zynq.lib/padr/rtd/xng`；
> ② 或者你们内部**已经布线完成的含 NPU DCP**（`.dcp`）＋对应 XDC；
> ③ 或者告知什么条件下应该改用 `AI_Mate_no_detpost.edif`（我们怀疑这颗 EDIF 对 PS7 的端口要求和本地器件库里的模型不一致）。
> 我们要的是能在综合报告里复现你们结果，不是口头结论。

**【为什么问】** 本地器件库的 PS7 模型只声明 `AI_OUT*` 不驱动它（`assign AI_OUT*` 全文 0 条命中，A 级：对本机 `S:\apps\Xilinx\Vivado\2018.3\data\...` 的模型文件逐行数出来的），所以只要把 AI_Mate 链进去就一定有未驱动寄存器。而板上跑通过 NPU 的那颗是**厂商预编译**的，我方从没能自己造出一颗既能推理又有视频通路的位流。这条不解决，"推理与直播并存"这种需求只能永远依赖厂商给件。过程与三次失败点见 [[位流构建与SDI信号检测]]。

**【要的答复形态】** 文件（`.btl`／`.paspd`／`.lib`／`.padr`／`.rtd`／`.xng`／`.dcp`）＋ 一句"这颗 EDIF 对应哪块板型/哪份配置"。文件给不到就要**目录树截图**。

## 二、出厂位流的身份口径：哪颗含 NPU、怎么在 `BOOT.bin` 里判、校验值是多少

**【问什么，可直接发出】**

> 请教 30TAI（悟净）两个位流侧的问题：
> ① 出厂 `BOOT.bin`（我们手上这颗 7,023,040 B、MD5 `aca4612b566738350a8c5edac0db1929`、SHA256 `0088581b738fdef741983d2dfd4dd52363d2d90fddc2fa4dafb30cfdb3b23fca`）里，PL 设计是哪个工程的哪个变体？是不是**一定含 NPU**（`axi://zg330aiu` 能打开）？
> ② 我们自己判定"这颗 `BOOT.bin` 里是哪份设计"的办法只有两种：解头部位流名字段（**实测解不出来**，开头是重复的 `feffffea`，只有裸 `.bit` 在偏移 0x10 自报 `ai7030_top;UserID=53210711`）、以及按 `.bit`→`.bin` 字内字节序反转做窗口比对。请教官方口径：**`BOOT.bin` 里位流的名字/长度/偏移字段定义在哪份文档**？
> ③ 如果 PL 里的设计**不含 NPU**，PS 侧访问 `0x4000_0000`／`0x8000_0000` 这两个 GP 窗口会发生什么？我们遇到的现象是整机楔死、串口零行、`dmesg` 零条 printk、只能物理断电——想确认这是不是设计上的必然（无从设备的 AXI 从机 ⇒ 互连挂住）。
> ④ `fpga_manager/state = operating` **不能**用来判断是哪份设计，对吧？（我们已经被这条误导过一次。）

**【为什么问】** 这条现在是**硬门禁**：我方判断"能不能上板点火"的唯一依据是 `BOOT.bin` 的 MD5 白名单。10-13～10-14 之间板子上出现过多颗我方无法判定身份的位流；**10-14 15:10 UTC 又被换成一颗 7,023,552 B、MD5 `c69904af9d52b9e0fff63213deb4965e` 的件，用我方唯一验过的窗口比对法对 `ai7030_top.bit`（含 NPU 那份，MD5 `b1cf2f22…`）是 0/21 命中（A 级）⇒ 无法证明含 NPU，Qwen3 上板只能停在点火前**。判错一次的代价是整机楔死＋需要人手动断电。**这颗件已辨认（2026-11-03，A）：它就是厂商 `BIT.rar` 里 `30tai_detpost/BOOT.bin` 的原件**（本地三份副本同 md5），里面包的是同目录那份 `ai7030_top_disable_icap.bit`（`a942d387…`，5,980,609 B），按各自同步字对齐后逐字 **100% 相同**——**所以"对 `ai7030_top.bit` 0/21 命中"只说明它不是厂商基线那颗，不能当成"它没有 NPU"的证据**；`30tai_detpost` 这套参考实现到底含不含 AIU，仍是没答的问题（要问厂商的就是这一条）。逐字比对读数、阳性对照（`aca4612b…`×`b1cf2f22…` 187/187 全中）、本地副本位置在 [[板端我方代码与产物台账]] §十八末条；方法来历与「读 `BOOT.bin` 头字段解不出设计名、只能改逐窗口比对」那处更正见 [[板卡镜像实测取证]]。

**【要的答复形态】** 一张"出厂 BOOT.bin 与其内部 PL 设计的对应表"（名称＋长度＋偏移＋校验值），加一句"不含 NPU 时访问 GP 窗口的行为"。

## 九、TTS／声码器：`Mul` 广播在文档承诺下失败 ＋ `Cos`/`Sin` 量化参数未实现

**【问什么，可直接发出】**

> 我们在悟净（30TAI/ZG330，`--target zhuge`）上把 sherpa-onnx 生态的中文 TTS 模型编进 NPU，遇到两个问题，都能复现：
>
> ① **`Multiply` 广播失败，但你们的文档说支持广播**。`docs/ops/spec/Multiply.html` 原文写"检查：两个输入必须是可广播的"、"输出推导：Shape 重设为两个输入特征图广播后的形状"。可我们的 matcha 声学模型（`matcha-icefall-zh-baker`）在 `/encoder/prenet/Mul` 报
> `Op (Mul) [ShapeInferenceError] Incompatible dimensions`。
> 两个输入的实际形状我们已用 onnxruntime 实跑取到（A 级）：`A = [1, 192, 20]`、`B = [1, 1, 20]`。按标准广播规则 `192 vs 1` 可扩、`20 vs 20` 相等，**数学上完全可广播**。
> 请教：ZG330 的 `Multiply` 广播**实际支持的边界是什么**？是只支持"除 batch 外全维相同"，还是支持 `[1,192,L] × [1,1,L]` 这种在**中间维**上扩的形式？如果支持，我们这份图的哪一步不符合你们的要求？
>
> ② **`Cos`/`Sin` 量化参数未实现 —— 我们查了文档，口径确实是空的，所以按"当前就是不支持"处理，不作为索取项**。我们的 vocos 声码器（`vocos-22khz-univ`）五段全过（`rc=0`，产出 `_ZG.json` 878 KB ＋ `.raw` 19.2 MB），但 quantize 段出四条告警：
> `icraft::xir::CosNode SetQuantizedScale Not Implemented! Using Default Implementation!`
> `icraft::xir::SinNode SetQuantizedScale Not Implemented! Using Default Implementation!`
> `icraft::xir::CosNode ZhugeQuantParams Not Implemented! Using Default Implementation!`
> `icraft::xir::SinNode ZhugeQuantParams Not Implemented! Using Default Implementation!`
> 这里只留一条**通知请求**：若后续实现了，请给个更新通知；**不作为本次索取项**。
>
> ③ **核心一问：不支持的算子留在图上到底怎么处理**。`RandomNormalLike` 与 `Range` 你们的预检明确写 `Icraft do not support`，而 `Unsupport.html` 写明该占位算子**「该算子无前向」**。我们据此推断：预检不过的模型**不是"回落到 CPU"，而是把空洞留在图上**。实测印证——`rc=71` 的 matcha 一进 `icraft-optimize` 就报
> `Check failed: (-(int64_t)size() <= index && index < (int64_t)size()) is false / Index 0 out of bounds 0`
> 上层消息 `Unable to match pattern with Op, Op_id is 3, Op_type is icraft::xir::AddNode`。
> 请教：**如果模型里必须有不支持的算子，贵方推荐的处理方式是什么**——自己改图避开？整链走 CPU？还是有别的官方姿势？我们对 `Range`（动态长度序列 `Range(0, N, 1)`，`N` 随输入文本长度变化）尤其想要官方替代形态；`RandomNormalLike` 我们可用确定性采样（噪声置零）绕开。

**【为什么问】** 三个问题都有 A 级可复现证据，且互相咬合：

- **问题 ① 的复现链**：`matcha-icefall-zh-baker` 的 `model-steps-3.onnx`（75.6 MB，4802 节点）。原图直接 parse 会因 opset/输入维度等前置门失败；做完"输入 4D 适配＋opset 11/IR 8＋剥 `Reshape.allowzero`"后到达 `rc=71`（**解析走完、预检 2 条、产物落盘**）；此时 `Range` 被标 unsupport、形状**被跳过**，所以 `Mul` 从不做广播检查。一旦把 `Range` 换成可求值的常量表 `Slice`，形状有了具体值，`Mul` **第一次做真实广播检查**并失败 ⇒ `rc=76`、无产物。我试过三种绕法（`Expand` 显式展开、`Tile(repeats=[1,192,1])` 常量复制、`Shape+Expand+Mul`），**全部失败**，`Tile` 甚至仍报同一个 `Incompatible dimensions` —— 说明它没走到广播逻辑、直接比形状。详见 [[TTS同量级候选进NPU横评]] §6.2。
- **问题 ② 的读数**：`vocos-22khz-univ` 的 parse→optimize→quantize→adapt→generate **五段 `rc=0`**（体积 53.8→13.5→15.4 MB，最终 `_ZG` 件 878 KB＋19.2 MB），是本轮唯一走完全链的 TTS 件。但四条 `Cos`/`Sin` 告警说明**相位分支量化是空白区**，我们的 int8 件相位精度没有任何官方保证。
- **问题 ③ 的对照**：`Range`/`RandomNormalLike` 的替代顺序被实测证明**必须排在 ① 之后**，顺序反了会白干。

**为什么这条影响我们的主线**：我方作品链是"能听、会看、会认证、善问答"，TTS 是"能听"的输出端。30TAI 板上 993 MB 内存／4×A53，**TTS 全走 CPU 时 RTF 1.40–1.62（matcha＋vocos，A 级）**，占满 CPU 会影响 ASR 与业务逻辑；把声码器下沉到 NPU 是唯一能腾出 CPU 的路。现在声码器能编、但声学模型卡在 ①，CPU 省不下来。

**【要的答复形态】** ① 一句明确的 `Multiply` 广播边界口径（最好附一份能过/不能过的形状对照表，或直接给我们一份 ZG330 上"广播可用"的最小复现工程）；② `Cos`/`Sin` 量化参数的实现计划或精度损失量级说明；③ `Range` 的官方替代形态。文件优先，口头解释也接受，但①必须能让我们**改图改到过**。
