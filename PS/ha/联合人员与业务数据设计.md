# 联合人员与业务数据设计

## 数据归属总表

本页是目标数据契约正本，状态见 [[HA4FPAI与视频联合总规划#规划范围与状态|HA4FPAI与视频联合总规划——规划范围与状态]]。两库均为本机 SQLite；业务主库统一写入口，特征历史库单独 writer。跨网络通过 API 访问，禁止把 WAL 数据库放到 SMB／NFS 上供两机并写。

| 数据 | 权威归属 | 规则 |
|---|---|---|
| 人员、身份映射与登记状态 | 业务库 | 稳定 person_id；姓名可改、可重名 |
| 登记人脸和声纹模板 | 业务库专表 | BLOB＋样本 ID＋模型／算法／预处理版本＋原媒体引用 |
| 设备、实体、区域和能力 | 业务库 | klar 注册 JSON 是投影；启动地址默认来自 YAML，设备绑定修改经受控配置接口 |
| 可在界面修改的业务设置 | 业务库 | 类型化值、期望版本、生效版本与变更记录 |
| 指令、识别、登记、录像与修改事件 | 业务库 | 事件 ID、请求关联、来源序号、时间及精简结果 |
| 持久任务和计划 | 业务库 | 定义、时区、到期策略、尝试、状态与结果 |
| 历史检测特征、框与质量 | 独立历史库 | 复用现有历史模型，独立容量、保留期和降载规则 |
| 照片、录像、录音的业务目录 | 业务库 | 文件位置、哈希或完成后校验、大小、状态、关联事件与录像 ID |
| 媒体与模型本体 | 文件系统 | 不把视频、原始音频或模型放入数据库 BLOB；逐帧索引可保留侧车 |
| 实时帧、音频队列、硬件 busy | 内存／共享内存／FIFO | 重启重建，不持久化每帧运行状态 |
| 诊断日志与栈 | journald／轮转日志 | 总量封顶；业务审计事件与排错日志分离 |
| 启动、硬件和程序默认值 | YAML／模型描述文件 | 管理员维护；凭据由环境或受保护文件引用，不入业务 JSON 导出 |

“JSON 为导出”仅针对可变业务资料。模型包里的 models.json、设备协议 manifest、媒体侧车和发布哈希清单仍是各自契约的一部分，不为统一后缀而迁库。

## 统一身份与模板契约

### 人员与外部编号

新人员 ID 用不含姓名语义的 UUID；已有合法、无冲突的视频 person_id 优先原样保留。人员显示名不是唯一约束；新增登记必须选已有 person_id 或显式创建新人员，禁止仅凭同名自动追加。

`external_identity_map` 记录 namespace、source_store_id、旧人员 key、新 person_id 和映射状态。旧 key 可以是视频 UUID，也可以是旧声纹库名称。迁移时自动提出同名候选，人工明确关联后才允许跨模态融合；不确定的保留独立待关联身份。合并须事务内重挂关系、保留别名／旧 ID 映射和审计，不能用全库字符串替换。

识别后端返回结构化 person_id 与展示名。旧 Gallery 以姓名为模板 key，必须一并修改模板加载及结果回填接口；数据库里添一列 ID 而比对仍以姓名索引不算完成。

人员与操作账户分离：`person_id` 表示被登记的人，`principal_id` 表示发起操作的账户／设备主体。识别结果不是登录会话或管理员授权。

### 模板与样本

登记模板至少带：template_id、sample_id、person_id、modality、model_id、model_sha256、pipeline_id、预处理版本、维度、dtype、字节序、归一化方法、BLOB、BLOB 哈希、质量结果、登记时间、source_media_id 和状态。

- 人脸与声纹使用独立表，不能混用维度或阈值。模板是否有限值、维度是否匹配、归一化是否成立由对应后端验证，资料服务再按模型注册契约检查后提交。
- 默认候选编码为显式 little-endian IEEE754 FP32。旧 JSON 人脸特征经 float64 路径验证，不能默认转 FP32 就保持原判定；迁移时做向量、聚合模板和临界分数对照。不满足等价门槛时先以显式 FP64 BLOB 无损保留，禁止悄悄重新归一化。FP32 下 512 维是 2048 字节，FP64 是 4096 字节。
- 人员多样本与聚合中心分开；中心是可重建派生物，记录输入样本版本和聚合算法，不能把新旧模型向量平均。
- 原图是否只保留每人一份沿用实际旧策略；没有原图的旧样本标记 `source_media_id=null` 和原因，不伪造多份原图。原音频缺失亦如实保留。
- 模型标识必须保存内容哈希、precision 和预处理语义。旧 pipeline 依赖 models.json 原始字节 SHA256，变更 JSON 排版就可能改变标识；保留原始 manifest 指纹与 legacy_pipeline_id，显式声明兼容映射。不能仅凭同维度或模型同名互换模板。
- 模型更新建立新模板版本并验证后切 active。旧模型只兼容旧模板；无法重提特征的样本保持不可用于新模型，不能自动重写成“已升级”。

### 融合验证与删除

`verification_session` 对应一次验证目的，收集人脸、声纹和 PAD 独立证据。放行条件必须包含相同 person_id、相同 session、允许时间窗、有效帧、同一声段归属及有效模型。人脸 A＋声纹 B 必须失败。多人场景不能用“任一人脸成功”拼上“任一声音成功”。PAD 未标定时只提供模型结果，不产生安全授权。

删除人员先撤销 active 模板并增加 revision，后端收到新快照或失效通知后 ACK。离线缓存不能继续用已删人员授权；确认删除应带模板生效版本。用于授权的每次最终决定须在线核验控制服务当前 restore_epoch、撤销／模板 revision 和证据关联；无法证明当前有效即拒绝授权。仅靠异步通知或无限期缓存不能满足这一要求。旧模板可供在途普通识别完成并注明版本，但不能据此放行。删除接口分别报告数据库已撤销与消费者 pending／blocked，不把未同步显示成全部生效；普通预览、识别展示和在线语音可继续。

媒体物理删除由文件生命周期处理，普通事件保留 ID／墓碑，显示信息按保留策略脱敏；法定或用户明确要求的彻底删除需覆盖历史特征、导出、备份保留政策，不能宣称删主表即全量抹除。

## 业务库逻辑表

下表是第一版逻辑 schema 合同；实施时用版本化 DDL 与迁移脚本实现，不以本页代替可执行建库文件。JSON 文本可作为有界的扩展字段存入 SQLite，不构成第二主存储；关键关系和可查询状态必须有正式列。

| 表或表组 | 主要字段与约束 |
|---|---|
| schema_migrations、store_meta | schema_version、迁移校验值、store_id、generation、restore_epoch、数据格式版本、写入协议版本；未知新版本拒绝写入 |
| persons、external_identity_map | person_id PK、display_name、status、revision、created/updated；映射唯一键为 namespace＋source_store_id＋legacy_key |
| models、pipelines | 模型哈希、runtime／precision、预处理版本、manifest 原始哈希、legacy 标识与兼容结论 |
| face_samples、voice_samples | sample_id PK、person_id FK、模板 BLOB 契约、source_media_id、quality、active；索引 person_id＋model_id＋active |
| template_sets、template_members | 不可变模板集合版本、组成样本、聚合哈希、validation_status；按 modality/model 维护当前生效集合 |
| areas、devices、entities、capabilities | 区域、设备、实体标识及关系，稳定 entity_id 和能力版本；自有命名与 klar 导出映射分离 |
| settings、settings_changes | scope＋key 唯一、类型／值、revision、desired_revision、applied_revision、错误和生效方式；变更审计同事务提交 |
| principals、sessions、pending_confirmations | 操作主体、权限范围、到期会话；确认绑定动作摘要、请求参数、主体、设备和失效时间；不存明文凭据 |
| commands、command_attempts | request_id、幂等键、参数摘要、动作、目标、状态、deadline、执行回执；幂等唯一键限定在发起主体与目标范围 |
| events、event_links | event_id、producer_id、producer_seq、类型、请求／会话／人员／设备／媒体／录像关联和时间；producer_id＋seq 唯一去重 |
| verification_sessions、verification_evidence | 同一验证会话、模态、person_id、证据来源、有效期、模型、帧／声段标识与原始判定 |
| media_assets、recordings、media_operations | media_id、storage_root_id、相对路径、大小、状态、录像旧 ID、时间范围、回收站、操作日志及配额归属 |
| tasks、task_attempts | 计划／时区／missed_policy、触发序号、lease、状态、尝试、action_ref、结果；task_id＋occurrence_key 唯一 |
| exports、outbox、consumer_offsets | 导出 kind/revision/schema/hash；待投递域操作、重试、已确认游标，支持断线补偿 |

SQLite 连接逐个启用 `foreign_keys=ON`。为时间、人员、设备、命令状态、待执行到期任务和待投递 outbox 建索引。列表接口分页并限制上限，库内不做无界扫描或读取所有 BLOB。

## 设置的期望值与实际生效

启动加载顺序：**程序／YAML 默认 → SQLite 显式用户覆盖 → 内存中的已应用配置**。接口同时报告值的来源与版本。安装时环境变量仅用于启动地址、凭据来源等管理项；同一可变业务键不能再由环境变量悄悄覆盖。

| 设置类别 | 保存与应用方式 |
|---|---|
| 音量、界面主题、允许的声音档 | 业务库；可热更新的给出 applied ACK |
| 声纹／人脸阈值 | 业务库，按模型／策略版本作用域；修改不能自动标记安全标定完成 |
| 录像模式、配额、保留策略 | 业务库记录 desired；recorder 校验并应用后回报 applied，停机时按版本恢复 |
| 模型路径、设备寄存器、挂载 UUID、服务监听、日志上限 | 启动配置，管理级变更；不作为普通网页自由编辑项 |
| API 密钥、Cookie、SSH 及数据库访问凭据 | 安全文件／环境／系统凭据库引用；响应与导出不含值 |

UI 更新使用预期 revision，冲突返回 409；多键提交先整体校验再事务提交，不允许保存一半。配置元数据声明类型、范围、依赖、敏感性和 `hot / restart / startup_only`。重载失败保留旧 applied 版本并显示失败原因，不能把“写入成功”显示成“已生效”。

应用命令按 scope＋restore_epoch＋revision 排序并做持久 fencing。消费者拒绝低于已接受版本的应用，重复同版本须校验参数摘要；主库忽略旧 ACK 对当前 applied 的覆盖，并把被新版本替代的待执行项标 superseded。若期望13=manual、14=off，13的迟到重试不得重新开启录像。新世代先完成恢复握手，不仅凭数字更大就信任任意命令。模板快照和导出 current 指针也只能前进，禁止异步旧作业覆盖新版本；无法实现下游版本检查的旧接口须经设备侧串行适配器核对并停止旧尝试，不能仅在电脑端加幂等键。

ggradio 的业务设置写回改用设置 API；YAML 原注释与默认值继续保留。开发者需要实验覆盖时使用隔离实验 profile，不污染现役设置。新包升级不能用默认配置覆盖已有数据库用户设置。

## JSON投影与缓存

数据库提交递增 domain revision，并在同事务创建导出 outbox。导出器生成不可变版本目录，再原子切换 current 指针；manifest 含 store_id、source_revision、export_schema、pipeline_id、文件哈希和生成时间。数据库已提交但导出失败显示 `export_pending`，重试导出，不回写旧 JSON。

klar 原生注册文件如不接受额外字段，保持原生格式，版本信息放伴随 manifest。实体、区域和设备映射从一个数据库快照导出，保持稳定 entity_id。人脸旧格式需要姓名 key 时必须通过显式映射转换，禁止重名覆盖；在完成 person_id 模板接口前不能启用重名登记。

后端缓存按 `store_id＋revision＋model_id` 取不可变模板快照，完成校验后原子切换，旧请求保留旧版本并在结果标明。数据库暂不可用时可按既定策略继续展示缓存状态，但拒绝资料修改和依赖已撤销身份的授权。缓存与导出不能反向成为资料写入口。

## 时间与跨库关联

事件公共 envelope 包含 event_id、request_id、session_id、person_id（未知可空）、device_id、recording_id、media_id、boot_id、producer_id、producer_seq、UTC wall_time、monotonic_ns、time_quality、frame_id／frame_token、模型／pipeline 和所用模板 revision。

producer_id 明确定义为生产者实例 UUID：设备 ID＋boot_id＋进程启动随机世代可共同溯源；稳定组件名另用 component_id。每个实例内 producer_seq 递增，进程重启产生新 producer_id；已持久化待重发事件保留原实例 ID、序号和 event_id，不能重新编号后重复入库。

单调时钟只能在同一设备同一 boot 内比较；跨主机用各自 wall_time、同步质量和接收时间建立带不确定度的关联，不把电脑与板子的 monotonic 相减。墙钟回拨或 NTP 校时不能改变事件唯一性；同一 producer 实例内按 producer_seq 排序，不同实例结合采集时间与接收顺序展示。

历史库保存同一 event_id／frame 标识和可选 person_id，不对另一个 SQLite 文件建立伪外键。入库先后不同是可恢复状态：业务事件可标历史特征 pending／dropped，后台按 event_id 对账。历史检测永不自动升级为登记身份；登记须显式选择和质量审核。

## SQLite运行与保留策略

- 两库分别 WAL，连接配置 bounded busy_timeout，短事务。业务库优先 `synchronous=FULL`，历史库的持久级别由历史可丢策略明确配置和断电测试决定；不把 WAL 等同不会丢数据。
- 每库单 writer，有界请求／历史队列；SQLITE_BUSY、磁盘满、只读均返回明确状态。历史过载可采样或丢弃并累计计数，资料修改与关键命令不能静默丢弃。
- 业务数据库、WAL、导出和备份同样计入磁盘预算；历史库有独立字节／条数／时间限额。先限高频历史，再限制非关键事件，保留恢复所需空间。
- 控制页低频读快照，特征只在模板版本变化时加载；不在每帧识别前读数据库。读事务不能长期持有阻塞 checkpoint；checkpoint 在后台有界进行，VACUUM 仅维护窗口且先验证可用空间。
- 支持的 SQLite 版本、WAL／外键、线程连接纪律和所用 SQL 在目标 Python 3.8 环境实测；不依赖未探测的 JSON1、STRICT 或 RETURNING。

容量、写入吞吐和长稳判据见 [[联合实施路线与验收#联合验收矩阵|联合实施路线与验收——联合验收矩阵]]；崩溃一致性和备份见 [[联合存储迁移与恢复方案#文件与数据库的一致性|联合存储迁移与恢复方案——文件与数据库的一致性]]。
