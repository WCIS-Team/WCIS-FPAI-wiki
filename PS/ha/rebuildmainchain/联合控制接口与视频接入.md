# 联合控制接口与视频接入

## 统一执行路径

本页定义目标应用协议，**拟议 `/v1/` 路径尚未实现**。现有接口保持清楚的版本适配，不能把此处示例当作已可调用。存储契约见 [[联合人员与业务数据设计#业务库逻辑表|联合人员与业务数据设计——业务库逻辑表]]，进程职责见 [[HA4FPAI与视频联合总规划#模块与写入所有权|HA4FPAI与视频联合总规划——模块与写入所有权]]。

统一入口走：输入 → 标准化 → 意图／动作提案 → 参数与权限校验 → 必要确认 → 持久命令 → 域执行 → 状态核对 → 事件与反馈。按钮直接产生动作提案，语音与文本先解析成同一结构。ggradio 逐段实验继续存在，但“执行设备动作”只能调用同一入口。

klar 适配器处理官方 V2 的 decision、clarify／confirm／reject、plan 与 slots；独立 executor 和语言 router 共用适配结果。多轮会话传递稳定 conversation_id；原引擎拒绝不得因自动降级而绕过。自有设备短语作为明确命名的受控规则，同样经过确认与权限检查，不能让“direct 优先”越过策略。

普通闲聊进入 LLM；设备意图不明确、解析失败或执行超时返回澄清／错误，不能回落 LLM 后把生成文字冒充执行回执。设备动作完成后，可以润色回复，但成功与否以结构化回执为准。

## 动作目录与请求合同

动作目录由单一注册表生成后端检查、前端按钮说明、语音映射和能力清单。设备／实体源来自业务库，动作实现留在程序；数据库记录不能注入任意 Python、shell 或 URL。

| action | 参数 | 执行者与完成证据 |
|---|---|---|
| camera.open_view | device_id、client_id | UI 导航；需要客户端确认收到新鲜媒体，服务端生成地址不等于已播放 |
| camera.recognize | device_id、可选明确验证会话 | 视频 owner；本次 frame_token、模型／模板 revision 和结果 |
| camera.snapshot | device_id | 视频媒体接口＋持久文件流程；media_id 和已提交文件状态 |
| recording.set_mode | device_id、off/auto/manual | recorder；模式回读，区分 armed／actively_recording |
| recording.list / play | 时间范围、分页或 recording_id | 目录＋媒体读取；回放地址／权限，不必通过 LLM |
| recording.trash / restore / purge | recording_id、确认令牌 | recorder 保留回收站／清理规则；purge 不接受“全部”隐式展开 |
| person.create / update / merge | 资料及 expected_revision | 资料模块；新 revision、审计事件 |
| person.enroll_face / enroll_voice | person_id、media_id、模型版本 | 提取后端提交提案，资料模块原子登记；不按姓名自行建人 |
| settings.update | 多键变更、expected_revision | 设置模块；desired 与 applied 分别反馈 |
| system.status | 设备／能力范围 | 聚合状态，独立报告语音、视频、存储和版本 |

重启等现有管理动作沿此框架整治，默认不放进普通语音快捷动作；不得在电脑执行板端命令。真实门锁另需已验的验证与执行器，本规划不把 camera.recognize 直接映射为开锁。

拟议请求：

```json
{
  "request_id": "uuid",
  "idempotency_key": "client-generated-key",
  "session_id": "conversation-uuid",
  "client_id": "browser-session-uuid",
  "action": "recording.set_mode",
  "target": {"device_id": "board-camera-uuid"},
  "params": {"mode": "manual"},
  "expected_revision": 12
}
```

principal_id 由已认证会话派生，不接受请求体自报。幂等键连同主体、目标、动作及规范参数摘要检查；相同键不同参数返回冲突。媒体使用 media_id／上传接口，不把客户端任意路径交给板端打开。

拟议响应：

```json
{
  "request_id": "uuid",
  "command_id": "uuid",
  "status": "succeeded",
  "code": "mode_applied",
  "message": "已切换为持续录制模式",
  "desired_revision": 13,
  "applied_revision": 13,
  "data": {"mode": "manual", "actively_recording": false},
  "event_id": "uuid"
}
```

`manual` 已应用但尚无新鲜帧时，反馈“已设为持续录制，等待画面”，不能播报“正在录制”。

## 命令、任务与重试

命令状态为 proposed → awaiting_confirmation／accepted → running → succeeded／failed／cancelled／unknown。HTTP 202 只表示 accepted；即时完成可回 200。状态码区分参数错误、401／403、409、429、503，传输成功不等于动作成功。

`unknown` 表示无法确定下游是否执行，先查询下游回执与状态，不能盲目再次执行。领域操作携带 operation_id；幂等控制只保证业务接口重复请求可识别，无法让不支持该协议的硬件动作自动获得“恰好一次”语义。

持久任务用 tasks＋attempts 保存到期时间、IANA 时区、missed_policy、lease_until、触发序号和动作引用；同一 occurrence 唯一。系统重启后先核对未完成尝试，再按“跳过／只补最近一次／需确认”策略处理。仅只读或明确幂等动作可有界自动重试，删除／重启／物理执行在状态未知时停止并请求处理。任务 worker 与直接动作共用执行合同，不另造自动化执行器。

命令、worker 租约和域回执带 store generation／restore_epoch 的 fencing 标识。旧备份恢复后默认冻结执行，不能把旧库 pending 当成从未执行；旧世代 worker 不得领新任务，过期确认不得沿用。具体恢复步骤见 [[联合存储迁移与恢复方案#备份与灾后恢复|联合存储迁移与恢复方案——备份与灾后恢复]]。

否定、引用、询问、复合句与含糊指代必须覆盖：例如“不要开始录制”“怎么开始录制”“取消重启”不能被子串规则截成开启或重启。多个动作逐步记录结果，失败时报告部分完成；不伪装跨设备事务，补偿只做明确安全的逆操作。

## 拟议服务API

| 路径 | 职责 |
|---|---|
| POST /v1/commands；GET /v1/commands/{id} | 创建与查询命令 |
| POST /v1/interpret | 只解释文字并返回提案／澄清，不执行 |
| POST /v1/confirmations/{id} | 绑定主体和参数摘要确认，过期或参数变化失效 |
| GET /v1/capabilities；GET /v1/status | 版本／schema／能力与实际健康 |
| /v1/persons；/v1/persons/{id}/enrollments | 人员与跨模态登记；写请求使用 POST/PATCH/DELETE |
| GET/PATCH /v1/settings | 类型化设置及 revision 比较 |
| POST /v1/uploads；GET /v1/media/{id} | 有界上传与授权媒体读取；限制类型、大小、时长和路径 |
| GET /v1/events?after={cursor} | 分页事件补读，返回游标；后续可加 SSE |
| /v1/tasks | 持久任务、取消和结果查询 |

第一版不要求消息中间件、WebSocket 或开放任意代理。控制服务提供固定服务映射与白名单域动作，禁止通过设备地址字段访问任意主机／文件。

## 视频域适配与媒体

实施时对照视频交付快照与实际服务核对协议；既有接口目录见 [视频 API](../../repos/FPAI30TAI图像FPGA/docs/api-index.md#L15)，交付端口说明见 [submission](../../repos/FPAI30TAI图像FPGA/yuanma/submission/README.md#L60)。下表只规定接法，不复制底层全部路由。

| 能力 | 接法与保留边界 |
|---|---|
| 预览 | 复用现有 H.264 manifest、init 与分片；编码为 H.264 时不退回不断请求已返回 410 的 MJPEG |
| 单帧识别 | 调既有摄像头识别入口，传回 frame_id/token、采集及交付年龄、PAD 和模型结果；禁止复用过期结果授权 |
| 拍照 | 按可用 codec 的合法快照入口读取；无 JPEG 能力时明确不可用，不能把 H.264 哨兵当图片 |
| 录像 | recorder 保留封段、预缓冲、配额、回收站和 remux；HA 只请求模式与列表等域动作 |
| 回放／下载 | 复用 MP4 Range、Content-Type、长度与权限；元数据控制超时不能截断正常媒体读取 |
| NPU 与摄像头 | 仍由单 owner 管；不为按钮、语言链或 HMI 新开 SDK／采集实例 |

第一版保留 iframe，让原视频页面在自己的 origin 操作。统一按钮通过控制服务适配器调用视频服务；保留录像 API 的同源控制检查，不用全局 CORS `*` 解决跨端口。

媒体可直接访问配置的视频 origin；若外网／HTTPS／统一权限需要代理，只做固定前缀的媒体代理，支持 Range、流式传输与背压，不把整段视频读进内存。代理相对路径重写与 `Host/Origin` 仅针对已认证、白名单动作，不作为绕过鉴权的通用工具。相机编码和 H.264 会话切换时，播放器必须按新 session 重建缓冲。

## 界面与语音闭环

控制台先增加统一设备配置和能力状态，消除电脑 localhost 与板端 localhost 混淆。页面中的“服务在线”“画面新鲜”“模式已设”“实际录制”“资料已同步”分别显示。

第二步把直播、识别结果、快照和近期录像集中到视频工作台；完整图库、压缩与配额高级页面可继续复用原页。网页和原生 HMI 复用动作及资料 API，但保留各自显示后端；原生 HDMI 不因网页播放器通过就自动验收。

首批语音场景是“看看是谁”“拍张照片”“开始录制”“有人时再录”“停止录制”“查看今天的录像”。每次反馈来自实际结构化结果。视频故障时仍可转写和展示错误；TTS 故障不回滚已成功录像，响应分别标 `action_status` 与 `speech_status`。

UI 导航消息只发给原 client_id。板载麦克风的显示目标是明确配置的 HMI 会话；纯 API 调用不宣称用户已经看见画面。“播放刚才那段”只在当前会话保存了有效 recording_id 时执行，多个候选先澄清；人员资料与语音对话 session 分开。

## 安全与事件反馈

现有控制台 GET /api/run 可执行动作，声纹库也有 GET 删除路径；整改为 GET 只读，副作用走 POST/PATCH/DELETE，并覆盖旧兼容入口，不能只保护新路径。依据：[控制台 handler](../../repos/HA4FPAI/boards/console.py#L637)、[声纹 handler](../../repos/HA4FPAI/lang/server/app.py#L216)。

控制服务默认绑定回环或明确管理网段，远程入口采用服务端会话与 CSRF 防护、精确 Origin 校验及权限范围；鉴权信息由服务端持有，不写 iframe URL 或前端脚本。视频直连管理端口也必须收敛可达面或经过同等权限保护，否则会绕过控制层。不能把 klar 的语言安全决策当作整个系统的身份鉴权。

人脸／声纹登记删除、永久清理、重启和配置写入是管理操作。确认不是一次笼统 yes，而是短期绑定具体对象、参数、操作者和当前 revision。语音识别人名不自动认证操作者。

先实现有界状态轮询、动作完成立即刷新和带游标事件补读。后续 SSE 使用可恢复游标，慢客户端断开或跳过普通状态，但关键审计与命令回执须持久重放；同一事件不能因重连重复触发动作。统一编号与时间规则见 [[联合人员与业务数据设计#时间与跨库关联|联合人员与业务数据设计——时间与跨库关联]]。
