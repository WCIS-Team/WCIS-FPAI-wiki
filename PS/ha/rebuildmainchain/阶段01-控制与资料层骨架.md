## 问题与修复记录（本阶段真实踩到的）

| # | 现象 | 根因 | 修复 | 教训 |
|---|---|---|---|---|
| 1 | 破坏性到期任务静默不执行（测试 68/69 暴露） | `tasks.run_due` 在 `store.tx()` 内调用 `commands.create_confirmation`，后者自己 `BEGIN IMMEDIATE` → SQLite 嵌套事务报错，被 `except Exception: continue` 吞掉，伪装成"幂等跳过" | 确认创建移到事务外，attempts 行只记引用 | **`except Exception: continue` 会把程序错误伪装成幂等语义**；兜底跳过必须收窄到唯一约束冲突一类，或至少记日志计数 |
| 2 | 导出 fsync 报 `OSError: Bad file descriptor` | Windows 上对只读句柄 `os.fsync` 非法；目录 fsync 也不可用 | `_write_json` 内写时 fsync 已足够，删掉 replace 后的二次文件 fsync；目录 fsync 平台容忍（Linux 生效，Windows 跳过靠 replace 原子性） | 跨平台持久化协议的每一步 fsync 要分清"数据可见"与"目录项可见"；板端 Linux 与本机 Windows 行为不同，验收要两边都对 |
| 3 | 测试期望 `ForbiddenError` 实际抛 `ConfirmationRequired` | 两种 403 语义不同：缺确认＝`ConfirmationRequired`（引导去建确认），确认无效/过期/不匹配＝`ForbiddenError` | 修测试期望，并在 API 文档区分 | 错误码先分层再写测试，返工最少 |
| 4 | 测试对已 succeeded 的命令硬标 unknown 被拒 | `fail_unknown` 只允许非终态迁移（这是对的） | 测试改为手工造一条 accepted 态命令再迁移 | unknown 语义只属于"执行过但回执丢失"，不是万能后悔药 |

## 关键取舍（有其他选项的都记在这里）

| 选择点 | 备选 | 最终选择与理由 |
|---|---|---|
| 分支基点 | ① 共享树 HEAD ② 本地 master ③ origin/master | **③**：本地 master 落后 origin/master 5 笔，①还会带进共享树 83 个未提交改动（归属其他会话，不能吞）。隔离 worktree 从 origin/master 开，不合入。 |
| 重构策略 | ① 就地改现役文件 ② 纯新增模块＋契约铺垫 | **②**：现役文件正被其他会话改（十级链），就地改必冲突；骨架先落地，接线（WP2/4/9）在分支上分步做。 |
| 视频域 | ① 搬 yuanma 源码 ② HTTP 客户端适配器 ③ 留空 | **③（本阶段）→②（阶段02 起）**：她先令留空并登记接法（V1–V10）；后续按清单以 HTTP 客户端实现，仍不搬源码、不复制推理代码。 |
| 同版本回执语义 | ① 同版本也标 superseded ② 同版本幂等接受 | **②**：规划口径是"拒绝低于已接受版本"，严格旧版本才 superseded；同版本重放不改变任何状态，幂等接受。 |
| 事件 producer 唯一性 | ① 组件名＋全局自增 ② 实例 UUID＋实例内自增 | **②**：重启归零会撞号；实例 UUID 每次启动新生成，(producer_id, seq) 天然唯一，重启可溯源。 |
| wiki 推送方式 | ① 共享树直接 add/commit/push ② 临时工作树从 origin/main 起 | **②**：共享树 wiki 有大量其他会话未提交改动，直接 add 会吞别人的行（2026-11-02、11-01 两次事故形状）；按 AGENTS §七临时工作树流程做。 |
