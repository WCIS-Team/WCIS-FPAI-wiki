# 09-裁剪后设计总览

综合 wiki 记录与源码实测，对「裁剪后的 ha-small」做一次整体设计梳理。逐步骤的证据与规程见 01~08 各页；本页只做**总览与取舍判断**（判据以各页为准，不复制其表格）。

## 一、裁剪哲学

- **不是 fork，是子集**：从官方 Home Assistant Core **2026.10.4** 的 sdist（sha256 `8410fecb…`）出发，**只删不改**
- **逐字节可验**：保留的 5630 个文件全部有 SHA256 审计（`cut/source-audit.json`），`modified_upstream_files = 0`
- **零补丁**：删到依赖闭包固定点为止，绝不打补丁改造（因此也免除了 Apache-2.0 §4(b) 的变更标注义务，见 [[08-许可与合规]]）
- **安全取向**：减少集成数 = 减少攻击面与审计面；**裁剪从不为省磁盘/内存**（见下 §五）

## 二、架构对比

```
Home Assistant Core 2026.10.4 : 128 integrations
        │  删除 11 个叶子（无任何依赖方）
        ▼
ha-small v0.1.0              : 118 integrations（6096→5630 上游文件）
```

**删掉的 11 个叶子**：`ai_task, air_quality, calendar, geo_location, local_file, radio_frequency, schedule, switch_as_x, todo, command_line, shell_command`

**保留的核心支柱**（被其他集成引用 / 提供已验收功能）：
`generic`（摄像头/RTSP/HLS）、`mqtt`、`rest`、`rest_command`、`counter`、`wyoming`（TTS）

三条裁剪规则与收敛过程见 [[02-依赖闭包与三轮试删教训]]。

## 四、交付三件套

`源码包 6.85MB` · `wheel 8.28MB` · `deb 7.37MB`（构建细节与坑见 [[04-打包与交付]]）。
Actions 手动触发工作流 `release-ha-small.yml` 在 ha-small 分支根，无 CI 自动化。

## 五、关键取舍：裁剪省的是什么，不省什么

**这是本项目最需要说清的设计判断**（实测见 [[07-运行时内存RSS实测]]）：

| 维度 | 裁剪前→后 | 结论 |
|---|---|---|
| **攻击面 / 集成数** | 128 → 118 | ✅ 真收益：少 11 个入口、少 11 份待审代码 |
| **静态代码 / 认知负担** | 6096 → 5630 文件 | ✅ 真收益：待读代码少 ~8% |
| **磁盘（venv）** | ~759 MB → ~759 MB | ❌ 几乎不变：大头是 hass_frontend 269MB + av 127MB + numpy 60MB，与集成数无关 |
| **运行时 RSS** | 253.3 MB → 253.3 MB | ❌ 不变：删的叶子本就不在 config、从不 import，RSS 贡献≈0 |

**机制**：运行时内存是「**加载了什么**」（configuration.yaml 决定）的函数，不是「**盘上有什么**」（代码树）的函数。删死代码省磁盘与攻击面，不省 RSS。想省 RSS 要关功能（config 层）；想省磁盘要动 wheel（依赖层）——两者都不在“删集成”这个杠杆上。

## 六、边界（必须与结论同读）

- **Python ≥3.14.2**：板端仅 3.8，装不了 → HA 跑本机/容器，板端只出流
- **摄像头源当前未就绪**：短录 `received_frames` 不增（SDI→PL→PS 链路无 H264 输出），guard 未触发真实写入
- **mTLS CA 30 天**：实验室证书，生产需替换
- **商标**：Apache-2.0 不授商标权，“Home Assistant” 属 Nabu Casa，对外只能用自命名 ha-small（见 [[08-许可与合规]]）
