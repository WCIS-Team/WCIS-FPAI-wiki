## 一、Qwen3 K128 重编译（KV depth 512→128）

**动机**：测得每步 KV DMA 112MB ≈ 0.93s（瓶颈），深度 128 后每步 28MB → 理论 3×提速。

**方法**：复现本仓现有编译链（pipeline.md §4~§4b）：
1. 复制 Q3V1_parse.toml 改 `max_tokens_length=128` → `Q3K128_full.toml`（隔离到 jr_path/Q3K128/不碰现役）。
2. parse → optimize → quantize → adapt → generate（五段 ~5min + mask0 patch）。
3. host_gen 单步校验 + 25 token 链 vs 校机 padfix-mask0 参考：逐 id 全等 **26/26**。
4. 板上 deploy：registry qwen3 defaults 加 json/raw/max_decode_length=128；生成测试 max_new=32 → 2.01 tok/s, 64 → 2.13 tok/s（原 0.93）。

**证据**：
- `workenv/migrate-real-preview/k128_step*.sh`（编译链脚本）、host_gen 25 链对比 `cmp_k128_ref.py`
- 板上验证脚本 `k128_board_test.sh`（推送到 board 的测试序列）
- 文档更新：Qwen3 README “K128 段”、pipeline.md §9（新增重编译步骤与三个坑：parse/toml 路径、generate 段也要 depth、jr_path 隔离必须做）
- 源码：lang/llm/models/Qwen3-0.6B/compile/（Q3K128 新 toml）、patch/q3_infer_board.py（init_device(device) 注入接口，见 resident 节）

**结论**：**2.13 tok/s（≈2.3×）**，语义质量不变（26/26 id 全等）。

## 二、npuserv resident 多模型常驻（设备独占规则修正）

**原误判**：“NPU session 设备级独占 → 不能并存”；**真相**（2026-11-08 裸测）：`openDevice()` **每进程只能调一次**，第二把 device 句柄会打坏第一把的 DMA。**解决方案**：worker 开一把 device，adapter 接收 device 注入（不再自己 openDevice），任意会话叠加于同一 device 均 OK。

**实施**：
- adapter_lib.run_resident() + resident_worker.py + bootstrap_zg330.py + server --resident (ResidentSupervisor class)
- adapter 改造：qwen3 init_device(device)/DecodeOnlySessionManager(device)；hifigan _apply(device)；ernie E41(device)
- resident 模式测试：qwen3+hifigan 交替 forward/generate 全绿（q3 2.06→2.54 tok/s、hf peak 1.0）；ERNIE 也加入 resident（apply 44s + 生成）。

**证据**：
- `workenv/migrate-real-preview/k128_shared_test.py`（裸测 shared device，证明 qwen3+hifigan 同 device 可共存）
- `workenv/migrate-real-preview/resident_order.sh`（resident 双负载顺序测试，board 日志 log/npu_resident.log）
- lang/npuserv/server.py（ResidentSupervisor + describe_model(id) fix）、adapter_lib.py（run_resident）、board/npuserv_adapter.py（_apply(device)、load(device)）
- docs/COEXISTENCE.md §一①重写（“设备独占”更正为 openDevice 单次规则）

**结论**：**三模型（qwen3-K128/hifigan-v2/ernie-4.5）resident 并存通过**，multi-resident 成为真实可用架构。

**结论**：**CORR 0.9996 PASS**；误诊修复 + 排布修正 = 可信数值基线。

## 九、CPU 预算线（两轮实测，第二次推翻第一次）

**第一轮（轻载）**：视频三服务+ASR 2 线程并发，每核 busy 12–17%、相机满帧 30fps、loadavg 0.27
→ 曾判“核不是瓶颈、不用分核”。

**第二轮（重载，复刻历史事故条件）**：ASR 4 线程满负荷 → rtf 2.18、相机 `frame_age_s` 从
0.46 漂到 **1.24s**、帧率掉约一半 ⇒ **跨进程 CPU 抢占真实存在**。历史依据：决策记录里
SenseVoice+VAD 4 线程自抢（rtf 1.161→0.8025）、10-21 多进程抢 `/dev/video0` 致 PS 无响应。

**分核实测（有效）**：视频进程钉 cpu0、ASR 钉 cpu2-3 后 → ASR rtf 1.89（反而更好）、
相机 age 回 0.24–0.38 满帧。

**压核实验**：视频钉 **1 核**即满帧（29.5fps，age 0.67）；叠加 ASR 4 线程压另 2 核时
仍 29.4fps、age 0.23 ⇒ **视频链 1 核够用**，分核方案 v2 = 视频 1 核 + CPU 件 3 核。

**四条预算线正本**：`repos/HA4FPAI/docs/COEXISTENCE.md` §一/§三/§五/§六
（NPU 会话=openDevice 单次规则、主存、**CMA=LLM apply 吃光池使相机死**、CPU）。

**副作用实测（供选型用）**：停 recording+vpu_live 两个面板服务 **CPU 增量≈0**（只省 ~40MB 内存）；
视频编码走 `h264_v4l2m2m`（硬件 V4L2 M2M），ffmpeg 只是 UYVY→硬件帧的搬运壳。

**合同测试**：把原先散在 `workenv` 的板端验证脚本收编为库内测试

无板环境全 skip 绿；新增 CI `board` 档（`ci/run.py --profile board`）。板端实测 **29/29 全绿**。

**视频传输协议（读码实证，板上现役）**：**不是 WebRTC/SRT**——实时预览＝
**HTTP 连续 fMP4 + 浏览器 MSE**（`/api/camera/h264/live.mp4?session=` → MediaSource
`appendBuffer`，播放端自带追帧：lag>0.9s 跳 seek、playbackRate 0.97–1.01、每 20s 清旧 buffer）；
回退路径是 `multipart/x-mixed-replace` MJPEG；快照单帧 HTTP；录像回放走 HTTP Range（206/416）。
无 WebSocket/EventSource/RTSP/RTMP。**CPU 面**：0 观众 vs 1 观众板端各进程 CPU 无差
（解码全在浏览器），是三种方案里最省的；代价是延迟 ~0.25–1s、单 viewer 槽位限流、明文 HTTP。

**VPU 硬编与 SDI 格式约束**：`wcis_camera_owner` 二进制内含 `Unsupported H264 raw format`
——VPU 的 H.264 硬编不吃 SDI 的 UYVY raw（JPEG 路径可用）。绕开需 UYVY→NV12 转换，
属视觉仓 PL 改造（`FPAI30TAI图像FPGA/scripts/build_face_board.tcl` 全流程 2–3 天 + 时序
重收敛风险），换约 0.3 核 —— 已判定暂不做，触发条件写在 `wiki/todo/todo.md`。
