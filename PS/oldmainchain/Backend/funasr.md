## 一、流程（按常驻循环重排）

原始规划的第 8、9 步缺号，这里连续编号；"启动即采集、采集不开关"是设计前提，写进步 1。

| 步 | 动作 | 备注 |
|---|---|---|
| 1 | 常驻程序启动，打开 ALSA 采集，持续读麦克风 | 采集从头到尾**不关**，VAD 的判决不门控录音，见第二节 |
| 2 | 48 kHz 输入 → 16 kHz 单声道 PCM | 录音流原生就是单声道（格式读数正本 [[音频#二、接口与端点（设备提供的全部空间）\|音频——二、接口与端点（设备提供的全部空间）]]），所以这一步**只有速率转换、没有下混**。做重采样的不是 VPU 而是 CPU，见第三节第 1 条 |
| 3 | 逐帧送当前选中的断句档持续检测 | 四档可切换（webrtc／fsmn／silero／firered），默认档与各自参数见第 4.1 节 |
| 4 | 静音累计到端点阈值 ⇒ 判定一句结束 | 端点值与现役链路同档，理由链接不重述 |
| 5 | 从环形缓冲切出该段 PCM，句缓存清零 | 段头按帧判决回扫，不是按音量 |
| 6 | 整段按协议外发 | 采样率写在请求头帧里，不用自己补 WAV 头；三帧契约见第 5.1 节 |
| 7 | 等远端返回纯文本字符串 | 超时与失败要记账，不能静默丢句 |
| 8 | 文本交给 TTS（`repos/lang/tts/ekho-linux`） | 接口是 `POST /tts`，正本 [[实时伪tts#三、流式 TTS 的组件设计\|实时伪tts——三、流式 TTS 的组件设计]]；**ekho 至今没上板** |
| 9 | 回到步 1，循环 | 进程不重起，冷启动只发生一次 |

明确**不做**的：不维护 ASR 隐状态、不分小块持续推送、不做流式识别、不在边缘端跑标点或 ITN。断句之后一次性发包。"不开长连接 websocket"这条按 D-78 读作**不许常驻连接**——一句一段的短连接（连—发—收—断）不在禁列，理由与代价写在第 5.2 节。

## 二、断句判据：什么时候开始收，静音怎么切

她提的那问是"VAD 检测到音量够大才开始录音，还是句子结束后对取出的缓存头切除静音"。**这个二选一本身有个错前提**，两半要分开答。

### 2.1 VAD 判的不是音量

WebRTC VAD 对每个语音帧输出**二值判决（语音／非语音）**，机制是帧内特征 ＋ 高斯混合模型的对数似然比，`aggressiveness 0~3` 调的是判决松紧，**不看绝对 dBFS**（**B**：这是算法层描述，落到所选那份移植的头文件与 API 上还没读，验收第一步就是读它）。模型档（silero／fsmn／firered）吐的是**每帧语音概率或三类判决**，要自己配阈值与平滑窗，但"**判的是语音性、不是能量**"这一条四档都一样，所以本节的结论不随档位变。反过来，安静时那档本底也不会因为它而"够大"（本底读数正本 [[音频#四、测试记录|音频——四、测试记录]]）。

### 2.2 录音是恒开的，切头是事后按帧回扫

- **采集侧**：进程从启动到退出一直在读 ALSA，把每一帧同时写进两处——一个只保留最近几百毫秒的 **pre-roll 环形缓冲**，和一个"当前句"累加器。VAD 的判决只决定"这段字节是不是一句话"，从不决定"要不要读麦克风"。
- **切头侧**：端点计数满了以后，拿这一段的起始帧号回到环形缓冲里捞 pre-roll，起点退到**判决为语音的第一帧**、再留 1 帧余量；尾部把超出端点阈值的那段静音剪掉。

为什么不能"等 VAD 说开始了再开录"：判决本身要一整帧（30 ms）才出，防误起还要连续帧确认，从真正发声到"开始录"已经 60~90 ms 过去了。汉语塞音／声母的除阻段就集中在句首那几十毫秒，切掉它等于把第一个字最有信息的一段扔掉——ASR 前端（fbank ＋ 倒谱均值归一化）拿到的首帧是残缺的，典型后果是首字丢或同音替换。pre-roll 的存在就是为了把这段时间还回去。

也不要改用能量切头：本板上这台麦"安静"与"轻声起音"在 30 ms 粒度上并不总是分得开，而"能量 FSM 与神经网络分段谁更对"在这块板上**至今没裁**（见 [[ARM CPU TTS性能测试]] 第十五节）。所以切头以 VAD 帧判决为准，能量只当旁证。

### 2.3 建议参数（webrtc 档，全部未核，跑起来才能定档）

| 参数 | 建议初值 | 依据与风险 |
|---|---|---|
| 帧长 | 30 ms @16 kHz ＝ 480 样本 ＝ 960 B | WebRTC VAD 只接受 10/20/30 ms × 8/16/32/48 kHz（B，未对着所选移植核） |
| aggressiveness | 1 | 调高＝更容易把非语音判成静音，代价是轻声尾部切早 |
| 起音确认 | 连续 2 帧（60 ms） | 单帧判决误起会直接发一个空段出去 |
| 端点静音 | 400 ms | 与现役链路同档；200 档与 800 档各自的实测后果（空段／同音替换、长尾撞顶）记在 [[板端FunASR链路操作与可调参数#四、需要她斟酌调整的旋钮（当前值全在这）\|板端FunASR链路操作与可调参数——四、需要她斟酌调整的旋钮（当前值全在这）]]，本页不复述 |
| pre-roll | 500 ms | 覆盖起音判决延迟有余量；太小＝切掉句首，太大＝多带一段无关音频 |
| 最短段 | 250 ms | 短于此不发，省一次往返、也省一次误触发 |
| 最长段 | 20 s 到点强制闭合发包 | 照现役的模型侧单段硬顶那一档取（数值与它存放在哪个文件里，同上一条链接） |
| 缓冲不变式 | 环形缓冲保留时长 > 最长段 ＋ 端点静音 ＋ pre-roll | 违反就会**静默吃音频**：段闭合比这慢，开头就切不回来。这条推导现役链路已经推过，耦合关系同页第五节 |

换到模型档，上表里三行要重写：帧长由模型自己的窗定、"起音确认"变成概率阈值 ＋ 平滑窗、"端点静音"变成以帧计的 `min_silence_*`。**同一个语义在不同档里单位不同**，所以切档＝同时换一套参数，不能只改一个数。firered 那批以帧计的阈值现在还不能抄（帧长毫秒数未读到，见第 4.1 节）。

## 四、开发选型（收敛后）

### 4.1 断句器做成可切换的四档，默认取中文特化档

她的原话："vad三种都选，做成可切换的，中文特化的优先，增加一个小红书的firered vad"。落成实现＝**同一套帧判决状态机，后端可换**，编译期选择（代价见末段）。

| 档 | 是什么 | 要不要 ONNX Runtime | 中文特化 | 本板实测 | 帧长 | 判决参数 |
|---|---|---|---|---|---|---|
| `fsmn` | FSMN-VAD（达摩院，现役板上链路正在用的那颗，权重目录体积正本见下一列 [[板端FunASR链路操作与可调参数#三、测试期脚手架（最后实装要卸掉的）\|板端FunASR链路操作与可调参数——三、测试期脚手架（最后实装要卸掉的）]]） | 要 | **是**（`zh-cn` 件） | **有**：RTF 与句尾静音扫档读数正本 [[板端FunASR链路操作与可调参数#一、现役链路是什么\|板端FunASR链路操作与可调参数——一、现役链路是什么]] | 以毫秒计 | `max_end_silence_ms`／`max_single_segment_time`，数值与存放位置同上一条链接 |

**默认档＝`fsmn`**，四条理由：① 它是"中文特化"这一格唯一在**这块板上跑通过**的（其余中文候选只有厂商数）；② 现役链路的切句读数与它绑定，端点静音扫档那批实测可直接复用；③ 它的旋钮按毫秒计，第 2.3 节那张表里"以帧计"的换算坑当场不存在；④ 换档成本只在运行时（多挂一颗小权重）。**代价写清**：默认档需要 ONNX Runtime，所以"纯 C、零 ORT"那一档**不是默认**——`webrtc` 要显式选，选它就等于接受"本板零实测"。这一格（默认取 fsmn 而不是 firered）是我拍的，改判权挂在 D-78 未决 ②。

| 重采样 | `plughw:` 直取 16k | 官方 `LinearResample`（线性插值，质量档低于 FIR）／自写多相 FIR | 本板重采样质量的对照实验她 10-04 已判不测，口径正本见 [[音频#四、测试记录\|音频——四、测试记录]]；所以这里**只做工程取舍（谁少写代码）不做音质取舍** |
| 外发 | 复用官方 `funasr-wss-server`，一句一条短连接 | 自包 HTTP；或官方 `runtime/http`（未核） | 三条判据见第 5.2 节 |
| 出声 | 本机 `ekho-server` 的 `POST /tts` | 进程内调 libekho | ekho 未上板，接口与格式以 [[实时伪tts]] 为准 |
| 常驻 | systemd unit ＋ `LimitAS` | `rc.local` ＋ `cap.sh` 那套 | 现役用后者，两者选一别混 |

不进这个程序的：标点模型、tokenizer／seg_dict、ITN 资源、任何 Python 运行时、venv。ORT 只在选了模型断句档时才进来。

## 五、协议与部署

### 5.1 一次外发的三帧契约（照官方参考客户端抄）

| 序 | opcode | 内容 | 出处（A，均为 2026-10-21 现读） |
|---|---|---|---|
| 1 | text | `{"wav_name": <段号>, "wav_format": "pcm", "audio_fs": 16000, "itn": false, "svs_itn": false, "is_speaking": true, "chunk_size": [5,10,5], "chunk_interval": 10}` | 发端 `funasr-wss-client.cpp:231-249`（`wav_format`／`audio_fs`／`itn`／`is_speaking` 四个键逐行现读；`itn` 默认 true、第 244 行改 false）；`chunk_size` 那三项是流式遗留字段，离线整段是否被读**未核**，参考客户端无条件照发，先跟着发 |
| 2 | binary × N | 该段 16 kHz／int16／单声道 PCM；参考客户端按 `block_size = 102400` 字节分块循环发 | `funasr-wss-client.cpp:274` 一带 |
| 3 | text | `{"is_speaking": false}` ⇒ 服务端把这条连接的整块缓冲 `asio::post` 给解码线程 | 发端 `funasr-wss-client.cpp:332`；收端 `websocket-server.cpp:378` |
| 回 | text | 一段 JSON 文本（参考客户端只把它打印出来，字段名本轮未逐读） | 收端 `websocket-server.cpp:120-142` |

采样率写在第 1 帧、位宽由 `wav_format: "pcm"` 约定为 int16——所以**不需要 44 字节 WAV 头**。第 2 帧起是 `n × 2` 字节，段长可按下式自洽核对（验收第 1 条用）：字节数 ÷ 2 ÷ 16000 ＝ 段秒数。

### 5.2 服务端形态：不必用 HTTP，也不是每请求冷启动

她问"一定要用 http 外发吗，funasr 内部组件之间怎么传数据的，应该不是上一个来了才冷启动吧"。**她这句直觉是对的，而且能引到源码行**：

- **模型只在服务启动时装一次**：`WebSocketServer::initAsr()` 里 `asr_handle = FunOfflineInit(model_path, thread_num, use_gpu, batch_size)`（A：`websocket-server.cpp:417-422`），它在主函数把 io 循环跑起来之前被调用，紧接着一句日志 `asr model init finished. listen on port:`（A：`funasr-wss-server.cpp:516`）。所以"请求来了才装权重"不存在。
- **组件之间是进程内函数调用，不是网络**：`FunOfflineInit` → `OfflineStream` 构造函数按 `model_path` 里有没有那几个键逐个装载——`VAD_DIR` 给了、且 `model.onnx`／cmvn／config 三件齐全才 `use_vad = true`，缺任一就打 `VAD model file is not exist, skip load vad model.`；`PUNC_DIR`、`ITN_DIR` 各自独立可选（A：`runtime/onnxruntime/src/offline-stream.cpp:7-28、107-146`）。⇒ **可以只挂 ASR**，正好对上"边缘端断句、服务端只转写、不出标点、不做 ITN"。热词同理：只有模型目录里存在 `model_eb.onnx` 才启（同文件 63-72 行），所以 seg_dict 也不必带。SenseVoice 那颗更狠：`model_type == MODEL_SVS` 时 `use_itn`／`use_punc` 被无条件置 false（同文件 147-150 行）。
- **一条连接的成本不是零，但只是解码器句柄**：`on_open` 里 new 一个 `std::vector<char>` 缓冲 ＋ `FunASRWfstDecoderInit(asr_handle, ASR_OFFLINE, …)`，`on_close` 里 `FunWfstDecoderUnloadHwsRes` ＋ `FunASRWfstDecoderUninit`（A：`websocket-server.cpp:154-208`）。⇒ **"一句一连"完全合法**：参考客户端本身就是一次 `connect`（第 134 行）、按文件列表逐个发、发完置 `close_client = true`（第 155 行）后在应答回调里 `m_client.close(...)`（第 108 行）——连接生命周期由客户端定，不是协议限制。
- **于是三条判据**（选协议只看这三条）：① 想零自研服务端 ⇒ 只能用官方那份，它的对外形态是 ws ⇒ 接受"短连接 ws"；② 想连 ws 这个字都不要 ⇒ 只有自包一层 HTTP／gRPC，代价＝服务端那块自己重写并长期维护，且官方那套 `FunOffline*` C API 得自己接；③ 想省掉自研又要纯 HTTP ⇒ 先读 `runtime/http` 到底能不能整句收发（本轮**未核**，它是唯一还挂着的一条）。
- **D-78 取 ①**：边缘端按"一句一连"用官方 ws 服务。这与她原话"没有长连接 websocket"的关系已在第一节写成解释——禁的是常驻连接，不是一问一答。**如果她认为 ws 短连接也算违禁，退回 ② 或 ③ 即可，本节就是回退入口。**

### 5.3 部署步骤

```
1  校机交叉编译两类产物：VadBackend=webrtc（不链 ORT）与 VadBackend=fsmn（链 ORT）
2  产物过 L1 三闸再拷板（板端 rootfs 已用近八成，位置按 [[硬件与基础运行环境档案]]）
3  服务端：起官方 funasr-wss-server，只给 --model-dir，不给 --vad-dir/--punc-dir/--itn-dir
4  校机侧先验契约：用官方参考客户端发一件已知 wav，把三帧与回包字段抄成契约页
5  写主程序：ALSA 采集 -> 帧状态机 -> pre-roll 环 -> 段闭合 -> 三帧外发 -> 文本送 ekho
6  装 systemd unit，LimitAS 先按第 5.4 节那条给个未核的初值，跑一轮 sizing 再收
7  开机自启，前台跑一轮看日志，再交给 systemd
8  验收：跑第七节六条判据，缺一条不算过
```

`intra_op_num_threads`／`--model-thread-num` 这类线程旋钮**只在选了模型档时才有意义**；纯 `webrtc` 档的进程里没有这个旋钮，线程预算就一句话：采集线程 ＋ 发送线程，别更多。服务端侧另有 `--io-thread-num`／`--decoder-thread-num`／`--model-thread-num` 三个（A：`funasr-wss-server.cpp:101-106` 的命令行定义），它们跑在远端机器上、与本板的核数预算无关，别混进同一张表。

### 5.4 服务单元

内容全英文，避免 codepage 与 CI 编码问题：

```ini
[Unit]
Description=WCIS edge VAD sentence poster
After=local-fs.target

[Service]
Type=simple
ExecStart=/usr/local/bin/funasr-edge
Restart=always
RestartSec=2
LimitAS=512M
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

`LimitAS=512M` 是占位初值，**没有任何实测支撑**——现役那条链的上限是量出来的（数值正本 [[板端FunASR链路操作与可调参数#四、需要她斟酌调整的旋钮（当前值全在这）\|板端FunASR链路操作与可调参数——四、需要她斟酌调整的旋钮（当前值全在这）]]），但那一档包含板上转写，不能搬过来用。

## 六、运行约束

| 约束 | 落到实现 | 现况 |
|---|---|---|
| 空闲时 VAD 仍轻跑，避免冷启动 | 采集与判决不随说话开关；进程不重启 | 本板 `webrtc` 档**无占用读数**（第三轮那档失败），silero 档有数但那含 Python/numpy 开销；模型档的"冷启动"只在服务侧，而服务侧每请求不重装（第 5.2 节） |
| 空闲时无其他重计算 | 没有段在飞时不发网络、不分配大缓冲 | 待测 |
| 不做标点与 ITN 推理 | 边缘端不带任何 punc／itn 资源；服务端不挂 `--punc-dir`／`--itn-dir`；请求头帧再发一次 `itn: false` 兜底 | 第三节第 2、3 条已按此改判，冲突消解 |
| 无常驻连接、无流式 | 一句一段：连—发—收—断；超时后丢弃并记账 | 超时值未定；"短连接 ws 算不算违她原话"挂在 D-78 未决 ① |
| 目标设备"4 核 1 GHz" | **1 GHz 是手册标称、板上取不到频率读数**（无 cpufreq 接口），规划里把它当已知量要打个折；核数与频率的现场口径归正本，本页不抄第二份 | 正本 [[硬件与基础运行环境档案#一、硬件规格报告\|硬件与基础运行环境档案——一、硬件规格报告]] |

## 七、验收判据（这条链怎么算跑通）

1. **说一句话停 0.6 s**：收到文本，且发出去的段长与"说完话"的时刻对得上；段字节数 ÷ 2 ÷ 16000 ＝ 段时长，逐帧自洽（这套"按字节数反推时长"的验收法在 [[音频#四、测试记录|音频——四、测试记录]] 用过）。
2. **首字不糊**：同一句连录 20 遍，转写文本首字一致；若首字翻动，先怀疑 pre-roll 太短。
3. **静音 60 s**：零发包，CPU 占用有读数（这一条补上本板 `webrtc` 档的实测缺口）。
4. **底噪不触发**：拿那档"安静房间"量级的素材放给链路（本底读数正本 [[音频#四、测试记录|音频——四、测试记录]]，同量级合成底噪素材的做法见 [[ARM CPU TTS性能测试]] 第十二节），要求零段。
5. **长时不掉道**：连续 1 h，采集侧不丢帧、发送侧不积压；长跑同时记 `VmHWM`／`VmSwap`／缺页，口径同 [[板端内存上限与心跳日志]]。
6. **协议自证**：抓一次外发，逐帧核对第 5.1 节三帧的形状；回包字段抄全、落成契约页——**没有这一页，"远端返回纯文本字符串"这句话就还是猜的**。
