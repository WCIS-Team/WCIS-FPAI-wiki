## 一、先决事实：这块板子上 cgroup 根本不存在（**实测，三处都空**）

| 查什么 | 读数 |
|---|---|
| `/proc/cgroups` | **只有表头，零行**（`#subsys_name hierarchy num_cgroups enabled` 下面是空的） |
| `/sys/fs/cgroup/unified/cgroup.controllers` | 空 |
| `/sys/fs/cgroup/memory`（v1） | 不存在 |
| 挂载 | `tmpfs /sys/fs/cgroup(ro)` ＋ `cgroup2 /sys/fs/cgroup/unified` ＋ `cgroup /sys/fs/cgroup/systemd`（只有 named 那套） |

⇒ **内核没有编译任何资源控制器**（memory／cpu／io 都没有）。实测后果：

```
systemd-run --scope -p MemoryMax=100M -- python3 -c "分配 400MB"
→ SUCCEEDED 400MB in 100M scope -> MemoryMax NOT enforced
```

**systemd 245 不报错、静默忽略**。这条要写死：`MemoryMax`／`MemoryHigh`／`CPUQuota`／`IOWeight` 在这块板子上**全是 no-op**，谁再往方案里写 cgroup 限资源，就是写了一条不生效的假闸门——和 §十二 里"闸门＝load1＋MemAvailable"那种**真读 `/proc` 的闸门**不是一回事，别混。

## 二、上限只能走 RLIMIT_AS，两个坑都得先知道

没有 cgroup 时，能把"分配无限增长"换成"分配失败"的就只剩 `prlimit --as`（`RLIMIT_AS`）。**实测有效**：

```
prlimit --as=209715200 -- python3 -c "申请 400MB"
→ ALLOC REFUSED at 183 MB (cap works)
```

**坑 1｜带单位后缀会 segfault。** 本机 `util-linux 2.34-0.1ubuntu9.6`：

```
prlimit --as=200M     -- python3 -c "print('ok')"   → Segmentation fault（139）
prlimit --as=209715200 -- python3 -c "print('ok')"  → ok
```

⇒ **后缀必须自己换算成字节再喂给 prlimit**，`#166` 的 `cap.sh` 就是自己换算的（`to_bytes()` 认 K/M/G）。这不是配置问题，是这个版本的 bug，直接抄命令会踩。

**坑 2｜`RLIMIT_AS` 卡的是虚拟地址空间，不是 RSS。** ORT 这类运行时 VA 远大于 RSS：

| 时刻 | VmSize | VmRSS | 比 |
|---|---|---|---|
| 刚 `import onnxruntime` | 207,860 kB | 38,488 kB | 5.4× |
| 装载完 Paraformer-large | **732,280 kB** | 369,528 kB | 2.0× |
| 装载完 SenseVoiceSmall | **760,496 kB** | 398,104 kB | 1.9× |

⇒ **`--as` 必须按 VmSize 峰值定，拿 RSS 直接当 AS 上限会把正常任务掐死。** 第一次用某个新任务请带 `--as 2G` 跑一遍 sizing，从心跳日志里读 `tgt_vsz` 峰值再收紧（`cap.sh` 会自动把峰值打出来）。

## 四、CMA 是比 RAM 更早见底的那个瓶颈

启动预留 **CmaTotal 262,144 kB（256 MB）**，这块**malloc 一点都碰不到**；真正能给用户态的是 `754924K/1048576K available` 那一行。空闲时 `CmaFree` 在 **15 MB～96 MB 之间飘**（Mali DDK 初始化后就占掉一大块）。**装载模型期间它会见底**：

| 时刻 | CmaFree |
|---|---|
| 空闲 | 96,152 kB |
| 装载 SenseVoice 期间 | 1,876 → **44** → 3,976 kB |
| 装载 Paraformer 期间 | **0** → **0** → 47,288 kB |

⇒ 256 MB 的连续内存池在装一个 232 MB 权重时会被压到 **0 kB**。**这一条比"993 MB 不够用"更能解释那次挂死**：10-11 20:17 是 **ASR 批跑（`run_env.sh` pid 3184）和 Qwen2 点火同窗**，两条链都要连续内存；CMA 分配失败如果落在厂商 NPU／Mali 驱动里，表现就是**整机卡死且一行日志都写不出来**——而那正是现场的样子。

⚠ **这条是机制推断，不是已证实的死因**：没有 `/sys/kernel/debug/cma` 的 current/peak 读数（`CONFIG_DEBUG_CMA` 没开），也没有崩溃时的内核打印。**要证它，只能等下一次同窗起跑时把心跳开着**（心跳每行都带 `cma=`，见下节）。

**10-11 晚那场就是"把心跳开着"跑的第一轮，结果把这节的归因往下压了一档**（A 级读数，全在 [[板端我方代码与产物台账#十六、板端 OS 侧改动、指标扩展与 ASR 战役续（2026-10-11/12，D-44 的执行体）|板端我方代码与产物台账——§十六]] 的战役表里）：离线 Paraformer＋FSMN-VAD **单链**逐件跑完四件（60／122.9／246.5／289.5 s 音频），四件自报的 `cma_free_min` 依次是 **63,756／27,504／19,984／0 kB**——最长那件把 `CmaFree` **打到了 0**，同窗 `hb.sh` 在 19:09:40 那行记到 `cma=100`，**而板子活着、四件全跑完、`asr_errors` 与 `ring_lost_ms` 全 0**。

⇒ **"CMA 见底"不足以单独让整机挂死**，那条判据（第四节＋§十四 的回写 ③）从此不能单用它解释 20:17 那次；剩下的解释要往"两条链同窗"这侧找（那是本轮没有的条件）。**但这一列仍然是更早报警的那一列**——`CmaFree` 掉到 0 时进程毫发无损，只能说明**用户态 malloc 碰不到它、也就不受它伤害**，而厂商 NPU／Mali 驱动要连续物理页时会不会失败、失败后干什么，这轮**没有测到**（没跑 NPU 侧任何东西）。

**10-28 补：NPU 侧那半有了一份读数，但仍没结案**。10-14 的 Qwen3 四档预检（位流含 NPU、`apply` 75.1 s 跑完、`exit=0`、一次电没断）在 5 s 心跳里记到 `CmaFree` 最低只剩 **80 kB**、同档 apply 窗口 `MemAvailable` 最低 **5,020 kB**——出处与逐条时间戳在 [[板端我方代码与产物台账#廿一、Qwen3 件上板与四档预检（2026-10-14 18:09–18:43 UTC 推件＋预检；10-28 逐份读出补登记）|板端我方代码与产物台账——§廿一 `#212`／`#213`]]。⇒ "CMA 几乎见底时 NPU 链照样跑完并正常退出"现在有了实例，**但"分配失败之后驱动干什么"仍没测到**：这四次都没失败、也没归因那 130 MB 是谁占的（s0～s2 同一步 `CmaFree` 一动不动，只有 s3 掉下去）。所以本节结论不变，只是"能不能撑住"这半从 D 升成 A。

## 五、心跳日志 `hb.sh`（`#166`）

**为什么需要**：10-11 那次挂死，`journald` 还压在内存缓冲里的日志**一行都没落盘**，`/var/log/journal` 里查不到那个 boot ID（只有 10-09 22:38 那次和本次）。事后能定位到的"最后一条"只是 `run_env.sh` 闸门打在 `/root/funasr/logs/env_probe.log` 里的 `wait gate` 行——**那不是设计，是运气**。

**每行字段**（key=value，便于 grep/awk）：

```
ts=2026-10-11 16:22:48 mono=1989.90 load=0.80 avail=393220 cma=3976 dstate=0 top=398104/python tgt=R rss=398104 vsz=760496 wchan=0
```

| 字段 | 含义 | 判读 |
|---|---|---|
| `mono` | 开机秒（`/proc/uptime`） | 不受板子**没有 RTC**、每次上电时钟从 1970 起这件事影响 |
| `avail` | `MemAvailable` kB | 逼近 0 才是内存问题 |
| `cma` | `CmaFree` kB | **见上一节：这条比 `avail` 更早报警** |
| `dstate` | D 状态（不可中断睡眠）进程数 | 突增＝卡在内核等待（多半 I/O）；600M 那次失败时就抓到 `dstate=3` ＋ `wchan=generic_file_read_iter` |
| `top` | 全板最大 RSS 进程 | 谁吃了内存 |
| `tgt` | 被盯进程的 `State`／`rss`／`vsz`／`wchan` | `tgt=D`＋`wchan` ＝ 卡在哪个内核函数 |

**落盘时序**：每行是一次独立的小 write（`>>` 追加），内核 `dirty_expire` 默认 30 s 刷到卡 ⇒ 硬挂死时最多丢最后 30 s 的行，之前的都在盘上。**这就是它比 journald 强的地方**——journald 要先活到刷盘那一刻。

**用法**：

```bash
hb.sh start <tag> [interval_s] [pid]     # 后台起，日志 /root/hb/<tag>.log
hb.sh status                             # 在跑哪些 + 各自最后一行
hb.sh tail <tag> [n]                     # 看最后 n 行
hb.sh stop <tag>
```

`#146` `run_env.sh` 那个 `wait gate` 每 20 s 一行是同一思路的早版本（只记两个量、只覆盖批跑窗口）；`hb.sh` 是它的通用化。

## 六、带上限的运行器 `cap.sh`（`#167`）

```bash
cap.sh --as 900M --tag qwen2 -- python3 qwen2_infer_decode_only_axi.py
cap.sh --tag sweep --interval 10 -- bash -c '...'          # 不设上限，只记心跳
cap.sh --as 900M --tag run --no-hb -- ./bench.sh
setsid nohup cap.sh --as 900M --tag long --interval 5 -- ./long.sh &   # 长跑：三个 fd 都重定向
```

跑完自动打：`exit=` 码、`实限`（从 `/proc/<pid>/limits` 读回来，**确认上限真的落到子进程上**）、峰值 `tgt_rss`／`tgt_vsz`、最后 3 行心跳；非 0 退出时额外打最后 10 行。`/proc/cgroups` 为空时会提示"MemoryMax 不可用，本次只靠 RLIMIT_AS"。

**这正是 §十四 认的那条账**（"远端长命令写成 `… | tail -60`，SSH 一断遗言全丢"）：`cap.sh` 一律 `> 落板端文件`、读文件不读管道，心跳与 stdout 都在 `/root/` 下，重新上电后 `hb.sh tail <tag>` 直接读。

## 八、串口是唯一的现场通道（COM 一直连着）

- 本机 **COM6 ＝ Silicon Labs CP210x USB to UART Bridge** → 板子 `/dev/ttyPS0`。
- 板侧参数是内核命令行写死的：`console=ttyPS0,115200n8 earlycon=uart8250,mmio32,0xe0004000`。**这条以后不用再查**。
- **COM 一直连着**（她的设备状态，不是临时插的）。
- **本轮实测串口是活的**：COM6 打开 115200 8N1、发两次回车 ⇒ 收到 4 组 `U login:` 提示。

⇒ **更正 [[板端我方代码与产物台账#十四、Qwen2-0.5B 上板（2026-10-11，本机编译＋板上只部署）|§十四]] 留的那条保留意见**：当时写"发回车 0 字节，但厂商镜像是否在 `ttyPS0` 起 getty 未核 ⇒ 串口静默**不能单独**当死机证据"。**getty 确实在起**（`getty@ttyPS0.service` 在 running 列表里，串口实测有登录提示）⇒ **从现在起，"串口发回车 0 字节"可以单独当死机判据用**；反过来串口有 `login:` 提示就说明内核还活着、只是网络挂了。

本机抓法（PowerShell，30 秒内能出结果）：

```powershell
$p = New-Object System.IO.Ports.SerialPort "COM6",115200,"None",8,"One"
$p.Open(); $p.Write("`r`n"); Start-Sleep -Seconds 3
# 读 BytesToRead → 有回显=活着；0 字节=按死机处理
$p.Close()
```

⚠ **挂死瞬间只有串口能看到内核 printk**——journald 那时已经在死了（第四节）。这是它不可替代的地方。

2. **整链路的 VmSize 峰值：已测（10-12，台账 `#177`）**。做法走的是第二条路——`cap.sh --as 2G --tag sz --interval 2 -- <链路>`，输入 `d290.wav`（289.5 s，四件里最长），板钟 22:37:51→22:43:09 UTC、`exit=0`、147 个 2 s 心跳样本。**峰值 `tgt_vsz` 829,380 kB＝810.0 MiB，同时刻 `tgt_rss` 峰值 419,268 kB＝409.4 MiB ⇒ 这条链的 VA/RSS ≈ 1.98**（落在第三节记的 1.9～5.4 倍区间下端）。⇒ **`--as 1G` 这个旧估值离峰值只差 190 MiB，不该再用**；按峰值留 1.85 倍余量，**整链路上限收到 1.5 G** 才有余地，2 G 是 sizing 档不是运行档。单档（`env_probe` 那种一进程一模型）此前定的 900 M 没在这轮复核，仍按原值。⚠ 这条只覆盖**离线 Paraformer＋fvad 这一档链路**，换后端（SenseVoice 峰值 RSS 更高）或加常驻麦克风缓冲，VA 还得重测。**10-12 她裁"要套"⇒ 已落成运行档**：`run_testset.sh` 默认对每件起 `cap.sh --as 1536M`（`#178`／`#180`，`AS=off` 才裸跑），随后 **10 场带上限的跑（扫档 7＋默认档 1＋文本复测 3）全 `exit=0`，`tgt_vsz` 峰值 811,172~817,072 kB＝792.2~798.3 MiB**——包括 `end-sil` 收到 400／200 那种**段数 ×2.7~3.5** 的更碎形态，VA 只比 sizing 场高约 6 MiB，离上限还剩约 740 MiB ⇒ **1.85 倍余量在改档之后依旧成立，"切更碎会把 VA 抬上去"没有发生**。**这套上限卡的不是整机 RAM 也不是 RSS，而是单个进程的虚拟地址空间**（触限＝分配失败，不是被 OOM killer 杀；所以上限写 1536 M 大于 993 MB 物理内存是故意的），完整口径见 [[状态源与决策记录#D-45 · 长跑一律套 1536M 的 RLIMIT_AS 上限，VAD 句尾静音从 800 ms 收到 400 ms（长尾被打掉且文本未变），并公开更正"离线 Paraformer 的文本被我方 wrapper 输出两遍"|D-45 决定 1]]。
