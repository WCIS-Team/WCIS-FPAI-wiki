### 1.1 为什么这个镜像"必须配一张刚好大的卡"，而普通发行版不会

厂商让用 `imageUSB` 烧，是因为它**只会按字节整盘写**：把镜像从头到尾原样灌进设备，写完就结束，**没有任何调整分区大小的逻辑**。镜像 29.72 GiB，所以卡必须 ≥ 29.72 GiB，容不下一句"卡小一点也行"。

普通 Linux 发行版（树莓派、Armbian、Ubuntu 官方镜像）之所以给 2 GB 卡也能烧，是**做法不同**，不是工具更聪明：

| 做法 | 说明 | 本镜像有没有 |
|---|---|---|
| 镜像本身做得很小 | 只装必需的根文件系统，几个 GB 起步 | **没有**，厂商给了 29.72 GiB |
| 首次开机自动扩容 | `raspi-config` 的 `--expand-rootfs`、`growpart`、`systemd-growfs`、cloud-init `growpart`——开机时脚本发现"卡比镜像大"就把最后一个分区拉满 | **没有**。rootfs 是 ext4 直接铺到分区边界，`/etc` 里也没有 growfs 类服务 |
| 分区表留未分配空间 | 镜像里分区只占一半，剩下的留给用户 | 未验证；从 FAT 起点 = LBA 2048 这种标准对齐看，厂商更可能是"分区铺满"的做法 |

**结论**：换大卡（64 GB／128 GB）时，烧完仍然只有 29.72 GiB 被写入，**多出来的部分是未分配空间，系统不会自动用**。要用的话得自己 `growpart` + `resize2fs`，而这两件事都要求分区表读得对——正好卡在"MBR 到底在偏移 0 还是 512"这条**待验证**上。所以顺序是：先到板 `fdisk -l /dev/mmcblk0` 看清楚，再决定要不要扩。

**如果确实想把镜像做小**，只有三条路，代价从低到高：

1. **只替换内容、不缩容器**——最省事。启动分区是 FAT、根分区是 ext4，都是普通文件，直接在 PC 上挂载改文件，镜像尺寸不变。日常开发根本不需要缩。
2. **截断尾部空闲块**——ext4 尾部多半是空块，`e2image -ar` 或 `dd` 只拷到最后一个分配块，能压出可观的空间；但**必须先确认 MBR 与分区表在哪**，否则截完的镜像分区表指向卡外，板子直接起不来。
3. **重建成小镜像**——`losetup` 逐分区导出、新建小分区表、`mkfs` + `rsync`、修 `fstab`／`bootargs`／dtb 里的根设备。这等于自己做一个发行版，**收益只有"能用小卡"，风险是丢厂商东西**（`uEnv.txt` 的 `bootargs`、`download.bit` 名字、`/root` 下的脚本路径都可能被隐式依赖）。**不建议在比赛周期做**。

## 四、对软件栈的硬约束（这一节最影响设计）

1. **出厂镜像只随带 3 个现成模块；其余 `=m`／`not set` 的项板上没有模块文件。**（**2026-09-30 板端实测更正，见本条末段**）`/lib/modules/` 下只有 `5.4.52` 与 `5.4.52-gce01ed384` 两个目录；journal 里实际开过机的那几颗（`v2024.02`、`v2022.10` 两代更早构建）与目录名不匹配、`.ko` 的 vermagic 也不匹配。2026-03-13 那两次开机**没有任何** `Inserted module` 记录，而 2023 那批（内核名与目录一致的旧构建）`amvx`、`mali_kbase` 各插入 21 次。
   后果（原判断）：`/etc/modules` 里的条目、`mali_kbase` 的 `modules.softdep`（`pre: memory_group_manager`）、所有 `=m` 驱动在出厂镜像上都是静默失败。
   设计含义：**功能只能建立在内建（`=y`）驱动之上**；确实需要模块时，前提是拿到与运行内核完全一致、且带 `build` 目录的内核树重编（镜像里 `5.4.52-gce01ed384/build` 有源码树，但版本对不上运行内核）。
   **更正（E5，2026-09-30 板端实测）**：随镜像的这颗 `Image`（`#3`，2026-03-13 13:44 构建）在本板起的 `uname -r` = **`5.4.52`（无后缀）**，与 `/lib/modules/5.4.52/` 同名，`modinfo` 实读 `u-dma-buf.ko` 的 vermagic = `5.4.52 SMP mod_unload aarch64` **匹配**；三个 `.ko`（`u-dma-buf`／`mali_kbase`／`amvx`）**随开机全部加载**（`lsmod` 实到；`/etc/modules` 出厂就写这三个名字）。journal 里的不匹配记录全部属于**更早的内核构建**——厂商板 2026-03-13 11:07–12:03 的那几次开机早于镜像 `#3` 的 13:44 构建。口径改写为：**"一个驱动能不能用"看板上有没有对应 `.ko`，出厂镜像只有这 3 个**——设计含义不变，但理由从"模块机制坏了"改为"镜像里没装"。逐条读数见 [[PS/psrt&dev/os#二、内核模块（含一条对镜像取证结论的更正）\|os——二、内核模块（含一条对镜像取证结论的更正）]]。
2. **1 GB 内存是硬顶**，还可能被 CMA 拿走 256 MB。torch 本体 189 MB，多路 UVC 解码 + 推理 + 音频并发要按 700–1000 MB 的可用内存规划，`loglevel=8` 与 journal 也在吃这块。
3. **4 个 USB 口 = 一条 480 Mbps 总线。** 摄像头、麦克风、音箱、HID 必须合并算带宽；YUY2 720p30 约 55 MB/s（约 440 Mbps）已经吃掉几乎整条总线，所以摄像头**必须**走 MJPEG 或 H.264。
4. **没有任何板载音频硬件。** 麦克风与音箱只能走 USB（`CONFIG_SND_USB_AUDIO=y` 内建，插上即用），这也意味着 AEC 参考流必须来自同一台 USB 设备（带 loopback 的阵列或全双工会议一体机），两台独立声卡拿不到。
5. **没有 X server，也没有 Wayland 合成器。** `cv2.imshow`、GTK/Qt 窗口都起不来；结果只能落文件、stdout 或网络。演示时"接屏看画面"这条路在出厂镜像上不通。
6. **UVC 与 USB 音频都是内建**，这是把采集链放在 PS 侧的最大理由：`CONFIG_USB_VIDEO_CLASS=y`、`CONFIG_USB_VIDEO_CLASS_INPUT_EVDEV=y`、`VIDEOBUF2_*` 全套内建、`CONFIG_SND_USB_AUDIO_USE_MEDIA_CONTROLLER=y`。
7. **MIPI 直采在这块板上作废。** `CONFIG_VIDEO_OV5640=y` 与 Xilinx AXI 视频 IP（`CSI2RXSS`／`VPSS_*`／`TPG`／`VTC`）确实编在内核里，但：**完整版手册通篇没有 MIPI／CSI 字样**，J16 座子是 **Lite 独有**；随镜像 dtb 又把两路 I2C（`i2c@e0002000`、`e0022000`）全 disable 了。→ 从"二期实验"降级为**不做**，除非到板目视发现板上其实有座子。
8. **CAN0 是唯一"四头都对得上"的板载外设**：完整版配置表登记 2 路 CAN，dtb 里 `can@e0005000` = **okay**（`e0006000` disabled），内核 `CONFIG_CAN=y`+`CAN_SJA1000=y`+`CAN_SJA1000_PLATFORM=y` 全内建，journal 里实到 `sja1000_platform e0005000.can: sja1000_platform device registered (irq=6)`。也就是**不改内核、不改 dtb、不出比特流就有现象**——到板值得花五分钟验一次，作为"取证结论正确"的对照实验。注意上游 `XILINXCAN` 并**未**编译，走的是 SJA1000 平台驱动这条路。
9. **系统时间没有可信来源**：`CONFIG_RTC_CLASS=y` 但**整份 `.config` 里一条 `CONFIG_RTC_DRV_*` 都没有**，dtb 里也没有 rtc 节点（完整版硬件有 1 路 I2C RTC）。每次启动 `hctosys: unable to open rtc device (rtc0)`，这正是 journal 里大量记录停在 `2023-03-02 20:58` 的原因。**含义**：板端时间戳不可信，任何需要时序的自测数据都要自己打单调时钟（`CLOCK_MONOTONIC`）或与 PC 对时，不要依赖 `date`。
10. **rsyslog 会刷屏**，原因是 `/var/log` 属 `root:107` 且 755，而 rsyslog 降权到 `syslog` 用户写不进去，于是 `omfile` 反复 suspended/resumed。纯软件问题，改属主即可，不要当成硬件故障。

## 八、想重新跑一遍取证

1. 7-Zip 解出 `.img`（31.9 GB）。对整镜像 `fdisk -l` 读不到分区表是**正常现象**：偏移 0 是 512 B 的 imageUSB 头，卡自己的扇区 0 在偏移 512。要查分区表用 `dd if=<img> bs=512 skip=1 count=1 | hexdump -C`。
2. 启动分区：`losetup -f --show -o 1049088 <img>` 得到 loop 设备，直接 `mount -o ro` 该 loop（不是 `loopXp1`）。
3. 根文件系统：`debugfs -c <img>`（不写回），或 `dd` 出 ext4 段后 `mount -o ro,noload`。必须在 Linux 侧做，Windows 挂不了 ext4；WSL 需要 root。
4. 内核 config 不需要源码：`Image` 里 `CONFIG_IKCONFIG` 打开着，解出末尾的 `IKCFG_ST` 段 gzip 即可。
5. journal 不需要跑 systemd：`journalctl -D <目录>` 离线读，系统 journal 与 user journal 分别统计——**合并读只会更少**，user journal 不增加信息。

## 十、SDI 取图链路四步检查表（2026-09-30 实测口径）

**适用症状**：接了 SDI 摄像头但没有画面（HDMI 黑，或我们侧看到的帧全黑）。链路是 `SDI 线 → PL 的 rx_sdi → PL DDR（给 AI）／PS DDR（给显示）→ PS 画框 → display buffer → PL 读出走 HDMI`，**全程没有 V4L2、没有 `/dev/video`、没有 DRM**，所以"有没有识别到摄像头"这个问法在这块板上不成立，只能按下面四步逐段判。**用法**：从第 1 步往下走，**任一步不过就停在那一步**，后面的判据全部作废；每步的"过"都只是必要条件。缩写：**VTC**＝Video Timing Controller，PL 里的测试图形发生器；**GT**＝SoC 的高速串行收发器 bank，SDI 的差分时钟／数据落在哪两个管脚由位流的管脚约束决定。判据等级：A＝到板实测原文，B＝源码或厂商文档直证。

|---|---|---|---|---|
| **1** | **物理层：SDI 线有没有供电、有没有信号** | 断电插线（教程 §4.4.1 原文要求"断电状态下将 SDI 摄像头和 HDMI 接入开发板，上电启动"）；看摄像头指示灯／OSD 按钮有无反应 | 摄像头自检完成（OSD 可调得出菜单） | 线、供电、制式（3G-SDI 1080p60 vs 720p／1080i）问题，跟板子无关 |

### 10.1 板型约束分支闭合：厂商给的那颗就是完整版（A 级，2026-10-04）

**结论先行**：第 4 步里"现场无误才查板型约束"那一支到此关闭——**板上这颗位流是按悟净完整版（`U6/U5`）约束实现的，不是 LITE（`R6/R5`）**。两条互相独立的证据：真 SDI 后来出过图（功能上 GT 必然已经锁上），以及下面这套不依赖运行结果的位流差分取证。**改 xdc 再重新实现这条路不必走**（而且走不通：`FPAI_DEMO说明.pdf` §一原文「FPGA 工程仅适用于 Vivado2018.03」，工程里全是 `gtxe2_i`／`processing_system7_v5_5`／`mig_7series` 这类 Xilinx 专有 IP 与原语）。

**那两行管脚的差别是什么性质的差别：通断，不是性能。** `impl_constraints.xdc` 里那两行只决定 `IBUFDS_GTE2`（GT 的差分参考时钟输入缓冲，`rtl/sdi/rx_sdi.v:179-190`）落在哪一对物理管脚上。这颗缓冲的输出喂 `ip/mgtclk` 那颗 MMCM，MMCM 的 `clk_out1` 再喂 CPLL，而 CPLL 是 CDR（Clock & Data Recovery，从串行数据流里恢复时钟）能否启动的前提。约束落到另一块板的管脚＝缓冲盯着一对板上没接时钟的管脚＝参考时钟丢失、PLL 永不 lock＝`rx_sdi` 一个像素都不产出；**同时 PS 侧 take／done 握手照走不误**，因为它打的是 AXI 从侧寄存器，与 GT 有没有时钟无关。所以错约束的形状恰好是"第 3 步全过、第 4 步帧数满但全黑"。**性能层面唯一沾边的是同一个文件里的 `create_clock`**：它只喂时序分析，频率写错会让 STA 拿一个错的时钟模型（该收敛的判不收敛，或反过来放过），但不改变功能。还有一条要记住：管脚写错时 Vivado **不报错**，它照单把缓冲放到那对管脚上——这类错只能靠板型清单或位流差分来抓（B）。

| 偏移 | 板上那颗 | 完整版 | LITE |
|---|---|---|---|
| `0x042b113` | `08` | `08` | `1c` |

## 十一、960×512 模型上板实验（2026-09-30）

**起因**：试 960×540。**结论先行：540 做不了，实际做成并已上板跑的是 960×512**（下面第一节解释为什么）。这一节记：为什么只能是 512、部署改哪几行、PL 寄存器实测回读、与 640×352 的对照数字。

**为什么 540 不行、512 才行**（B 级，源码直证）：

1. **PL 硬缩放只认整数步长**：`RATIO_W = CAM_W / NET_W`、`RATIO_H = CAM_H / NET_H` 是 C++ 整数除法（`deps/modelzoo_utils/include/et_device.hpp` 的 `preprocess_plin`，写 `0x40080020/0x24` 两个步长寄存器）——非整数步长这一层没有表达能力；
2. **960 是 32 的倍数而 540 不是**：yolov5s 三个检测头 stride 8/16/32，输入必须能被 32 整除才能切出整数格子；540/32 = 16.875；
3. **512 的推导**：垂直 `RATIO_H = 1080/512 = 2`（整除）→ `IMG_H = 2×512 = 1024`、居中裁剪 `y0 = 28`、`y1 = 1051`；横向 `RATIO_W = 1920/960 = 2` → `IMG_W = 1920`、`x0 = 0`、`x1 = 1919`。计算量 = 640×352 的 **2.18 倍**。

**部署只动 yaml 四处**：模型路径、`net_w`、`net_h`、`view_except_op_ids`——PL 步长/裁剪、检测框回映射全从 `net_w/net_h` 推导（B，源码），C++ 一行没改。模型编译与 `view_except_op_ids` 重认见 [[板端我方代码与产物台账]] 第六节。

## 十二、NPU 调用取证与更正（2026-10-04）

**TL;DR**：NPU（iCraft 的叫法是 **AIU**，也就是 PL 里那颗 ZG330 NPU 硬核）**一直存在、而且一直在用**——`[ICORE]` 那行日志里的 `icore=` 就是它跑一层的时间。但**Linux 侧完全没有它的登记**：没有驱动、没有 `/proc/iomem` 条目、没有设备节点、`lsmod` 里也找不到它。真正干活的是 icraft 包带的用户态库 `libaxizg330aiu.so`，它自己 `open("/dev/mem")` 把物理地址窗口 `mmap` 进进程，再自己 `open("/dev/udmabuf0")` 拿 PS DDR 侧的 DMA 缓冲。所以此前那句"内核里看不到 NPU"和"板子在用 NPU"**两件事同时成立，不矛盾**：`/proc/iomem` 只登记被内核驱动 claim 过的地址，用户态直访 `/dev/mem` 不需要 claim，因此不出现。**判据等级**：A＝板上实测原文，B＝厂商源码直证，C＝推断。

**逐跳调用链的正本不在这页**，在 [[NPU调用链]]——那一页收了七跳表、`axi://` 与 `socket://` 两种设备 URL 的成立条件、板上现成的离线推理工具 `icraft-run`、以及若干术语（AIU／Icore／vsync／mmap）。本节只留**板端 A 级取证清单**与**两条公开更正**。

## 十三、conf 门限扫描（D-31 队列第 ② 项，2026-10-04 实测）

**结论先行**：现役 640×352 模型的工作点建议从 `conf: 0.1` 抬到 **0.15～0.20**；960×512 那一版在同样标称 conf 下明显更紧，**两版不能共用一个数**（0.20 时 640 版还有 2.02 框/帧，960 版只剩 0.85）。

**测的是什么**：`conf` 在 DetPost 开着的路径上同时干两件事（见 12.3），所以扫出来的是硬件门限与 CPU 乘积分两级串联的合力，不是硬件单级。

**回写公式**（`et_device.hpp:653-664 calculate_scale`）：`scale = ln(1/conf_new − 1) / ln(1/conf_orig − 1)`，再 `data_thr[i] *= scale` 截断取整。对 640×352（`thr_f=0.1`、`data_thr=[-15,-18,-19]`）算出的对照表：

|---|---|---|---|---|---|---|---|---|---|

| data_thr | −20／−24／−25 | −15／−18／−19 | −11／−14／−14 | −9／−11／−11 | −5／−6／−7 | −2／−3／−3 | 0／0／0 | ＋2／＋3／＋3 | ＋5／＋6／＋7 |

|  syscall | 次数 |
|---|---|

**结论（A）**：推理循环到达 NPU 靠的是**长期映射的指针解引用**，一次系统调用都不做。udmabuf 的那 8 个 cache-sync 节点在启动时打开后就一直握着，之后靠 `write()` 到已开 fd 完成（`sync_*` 走的是 fd 不是路径，所以 trace 里只剩 `openat` 也看不见它们）。这正是 [[NPU调用链#一、TL;DR|NPU调用链——TL;DR]] 那句"Linux 侧查不到它"的运行时版：**内核不是在推理路径上，只在建立路径上**。

**启动期 open/mmap 序列**（A，从 `/tmp/strace_demo.txt` 读，顺序即时间顺序）：

| 步 | syscall 原文要点 | 补齐了什么 |
|---|---|---|
| 1 | 读 yaml，再 `openat("names/coco.names")` | — |
| 2 | `openat("/usr/lib/aarch64-linux-gnu/libaxizg330aiu.so")` | **运行时按 URL host 加载**这件事的直接证据（[[NPU调用链#二、执行 YOLO 的七跳|第 2 跳]]） |
| 3 | 8 次 `openat("/sys/class/u-dma-buf/udmabuf0/{phys_addr,size,sync_mode,sync_direction,sync_offset,sync_size,sync_for_device,sync_for_cpu}")`，**开着不关** | udmabuf 的 cache 同步面 |
| 4 | `openat("/dev/udmabuf0", O_RDWR) = 7` → `mmap(NULL, 134217728, PROT_READ\|PROT_WRITE, MAP_SHARED, 7, 0)` | **PS DDR DMA 窗口＝128 MiB**（原为 C） |
| 5 | `openat("/dev/mem", O_RDWR\|O_SYNC) = 8` → `mmap(NULL, 16777216, …, 8, 0x40000000)`、`mmap(NULL, 16777216, …, 8, 0x80000000)` | **寄存器面与 DMA 面各 16 MiB**（原为 C） |

**全程 `ioctl` 只有 `TCGETS`**（终端属性探测）→ `ENOTTY`。也就是说 `libaxizg330aiu.so` **不用 ioctl 走控制面，全靠 mmap 后的读写**，所以内核里既没有 NPU 驱动、`/proc/iomem` 里也没有它的 claim。

**剩下的唯一空白**（C，仍未取证）：取帧那步地址 `>>3` 是否对应"512 bit 总线＝64 字节一拍"。这一条 syscall 层永远看不到——它是一次 MMIO 写，落在已映射窗口内部；要它只有两个入口，gdb 断在写寄存器处，或者拿到 linlon-v5／AIU 的寄存器手册。

**strace 的能力边界要写清楚**：它只看 syscall 面。**寄存器写了什么值、DMA 描述的是哪段地址，在 trace 里永远不出现**（都在 mmap 之后的用户态读写里）。所以"抓到了 open/mmap 序列"不等于"看清了调用链"，前者是入口证据，后者仍需插桩或 gdb。

### 15.4c 码率控制项收得下、但不生效（A）

`vpu::Encoder` 的 `fd_` 是 protected，我用派生类在自己的 fd 上发 `VIDIOC_S_CTRL`（`/root/vpu/vpu_br`）：

| 动作 | 结果 |
|---|---|
| `set(video_bitrate=0x9909cf, 2000000)` | `rc=0 errno=0`，回读 **2000000** |
| `set(0x00992008, 2000000)`（Codec 类） | `rc=0`，回读 2000000 —— ⚠ **这一条当初记成"私有类同名 `video_bitrate`"，按 15.2 的全清单它其实是 `internal_buffer_size`**，等于第二、三行是在设内部缓冲大小，不是第二个码率旋钮 |
| `VIDIOC_S_EXT_CTRLS`（class `0x00990000`）设 `0x992008` | `rc=0` |
| 设 0 | 标准 ID 被夹到 min=1000，`0x992008` 收 0 |
| 但 **0 / 2M / 8M 三次的码流 md5 全等**（60 帧 55,756 B） | **码率没变** |

`frame_rate` 也一样：设 30 与设 60 的码流逐字节相同。所以出厂这条路上**率控实际不起作用**，输出比特数只由内容与默认 QP 决定（实测 720p 平均 942 B/帧、1080p 1,506 B/帧）。

**机制判到哪一层**：V4L2 里"设 `video_bitrate`"只是写目标值，要不要按它来编是由**码率模式开关**决定的——标准开关是 `V4L2_CID_MPEG_VIDEO_BITRATE_MODE`（0x009909cc），而 15.2 的 66 条清单里**没有这个 ID**（A）。这颗驱动另给了 `frame_level_rate_control_enable`（bool，**default 0**）与四条同名 `bitrate_control_mode`（0x0099201b–1e，**default 0**）。**判到 B**：码率环没被任何默认值打开，所以 `video_bitrate` 写进去没人读。**当时判到 C 的那一项（把 `frame_level_rate_control_enable=1` 或某个 `bitrate_control_mode` 设上去是否真能生效）已在 15.9 做完，答案是"不能"**（A）。

顺带一条 A 级源码证据：厂商 `VPUEncoderConfig` 里的 `bitrate = 4000000` **只出现在结构体定义和日志打印**（`vpu_encoder_actor.hpp:32/50/63`），`vpu.h` 里唯一的 `VIDIOC_S_CTRL` 是 `V4L2_CID_MVE_VIDEO_FRAME_RATE`（`vpu.h:682-689`）。**所有示例里的 4 Mbps 对 VPU 路都是死配置**，`stream2rtmp.hpp` 那个 8 Mbps 是软件 `AVCodecContext` 那条路，跟硬编无关。

### 15.4d `MMU ABORT`：跟着 `buffer_count` 走，不跟着喂帧速度走（A）

`dmesg` 累计 9 条 `MVX session: … Firmware rsp: Error. code=0, message=V5/V7-H264ENC: MMU ABORT. (mvx_session.c:2120)`（HEVC 同理），表现是 `DQBUF` 返 `errno=5(EIO)`。我先怀疑"生产者不限速撞了 buffer 回收"，**这条被我自己的复测否掉**：不限速连跑 3 次 150 帧全成。当时的中止点全部落在 `frames_fed ≈ buffer_count + 2…7`，且 `buffers=8/12/16` 三轮**都在 12/15/23 帧处中止**，而 `buffers=6`（厂商默认）在限速与不限速下都跑满。另有一次更早的 `mvx_mmu_alloc_contiguous_pages → map_protocol_v2 → mvx_fw_cache_get → streamon` 分配失败栈，发生在 `/dev/shm` 占着 207 MB、空闲约 180 MB 的窗口。**判到 B**：触发条件是"该会话要的连续/DMA 内存拿不到"，`buffer_count` 放大它、低空闲内存放大它；**判到 C**：为什么 `>6` 就一定失败（驱动的 DPB/内部缓冲按 `buffer_count` 怎么算，没取到）。用法上的结论是硬的：**`buffer_count` 保持 6，别在 `/dev/shm` 堆裸帧**。

### 15.6 决定与边界（15.4b 更正后重写）

- **硬编这条路是通的**，D-31 ③ 的退路条件**没有成立**，初稿那句"直播不交硬编"作废。但要分清两件事：编码本身可用（A），**"把现役直播换成 H.264＋RTSP"还没有做**——现役是软件 JPEG（10-05 晚为 OBS 改成 960×540／q60／10 fps，见 18.1），换过去要新增 RTSP 服务端（见 15.7）与一个真能生效的率控（**15.9 已判定用户态打不开**：缺的是 `bitrate_mode`（0x009909cc）这个选择项本身，`VIDIOC_QUERYCTRL` 对它直接 EINVAL）。

- 未取证（C）：`buffer_count>6` 必然中止的驱动内部原因；`frame_rate` 默认值 1966080 的换算口径（看着像 30 fps×65536 的定点数，`setFrameRate` 就是 `fps<<16`，已印证但未验证它影响码流）；`M264` 与 `AVC1`/`H264` 的实际差别；`JPEG`／`VP80`/`VP90` 三条硬编没实跑（只实跑了 H.264 与 HEVC，见 15.2 与 15.8）。**原来挂着的两项已在 15.8／15.9 关闭**：硬编 CPU 占用（A）、率控组合实验（A）。

### 15.8 硬编的 CPU 成本（A，2026-10-05 21:12–21:16 UTC，直播链停掉的干净窗口）

先记一条**我自己踩的坑**：第一次测（21:12 UTC 前）把 `nv12_720.raw` 直接放在 rootfs 上读，同一命令 720p 只跑出 **17.7 fps**（`enqueue_wall_ms=8992`），1080p 只有 **7.8 fps**——那不是编码慢，是 **eMMC 顺序读 ≈23 MB/s 卡住了喂帧线程**（207 MB／8.99 s 与 466 MB／20.06 s 都正好落在 23 MB/s）。当时 `dmesg` 无事件、`ps` 里也没有别的重负载（`top` 97 % idle），所以我差点把这条记成"VPU 掉了两个数量级"。**源放 `/dev/shm` 之后数字回到 15.2/15.4b 记的量级**，之前那批 tmpfs 读数是有效的，不用更正。取样器 `cpu_run.py`（每 0.02–0.05 s 读 `/proc/<pid>/stat` 的 utime+stime），驱动脚本 `board-vpu-cpu2.py`。

| 档位（H.264 除注明外） | 稳态 fps | 每帧 CPU | 平均单核占用 | 峰值单核 |
|---|---|---|---|---|
| 720p 不限速，150 帧 | **255.5** | 6.6 ms（1.00 CPU-s/150 帧） | **101.6 %** | 189 % |
| 720p 限速 30 | 31.6 | 4.0 ms | 11.7 % | 73 % |
| 720p H.265 限速 30 | 31.8 | 3.8 ms | 11.4 % | 39 % |
| 1080p 不限速，60 帧 | **119.1** | 10.0 ms（0.61 CPU-s/61 帧） | **89.4 %** | 143 % |
| 1080p 限速 30 | 33.7 | 7.4 ms | 21.5 % | 59 % |
| 1080p 限速 15 | 16.8 | 7.4 ms | 11.0 % | 59 % |

三条判读：

1. **"硬编吃不吃 CPU"的答案是：吃搬运，不吃计算。** 每帧 CPU 时间基本就是 NV12 那 1.4 MB（720p）／3.1 MB（1080p）的用户态 memcpy ＋ QBUF/DQBUF 系统调用；不限速时**一个核被打满**（89–102 %，峰值 143–189 % 说明还有第二个线程在跑 writer），所以 255／119 fps 这两个"上限"量的是 **CPU 复制带宽，不是 VPU 的编码上限**——之前把它们当 VPU 天花板写，这一层口径在 15.2 与外设页第一节都已改成"搬运天花板"。
2. **实时档非常省**：1080p@30 只占 **21.5 % 单核**，15 fps 只占 11 %。对比 15.5 的现役软 JPEG（1080p q80 单帧 **67.9 ms**＝10 fps 要吃 68 % 单核）⇒ **同分辨率同帧率，硬编省约 3 倍 CPU，而且出的是标准 H.264 Annex-B**，不是 MJPEG。
3. 想再往下压只剩两条：**都没测，而且第一条现在查到有硬约束**。（a）让 PL 直接出 `UYVY`（省掉 CPU 转色，15.2 已确认喂帧侧收 `UYVY`）——**但位流里"PS 缓冲区出 UYVY"和"关 HDMI"是同一个 bit**：`sdicamera.hpp:219-222` 的 `camera_fmt::YUV422` 分支往 `base+0x78` 写 1，而 `frame_ctrl.v:865-866` 把 `9'h078` 的 bit0 译码成 `disable_hdmi`，`:877 assign display_en = ~disable_hdmi_2;`，`frame_to_ps_largebuf.v:331-332` 又用同一个 `display_en` 在"写 RGB565 打包"与"写 `rgb888_2_yuv422` 出来的 UYVY"之间二选一（A：逐行读的 RTL，10-15）。⇒ 要走 UYVY 就得接受显示面关闭，并且**给 NPU 的那一路读的是同一块 PS 缓冲，格式会跟着一起变**。（b）零拷贝（`VIDIOC_EXPBUF`／dmabuf，厂商 API 未暴露）。

顺带把 15.2 的"实跑过哪几条"补实：同窗口用 `s15_720.raw` 各编 15 帧拉回 PC，`ffprobe` 认 **H.264 Main 1280×720 yuv420p**（17,161 B）与 **HEVC Main 1280×720 yuv420p**（16,862 B）⇒ 硬编实跑到流级验证的是这两条；`JPEG`／`VP80`／`VP90` 只在驱动声明里，没实跑（C）。

### 15.9 率控定案：用户态打不开 RC 环（A，决定性实验）

15.4c 留下的唯一实测项是"把开关设上去到底生不生效"。把 `vpu_br` 改成通用控制注入器（`id=value` 列表，每个 id 先 `QUERYCTRL` 打印驱动侧 min/max/step/default，再 `S_CTRL`＋`S_EXT_CTRLS` 两路都设、`G_CTRL` 回读，跑完再回读一次），17 组组合（底稿 `vpu-bench/rc_matrix_2026-10-05.txt`、`rc_matrix2_2026-10-05.txt`），统一条件＝720p、60 帧、`fps=30`、`buffers=6`、源在 `/dev/shm`：

| 组 | 设了什么 | 码流 | 判定 |
|---|---|---|---|
| `none2` | 什么都不设（基线） | **55,756 B**，md5 `53a23224aea7…` | 基线 |
| `frcon_br10k` | `video_bitrate=10000` ＋ `frame_level_rate_control_enable=1` | **55,756 B，md5 与基线全等** | 目标是实际的 **1/22**，输出一点没缩 ⇒ **RC 根本没参与编码**（这是决定性那一行） |
| `br50k`／`br400k`／`frcon_br1200k` | 只设 `video_bitrate`（另含 1 组带开关）三档 | 同上，md5 全等 | 同上 |
| `frcon` | 只开 `frame_level_rate_control_enable` | 同上 | 开关本身不改变输出 |
| `hrd_br50k` | ＋`hrd_buffer_size`／`bandwidth_limit`=50000 | 同上 | 无效 |
| `cq80` | `compression_quality=80` | 同上 | 无效 |
| `idr15` | `restart_interval=15` ＋ `gop_type=1` | 同上 | **连 IDR 间隔／GOP 结构都不可控**（对直播是坏消息：没法强制插关键帧） |
| `bcm_400k`／`frcon_brcq_br50k` | 四条同名 `bitrate_control_mode`（`0x0099201b–1e`）设 400000／50000 | **55,769 B（+13）／55,772 B（+16）**，md5 变、**码率仍是 222 kbps** | 唯一有反应的一组：这几个值**被写进了码流参数集**（VUI 一类），但没进 RC 环 |

**定案（A）**：这些控制全都"设得进、回读得到"（`rc=0 errno=0`），但对输出比特数的影响是 0 或 13 字节级——**用户态没有任何路径能打开码率环**。根因在 15.2 已定位、本轮再确认一次：这颗驱动**没有 `V4L2_CID_MPEG_VIDEO_BITRATE_MODE`（0x009909cc）**，也就是没有"选 CBR/VBR/CQP"的开关，`video_bitrate` 写进去没有消费者。**"直播不许挤掉 SSH"这条硬约束因此无法满足＝带宽只能靠"实测该场景是多少"来估，不能定量**。

附带三条操作级发现（A）：

1. **流已经开始之后再设 codec 类控制会把会话打死**：喂 8 帧后设 `0x0099201b` → `EINVAL`，紧接着两侧队列一起 `EIO`，150 帧只出 2 帧。控制必须在构造完 `vpu::Encoder`、喂第一帧之前全部设完。
2. `S_EXT_CTRLS` 用 `ctrl_class=0x00990000` 时，`0x009d0900` 那批（`compression_quality`、`restart_interval`）报 `EINVAL`，只有 `S_CTRL` 能设——**类码要按 ID 区间选**。
3. 基线那一行（`none`）第一次跑出来是 **0 字节**、6 帧后 `EIO`；紧接重跑（`none2`）完全正常。**判因＝上一次会话释放与本次 streamon 撞车**（C，没抓 dmesg 对齐），不是"不设控制就会失败"——这条别读成后者。
4. **码流只由参数决定，与哪个探针跑的无关**（A，收尾交叉复现）：同一素材（15 帧 720p）同一参数（`30 6`），`vpu_probe`（#43）与 `vpu_br`（#44）各编一遍，两者输出与盘上存档的 `v_h264.bit` **三个 md5 全等** `131bfc4b77e5a2c326e8351875a3c5c0`；HEVC 那份同样与 #44 重跑结果相等（`1f10f4df4e207483708aa9654497ebb1`，16,862 B）。⇒ 以后要比"改了某个控制有没有用"，**直接比 md5 就够了**，不需要再引入"同一二进制"这个前提。

## 十七、"能不能把设备树改成 FMQL30TAI"——板上实测（2026-10-05）

**问题来源**：用户 2026-10-05 提问。这一节只给读数与由此得出的"改了有没有人看"，不给排期。

### 17.1 那串型号从哪来、到哪儿去（全部 A 级，2026-10-05 板上 SSH 实测）

| 项 | 读数 | 含义 |
|---|---|---|
| `/proc/device-tree/model` | `FMQLMP FMQL100TAI` | 与出厂镜像一致，未变 |
| `/proc/device-tree/compatible` | `fmsh,fmsh-fmqlmp` | **不含 100TAI／30TAI 字样**，是芯片族名，不区分子型号 |
| 顶层节点 | 共 15 个：`amba-apu@0`、`cpus`、`memory@0`、`udmabuf@0`、`chosen`、`timer`、`psci`、`dcc`、`idle-states`、`aliases`、`name` 等 | **没有 `amba_pl`** |
| DT 内 AIU／NPU 相关节点 | `find /proc/device-tree -maxdepth 4 \| grep -icE 'aiu\|npu'` ＝ **0** | **设备树里根本没有描述那颗 NPU** |
| 反编译源 `board_extract/29_dts_fmqlmp-verify.dts`（1,038 行） | 第 728 行是 **`/*amba_pl {`** —— PL 那一段是**被注释掉的** | "DT 无 PL 节点"不是缺件，是出厂 dts 主动注掉的 |
| NPU 栈是否读 DT | `strings -a` 查 `device.tree\|libfdt\|sys/firmware`：`libicraft_xrt`＝**0**、`libicraft_zg330backend`＝**0**、`libicraft_hostbackend`＝**0**、`libaxizg330aiu`＝**0**、`/usr/bin/icraft-run`＝**0** | **整条 NPU 调用链不碰设备树**（归属由设备 URL＋加载哪颗 `.so` 定，与 [[NPU调用链]]、D-30 判据同一条） |
| 板上还有谁读 `/proc/device-tree` | `grep -rl` 命中只有 `systemd-networkd`、`libsystemd-shared-245.so`、`/usr/bin/lscpu` | 三个都与 NPU 无关；DT 的 `model` 串**零消费者**（本次检索口径：`/etc /usr/lib/systemd /usr/sbin /usr/bin`，**未覆盖全部 `/usr/lib` 与所有二进制**，故此项 B 级） |
| DT 被非 NPU 驱动读的例子 | `dmesg`：`mali f0000000.mali_gpu: Using coherency mode 31 set from dtb` | 说明 DT **确实**在被 GPU 一类驱动用——改树的影响面不在 NPU，在外设与启动 |

### 17.2 换 dtb 的技术路径（比原判容易，但没人需要它）

启动分区是**普通 vfat**（`/dev/mmcblk0p1`，LABEL＝`FAT`，1 G，板端 `mount -o ro` 可直接读），里面 8 个文件：`BOOT.bin`、`FSBL251210_ddr400_demo.out`、`Image`（13,158,408 B）、`bl31.elf`、`u-boot`（6,579,840 B）、`ai7030_top.bit`、`ai7030_top_disable_icap.bit`、**`fmqlmp-verify.dtb`（15,996 B，magic `d0 0d fe ed`）**、`uEnv.txt`。

`uEnv.txt` 原文两行决定一切：

- `uenvcmd=mmc rescan && fatload mmc 0:1 0x10080000 Image && fatload mmc 0:1 0x11000000 fmqlmp-verify.dtb && booti 0x10080000 - 0x11000000`
- `bootcmd=run loadbit; run uenvcmd`，`bootdelay=3`，`bootargs=... clk_ignore_unused mem=1024M`

**所以"换设备树"＝往这块 FAT 分区写一个文件再重启**，不需要重烧 QSPI（`/proc/mtd`：`mtd0 bootloader 4M`／`mtd1 kernel 16M`／`mtd2 rootfs size=0`）。**但没有可换的东西**：本地全部资料（`fdw/` 全树＋`board_extract/`）里只有这一颗 dtb 和它的反编译源，**不存在 30TAI 形状的 dtb/dts**；自己编要先补 `dtc`——本机与 `fpai-ub2004` 容器**都没有 `dtc`/`fdtdump`**（A 级实测）。

### 17.3 顺手关掉一条挂着"强推断"的旧项

第二节"板子身份实测表"里曾记：`loadbit` **很可能空转**（FAT 里没有 `download.bit`，且它读的是 `mmc 0:2`＝ext4 根分区），并要求"到板 `printenv`＋`dmesg` 过滤 fpga 复核"。**本轮复核结果＝成立**：

- `find / -maxdepth 3 -name download.bit` 在根分区**零命中**，`/`、`/root`、`/boot` 三处显式检查都不存在，FAT 清单里也没有 → **两条分区都没有 `download.bit`，这行必然失败**；U-Boot 用 `;` 串联，失败不中断启动，所以没人报错。
- PL 是 **BOOT.bin 配好的**：`dmesg` 有 `fpga_manager fpga0: FMSH FMQL FPGA Manager registered`，`/sys/class/fpga_manager/fpga0/state` ＝ `operating`。
- **更正**：我先前根据 `ls /config` 为空写"configfs 没挂载"——**错**，configfs 的挂载点是 `/sys/kernel/config`，`/config` 只是个无关的空目录。实测见下面 17.3b。
- 内核 `5.4.52`。

### 17.3b 顺带把"运行时设备树覆盖"的两个前提测了（第七节那条开放项）

- **configfs 是活的**：本轮 `mount -t configfs none /sys/kernel/config` 报 `none already mounted or mount point busy`（rc＝32）→ **观测时刻它已经挂着**（是否出厂自挂未核）；`/sys/kernel/config/device-tree/overlays/` **存在且为空**。我为做这个观测 `umount` 过一次，随后已按原状重新挂上（`/proc/mounts` 里有 `none /sys/kernel/config configfs rw,relatime`，A）。
- **`__symbols__` 确实没有**：`ls /proc/device-tree/` 全 15 项里 `grep -c '__symbols__'` ＝ **0** → **overlay 里不能用 `&label` 引用现有节点**，只能"新增节点"或按完整路径改属性。这条把第七节那句"取证件里 `35` 是节选，不能定论"变成板上定论（A）。
- 仍未测：往 `overlays/` 插一个最小 `.dtbo` 能不能生效（要 `dtc`，本机与容器都没有）。

### 17.4 由此得到的口径

1. **不改**。"把 DT 改成 FMQL30TAI"既没有可用的 30TAI dtb，也不改变任何一件事：NPU 归属早由设备 URL／`.so`／现役 ZG 产物定死（D-30），DT 的 `model` 串**没有任何消费者**。
2. 想让外部材料"看起来对"的唯一正路仍然是 **D-30 回退条件 ①**：拿到按板型裁剪的官方 dtb，或 FAE 书面确认贴片芯片。
3. **真要动 DT，动机只剩一个**：把 `amba_pl` 从注释里放出来、让它描述我方下沉进 PL 的 IP（现在 PL 侧全部靠用户态 `mmap /dev/mem`，`/dev/uio*` 不存在）。这条路的第一站是 configfs overlay（前提＝挂 `/config`），不是换出厂 dtb——见 [[板载接口与内核改造收纳进dev]]。
4. **动 DT＝动启动路径**：`console`/`earlycon`/`mem=1024M` 在 `uEnv.txt`，但 uart 时钟与 pinmux 在 dtb 里；写坏的表现可能是**串口也没输出**，恢复只剩"拔卡／重烧镜像"这一条（板子 `root=` 在 mmcblk0p2，FAT 可从 PC 侧读写，所以换回原文件可行——**这是纸面推演，未实测**，B 级）。

### 18.4 由此得到的三条口径

1. **指标口径已定**：交付对外只报这一组数（int8＋官方 9 张校准集＋`conf 0.1`），换门限或换校准集必须重跑并改本节。
2. **小目标不是量化掉的**：`AP small` 0.148 对 `AP large` 0.483（差 3.3 倍），对应的是**长边 640 的等比缩放＋补边**——原图缩到长边 640 之后，32 px 以下的人本来就没了。这一格是**输入分辨率的天花板**，与量化算法无关（推理见上表，未做消融，B 级）。
3. **缺一个 float 基线**：现在只有"量化版 0.331"这一个数，没有"同一份权重不量化是多少"。本地已有 `2_compile/fmodel/yolov8n_640x640.pt` ＋ torch 2.10 ＋ onnxruntime 1.24，但要得出**严格可比**的那个数，得把前处理（`Resize(LONG_SIDE)+rPad`）、DFL 解码、NMS 门限逐项对齐到板上这份 demo，不是改个配置就能算完的——已列为决策项，见 [[状态源与决策记录]]。

### 18.5 喂进 NPU 的那张图到底长什么样（代码直证，A 级，2026-10-05）

`3_deploy/BYZG/src/yolov8n.cpp:108-112` 就三行：

```
PicPre img(img_path, cv::IMREAD_COLOR);
img.Resize({netinfo.i_cubic[0].h, netinfo.i_cubic[0].w}, PicPre::LONG_SIDE).rPad();
Tensor img_tensor = CvMat2Tensor(img.dst_img, network);
```

- **目标尺寸不是写死的 640**，是从模型自己的输入 shape 取的（`i_cubic`＝`Yolov8n_ZG.json` 里那个 `[1, 640, 640, 3]`）。编多大的模型就喂多大的图，这条链上没有第二个尺寸。
- **`LONG_SIDE` ＝ 等比缩放**：`PicPre.hpp:150` 的实现是 `ratio = min(ratio_w, ratio_h)`，把**最长边**缩到 640，短边按比例走。
- **`rPad()` 是补边不是拉伸**：`PicPre.hpp:217`，默认 `PadModes::BR`，`copyMakeBorder(..., cv::Scalar(114,114,114))` 只在**下、右**补到 640×640，`_pad_info={0,0}`（框回映射按"右下补边"这一约定算）。
- **像素是 uint8 直接进图，不做 `/255`**：输入张量 `element_dtype=@uint(8)`，图里第一个 `CastNode` 的量化 scale 是 `3*2.007629`（≈255/127）＝归一化被烤进了计算图。与 toml 的 `inputs_dtype="UINT8"`／`pre_scale=[255,255,255]`／`pre_mean=[0,0,0]`／`image_channel_order="rgb"` 四处一致。
- **公开更正**：本条上一版把这里写成"640×640 硬缩放"，措辞错——实际是**等比缩放＋灰边补全（letterbox），画面比例不变形**。18.4 第 2 条的结论方向不变（小目标照样在缩放里丢像素），但丢的方式是"整幅等比缩小"，不是"压扁"。

### 18.6 "能不能和直播一样高清"这个问题里的误会，以及两条路各自的上限

**误会先拆掉**：直播那条链**自己也没把高清给 NPU**。`/tmp/live.stat` 里 `out=1920x1080` 是**编码推流那一路**的尺寸；AI 那一路用的是 `configs/ZG/sdicamera+yolov5+hdmi.yaml` 里的 `net_w: 640`／`net_h: 352`（厂商默认）或我方实验版的 960×512。一次采集、两路各自缩放，互不相干。

| 路线 | 现在喂进 NPU 的 | 谁在做缩放 | 能不能更清晰 |
|---|---|---|---|
| **PSIN**（本次评测，读图文件） | 长边 640 的 letterbox，640×640 uint8 | **CPU 的 `cv::resize`** | 尺寸在**编译时**就烤进计算图（119 个 HardOp 的 shape 全按它算），运行时改不了；要改只能**另编一个输入尺寸的模型**。官方现成给了 `fmodel/yolov8n_512x960.pt` |
| **PLIN**（直播那条） | 厂商默认 **640×352**；我方实验 **960×512** | **PL 硬缩放**，`RATIO=CAM/NET` **只认整数步长**（B 级，`et_device.hpp` 的 `preprocess_plin`） | 能，但只能整倍走：1080p 想再翻一档清晰就是 RATIO＝1＝1920×1080 整幅进 NPU，算力不答应。**1280×720 在这条路上根本走不通**（`1920/1280＝1.5` 非整数） |

**算力的账（实测与外推分开）**

- **已实测（A 级，第十一节，yolov5s／PLIN）**：640×352 → 960×512，计算量 2.18×，NPU 单帧 icore 中位 **7.06 → 13.24 ms（1.88×）**——大图把固定开销摊薄了，涨得比面积慢。
- **本次 yolov8n 640×640＝12.416 ms**（A 级）。按同一"面积≈线性"量级**外推**（**B 级，未测**）：960×512≈15 ms、1280×720≈28 ms、1920×1080≈63 ms → 约 66／35／16 fps。
- **直播链还有一层被忽略的抽样**：`RATIO_H=1080/352＝3` ⇒ AI 图上 1 像素≈原图 3 像素，**不是"取了全图再缩"**，是硬件按步长隔点取（C 级，我方通路推的）。960×512 那版是 RATIO＝2。

**"YOLO 不能用高清吗"——能，但不是无脑加大输入**

1. 检测器的敏感单位是"目标在输入图里占多少像素"，`AP small`／`AP large` 差 3.3 倍就是这条的直接后果。
2. 加大输入是**全图每个目标一起放大**，算力按面积涨。只为看清远处几个小目标时，**切片**（把 1080p 切成几块各按 640 跑再拼回）比整图放大划算，但 NPU 上没有 batch 免费午餐——**几块就是几帧延迟**（12.4 ms × 块数）。
3. 官方给的第三条腿是**换档而不是拉高清**：`512×960` 的 `.pt` 已在库里，且 960×512 正好让 1080p 走 RATIO＝2（与 PLIN 实验版同形）。改 toml 两行即可（`network` 与 `inputs`），**但 `jr_path` 指向 `../3_deploy/imodel/ZG/int8/`＝会把本次基线那五段产物原地覆盖**，所以要么先备份那个目录，要么改 `net_name` 另开一个输出目录。

### 19.1 链路形状（代码直证，A）

一次采集，两路并行，互不影响（JPEG 那路仍在，靠 `HDMI_LIVE_EVERY=0` 关掉）：

```
显示 actor loop()  每 HDMI_H264_EVERY 帧抽 1
  → 单槽 mailbox（std::vector<uint8_t> stage ＋ ready/quit/cv；不排队，来不及就计 drops）
  → 泵线程：RGB565 → BGR → I420 → 手拼 NV12（Cb/Cr 交错）
  → vpu::Encoder("/dev/video0", h, w, OUTPUT_MPLANE/NV12, CAPTURE/H264, buffers)
  → 写线程 getOutput()：按 IDR 边界切段（Annex-B 起始码＋NAL type 5/7）
      seg<seq>.part → 写完落 seg<seq>.info(frames=/unix=) → rename 成 seg<seq>.h264
      每个 closeSeg 后重写 state（心跳）
  → h264d.py（板端 python）：只认已 rename 的 .h264，喂 ffmpeg
      -f h264 -framerate 30 -i … -c copy -output_ts_offset <累计秒> -f mpegts seg<seq>.ts
      滚动写 index.m3u8（保留 6 段）
  → mjpeg_server.py 新增 /h264/ 静态路由（m3u8→application/vnd.apple.mpegurl，ts→video/mp2t）
```

三条设计约束（都是前面几节踩出来的，别再改回去）：
- **必须 `-framerate 30`**：裸 Annex-B 解出来 `avg_frame_rate` 默认 25/1，不指定就播成 0.83 倍速（A，第十五节）。
- **必须 `-output_ts_offset` 累计**：否则每段 PCR 都从 0 起，HLS 段间时间戳回跳，播放器会卡或重缓冲（A，10-08 本地 6 段拼接实测跨段 PTS 单调、无跳变，见 19.9）。
- **必须 `.part`→rename**：读取侧看到的永远是完整文件，这条与 JPEG 路的 `live.jpg` 同一套做法（A）。

### 19.2 五个旋钮（全在 #1 的显示 actor 里，env 传入）

### 19.4 CPU 与内核读数

- **纯硬编那一路的 CPU 成本仍以第十五节为准：1080p@30 单核 21.5 %**（A）。这一路 CPU 只干三件事：把 RGB565 转成 NV12（板载实测 1080p ≈ **14.9 ms/帧**）、把裸帧 `memcpy` 进驱动队列、把输出缓冲写盘——**像素搬运是 CPU 的，压缩不是**。
- **并发窗口里 demo 出现过 `%CPU 100.0`**（B：当轮 env 组合没留档，不能断定是 JPEG＋H264 双流还是别的）。有一个核被打满是事实，**归因未核**，别写成"硬编把 CPU 吃满了"。
- **`cv::resize` 在 1080p 是 ≈52 ms/帧**，所以**硬编侧永远编原生 1080p、缩放交给 OBS**，绝不在泵里做缩放（A，第十五节）。
- **`dmesg` 行数在所有轮次之间恒为 521**（A）：没有新增 `MMU ABORT`、没有 OOM、没有新的 MVX 报错 ⇒ 这条链**没有触碰内核态红线**，稳定性问题是用户态会话级的。

### 19.5 一种已经复现的失败模式（本节唯一未闭合项）

某轮 VTC：会话起来了、`session up` 与 `streamon` 都正常、**编出 6 帧之后**写线程抛异常，栈停在 `vpu.h:950`（capture 侧 `VIDIOC_DQBUF` 失败 → `Failed to dequeue output buffer`）紧接 `vpu.h:1001`（input 侧 DQBUF）。**演示程序活下来了**，泵自己退出了。

- **errno 没拿到**（A 级成因）：`vpu.h` 的异常串是多行的（`in File:… Line:… \n Failed to dequeue output buffer, errno=…`），而 `spdlog::warn("{}", e.what())` 只打第一行 ⇒ **最关键的那个 `errno=` 落在日志尾巴以外**。10-08 已修：加 `flat()` 把 `\n`/`\r` 压成空格，整条异常一行打完。
- **判因＝C，且不能排除外部因素**：当轮另一条会话正在同一块 `/dev/video0` 上跑 VPU 工具（十五节的探针也是同一个设备节点）。**"两路会话抢一个 M2M 节点"是我怀疑的头号原因，没有证据**。
- **补硬之后（10-08 本地，代码直证 A）**：任何 VPU 侧异常都走 `killPump()`——置 `dead`、置 `quit`、唤醒主循环 ⇒ 主循环立刻停止 `enqueueDataPtr`，随后 `streamOff()`＋`join` 写线程＋删掉未完成的 `.part`＋`delete enc`。**泵不可能再把异常抛出线程外**（未捕获 C++ 异常会 SIGABRT 整个 demo，第十八节那条 op 685 就是这么把直播带走的）。`streamon` 等待加了 20 s 超时，超时同样 `killPump("capture queue never started")`；三处 `cannot open` 也一律走 `killPump`，不再无限重试刷日志。

### 19.6 明确没测的三件事（要上板才能结）

| 项 | 读数 |
|---|---|
| 输入 | 9 段，每段 **23,912 B**（段间字节数相同是预期：每次 ffmpeg 都从 `testsrc` 第 0 帧起算，内容一致） |
| 窗口 | `www` 里剩 `ts=[3,4,5,6,7,8]`，seg0–2 被 `KEEP=6` 滚掉；TS **32,900 B／段**（720p 合成图） |
| 播放列表 | `#EXT-X-VERSION:3`／`TARGETDURATION:2`／`MEDIA-SEQUENCE:3` ＋ 6 条 `#EXTINF:1.000,` |
| ffprobe 解列表 | **rc=0、无 stderr** |
| 解码帧数 | **180 ＝ 6 × 30**，一段不差 |
| PTS | `4.4 → 10.366656`，**span 5.967 s**，**单调**，相邻差为负或 >0.08 s 者 **0 个** ⇒ 跨 6 次段拼接时间戳连续 |
| IDR | **6／180**，恰好每段 1 个关键帧 ⇒ 段边界＝随机访问点（这是"中途加入"的前提，OBS 本身仍判 B，没真开过） |
| 打包耗时 | `seg0 remux_ms=142`（本机 x86 数，**不能当板端数**，板端仍取 507–680 ms） |
| 首帧偏移 | 窗口起点 `pts_time=4.4` 而不是 `3.0`：存在 **+1.4 s 常数偏移**，跨段不变（B：机制未查，播放器按流自身 `start_time` 处理，未见影响） |

**新硬约束（现象 A／机制 B）**：第一轮没加 `-bf 0` 时 **9 段全部 remux 失败**，ffmpeg rc=3199971767，报错固定是

```
[mpegts @ 000001b6acd6a680] first pts and dts value must be set
[vost#0:0/copy @ 000001b6acd98b40] Error submitting a packet to the muxer: Invalid data found when processing input
```

`www` 里 **0 个 `.ts`**、没有 `index.m3u8`。判语三条：

1. `-c copy` 不做重排，muxer 要求每个包都带 DTS；libx264 默认 3 个 B 帧时包按解码序到达，而裸 Annex-B 不携带这层信息。**机制解释判 B**，"带 B 帧的输入会让打包全灭"这个现象判 **A**（同式复现两次，加 `-bf 0` 后全部通过）。
2. **板端 VPU 码流走的是完全同一条命令并且成功**（19.3 的 39,104–45,120 B／段）⇒ 反证 **VPU 输出不带 B 帧、DTS 可用**（B：没有逐 NAL 数过）。
3. **失败是闭合的**：`h264d.py` 对 remux 失败的处理是删 `out/raw/info` 三个文件、`fails+=1`、继续下一段，不崩也不堵。⇒ 以后若换成会出 B 帧的编码器，症状是**"直播没画面但所有进程都在"**，判据只有一条：**数 `/dev/shm/h264www` 里 `.ts` 是不是 0**。

**工具坑（A，本机）**：**`ffprobe -i index.m3u8` 对没有 `#EXT-X-ENDLIST` 的滚动列表不会自己结束**，它会持续等下一段——我这一轮先挂了 45 s 无输出，才改成"停泵 → 把同一份列表复制成 `index_static.m3u8` 并补 `#EXT-X-ENDLIST` → probe 副本"。对 OBS 这不是缺陷（它要的正是一直跟着列表走），但**别拿 ffprobe 当"能不能播"的判据**。

**未闭合**：本节只结"打包产物结构正确＋跨段时间戳连续"，**19.6 的三项一项都没动**（真实场景码率／OBS 实开／长会话）。临时树 `S:\apps\llm\agentwork\h264-local\` 留着可复跑，不占板子资源。
