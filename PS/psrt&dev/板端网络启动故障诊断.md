# 板端网络启动故障诊断

> **本页回答**：113（FMQL30TAI 悟净）开机联网"**先 DHCP 成功却不通**／**开机网络抽签**"的根因、journal 实证、修法，以及 ICS 场景为什么不是免疫。
> **本页不回答**：OS 层改动的逐项归口在 [[os#七、我方对板端 OS 的改动（归口，2026-10-11 起）|os——七、我方对板端 OS 的改动（归口）]]；出厂镜像的完整取证在 [[板卡镜像实测取证]]；我方改写 rc.local 的操作背景在 [[板端我方代码与产物台账]] #204～#207。
> 结论以板上 `journalctl` 实读为准；页内日志摘录都是板上原文，出处见正文。

## 一、现象

- 开机后板子看似拿到地址，**SSH 却连不上**，或**等很久才通**，或**抽到"坏签"那次直接不通**——直到有人手动 `dhclient -r; dhclient` 才"恢复"。
- 实际上多数时候**网络本来就在起来**，只是慢（跨网段旧租约 INIT-REBOOT 拖时间）；手动重跑反而把已经起来的状态又拆了重建，制造"刚才真坏"的错觉。

## 二、机制（修正版）

`timeout 5 dhclient` 只做一件事：**再起一颗 dhclient、只给它 5 秒**。它**不杀**已在跑的 dhclient（开机日志里它与 ifupdown 那颗**并存**，无 `Killed old client process`），也**不发** DHCPRELEASE（那是 `dhclient -r` 才发的）。真正的坑是：

1. **跨网段旧租约 → INIT-REBOOT**：dhclient 开机第一件事不是 DISCOVER，而是按租约文件里的**旧 IP** 发 `DHCPREQUEST`（INIT-REBOOT）。
   - **路由器**：NAK 很快 → 转 DISCOVER → **4 秒内**拿到新地址（2026-03-13 实测 03:28:14→03:28:18）。
   - **Windows ICS**：对**不认识**的 REQUEST **不回话**（既不 NAK 也不 ACK）→ 卡在 REQUEST 重传（3s、6s…）。
2. **5 秒窗口**：ICS 沉默场景下，5 秒还没轮到 DISCOVER 就被 timeout 杀 → **无地址**。
3. **双 dhclient 并存**：ifupdown 的 dhclient（`/etc/network/interfaces.d/eth0`）与 rc.local 的 `timeout 5 dhclient` 同时起，**各按租约文件 INIT-REBOOT 旧 IP、各用自己的 xid**（2026-03-13 pid 154＋155 都 REQUEST 137.242），加大旧租约重传与混乱；**彼此不杀**。

⇒ 所以"**先破坏再拿不到**"的**结果**能成立（慢／沉默服务器下确实断），但"破坏＝杀旧客户端＋释放租约"的**机制**是错的：`Killed old client process`＋`DHCPRELEASE` 只出现在 **`dhclient -r`**（手动排障那次），不是开机裸 dhclient。

## 三、实证（journal 摘录，板上原文）

- **2026-03-13 03:28:14 —— 跨网段 INIT-REBOOT→NAK，双客户端并存**：
  ```
  03:28:14 dhclient[154]: DHCPREQUEST for 192.168.137.242   ← ifupdown 那颗
  03:28:14 dhclient[155]: DHCPREQUEST for 192.168.137.242   ← rc.local 那颗
  03:28:17 dhclient[155]: DHCPNAK from 192.168.1.1          ← 路由器 NAK 旧 IP
  03:28:17 dhclient[155]: DHCPDISCOVER ... interval 3
  03:28:18 dhclient[155]: bound to 192.168.1.113            ← 4 秒内拿到，网络通
  ```
- **2026-03-13 03:29:13 —— 手动 `dhclient -r; dhclient`，这才是 kill＋release**：
  ```
  03:29:13 dhclient[249]: Killed old client process
  03:29:14 dhclient[249]: DHCPRELEASE of 192.168.1.113
  03:29:14 dhclient[249]: send_packet: Network is unreachable   ← 旧客户端已被 flush，释放包发不出去
  03:29:14 dhclient[265]: DHCPDISCOVER ...
  03:29:15 dhclient[265]: bound to 192.168.1.113
  ```
- **2026-11-04 三次开机（boot 0/-1/-2）**：pid 214/263/155 均**直接 DISCOVER→bound 到 113**，全库检索无 137.242、无 DHCPNAK、无 DHCPRELEASE——清掉旧租约后裸 dhclient 干净拿地址，不再 INIT-REBOOT 卡死。
- **当前 rc.local**（mtime `2026-11-04 00:41:08`）：`timeout 5 dhclient` **已注释**（`#timeout 5 dhclient`）；租约文件＝`192.168.1.113`（`dhcp-lease-time 4294967295`≈无限）。
- **全库 `137.242`／`DHCPNAK` 检索**：只在 2023-04、2024-12、2026-02、2026-03（ICS 场景）出现。

## 四、修法

```sh
sed -i 's/^timeout 5 dhclient/#&/' /etc/rc.local   # 注释掉 5 秒杀手：根治"5s 截断 + 双客户端"
rm -f /var/lib/dhcp/dhclient*.leases                # 清旧租约：跳过 INIT-REBOOT，开机直接 DISCOVER
```

- **换网络环境（ICS↔路由器）后**：清租约必做；`timeout 5 dhclient` 一次注释掉（根治）。
- **当前板子已无问题**：rc.local 已注释、租约已 113、boot 0 干净 DISCOVER→bound。
- **ICS 直连姿势**：`rm -f /var/lib/dhcp/dhclient*.leases; dhclient eth0`（或等 30–60 秒自动 DISCOVER）。

## 五、ICS 是不是不会这样

**不是免疫——ICS 反而是"更糟"的一侧**，区别在对旧租约 REQUEST 的反应：

| 服务器 | 对不认识/不记得的 REQUEST | 结果 |
|---|---|---|
| 路由器 | **NAK（快）** | 快速转 DISCOVER → 4 秒内拿到，通常没事（2026-03-13 即此） |
| Windows ICS | **不回话（沉默）** | 卡在 REQUEST 重传 → 5 秒内到不了 DISCOVER → 被 timeout 杀 → **断** |

- **唯一顺利例外**：板子旧租约就是 ICS 自己给的（`137.242`）**且 ICS 还记得它**（没重启/没忘）→ ICS 直接 **ACK**（2026-03-13 03:07 `DHCPACK of 192.168.137.242 from 192.168.137.1`）。这种情况"不会这样"——不 NAK、不卡，直接续租。
- 一旦旧租约是路由器的（113）、或 ICS 重启忘了 → ICS 沉默 → **比路由器更糟**。**所以插 ICS 前清租约。**

## 六、与 2026-11-07 那条不是一回事
