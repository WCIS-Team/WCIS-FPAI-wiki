# 音频

> **本页回答什么**：这台 USB 音箱麦克风一体机（联想 thinkplus MCP01）向主机暴露了哪些接口与端点参数、ALSA 侧怎么控它、在悟净板上对它做过的每一次测试与读数、以及还没测的缺口。**控件语义与描述符字段所依据的 UAC 1.0 规范原文，逐字摘录在第七节（7.1–7.7），PDF 已入仓。** **所有"这台设备"的事实只在本页记一次**，别页只写判据与链接。
> **本页不回答**：为什么买它、多少钱、还买不买别的 → [[外设与资金申报改成设备信息]]；USB 总线、内核驱动与板子接口 → [[板子（除芯片）]]；系统声音栈与内核内建策略 → [[os]]。

## 一、设备身份

- 枚举：`lsusb` = `17ef:a03b`（Lenovo），`bcdDevice=0.00`，`bcdUSB=1.10` → 这是一台 **USB 1.1 全速**设备；`MaxPower=100mA`、`Device Status=0x0000 (Bus Powered)` → **总线供电，不接外部电源**。
- 描述符字符串（`/sys/kernel/debug/usb/devices`）：`Manufacturer=Lenovo`、`Product=MCP01`、`SerialNumber=ACTIONS-DEV-SN1`；内核日志 `usb 1-1.2: New USB device strings: Mfr=1, Product=2, SerialNumber=3`。序列号里的 ACTIONS 是炬芯的方案自述。
- 硬件构成（拆解报告，非本板实测）：主控 **炬芯 ATS2836**（蓝牙音频 SoC），腔体两侧各一颗通话麦克风，360° 全向拾音、半径 3 米，主控自带通话降噪与回声消除。结论：**双麦 + DSP，不是能输出多通道原始数据的阵列**——本项目不做波束成形，这个差别不影响使用。 ^mcp-ident
- **蓝牙模式在这块板上不可用**：出厂内核 `# CONFIG_BT is not set`，配对与连接一概不可能，**只能走 Type-C 有线**；附带的那根线同时负责供电与传音频。 ^mcp-bt

## 二、接口与端点（设备提供的全部空间）

`lsusb -v` 的 `bNumInterfaces=4`——**这四个接口就是设备的全部**，没有第五个功能面。 ^mcp-ifaces

| 功能面 | 接口 / 端点 | 本板落点 | 可用容量 |
|---|---|---|---|
| HID 按键与灯 | If#0 `Cls=03 Sub=00 Prot=00`（非 boot 子类），EP `0x82` IN + `0x01` OUT，中断传输，各 64 B / 1 ms | `usbhid` → `input0`、`input1`（即 `event0`、`event1`）、`/sys/class/leds/input<N>::mute`——**这个 N 不稳定**，10-04 两轮 unbind/bind 之后已经变成 `input10::mute`；代码里要按 `*::mute` 通配解析（`^t23`） | 8 个消费类按键 + `KEY_MICMUTE` + 1 个可点亮的静音灯 |
| AudioControl | If#1 `Cls=01 Sub=01 Prot=00`，`bInCollection=2` → If#2、If#3，`bNumEndpoints=0` | `snd-usb-audio` | 只出 6 个控件（见第三节），没有路由矩阵 |
| 播放流 | If#2 `Sub=02`，Alt 1 用 EP `0x02` OUT，等时 **Adaptive**，`MxPS=192 Ivl=1ms` | `/dev/snd/pcmC0D0p` | 48000×2ch×2 B = 192000 B/s，正好占满该端点 |
| 录音流 | If#3 `Sub=02`，Alt 1 用 EP `0x81` IN，等时 **Async**，`MxPS=96 Ivl=1ms` | `/dev/snd/pcmC0D0c` | 48000×1ch×2 B = 96000 B/s，正好占满该端点 |

- 音频拓扑（AC 接口内部连线，来自 249 字节描述符原文）：播放 `Terminal#1 USB Streaming(2ch) → FU#9 → Terminal#3 Speaker`；录音 `Terminal#2 Microphone(1ch) → FU#10 → Selector#11 → Terminal#4 USB Streaming`。整条链**只有两个 FEATURE_UNIT、没有 Mixer Unit** → 设备侧不存在"把麦克风并回喇叭"的硬件支路（这一条否掉了"某个音量控件可能是侧音"的猜测）。 ^mcp-topo
- 总线占用：实际协商在**全速 12 Mbit/s**（主机控制器是 `dwc2`，经板载 480 M hub 的 Port 2），两路等时合计 288 B/ms ≈ **2.3 Mbit/s，约占全速帧带宽的 19%**——再加第二个等时音频设备要先算这笔。 ^mcp-bw
- **同步类型与 CS 端点描述符**（读数来自同一份原始描述符，判据见 7.4／7.5）：播放 EP `0x02` 的 `bmAttributes` D3..2＝`10`＝**Adaptive**、录音 EP `0x81`＝`01`＝**Asynchronous**，与上表两格一致。两条 `EP_GENERAL`（CS 端点描述符）分别报：播放 `bmAttributes=0x01`（只置 D0 `Sampling Frequency`，**D7 `MaxPacketsOnly`＝0 ⇒ 允许短包**，主机侧发送不必把每个包补满 `wMaxPacketSize`）、录音 `bmAttributes=0x00`（一个端点控件都没报）；`bLockDelayUnits`／`wLockDelay` 播放报 `1`（毫秒）／`1`、录音报 `0`／`0`——**录音那两个零是规范对 async 端点的强制要求**（7.5 原文），不是设备偷懒。两条 AS 接口的 `bDelay` 都是 **1 帧（1 ms）**。**这块设备没有伴随的同步端点，而且是正常的**：`0x02` 是 adaptive **sink**、`0x81` 是 async **source**，规范要求配对同步端点的是 adaptive source 与 async sink 这两种（7.4）。 ^mcp-sync
- **描述符里两处要记账的细节**（2026-10-16 重读原始字节，→ `^t28`）：① 配置描述符 `wTotalLength=0x00E7`＝**231 字节**，与 `^mcp-topo` 那句"249 字节描述符原文"对不上（18 字节设备描述符＋231＝249，怀疑当初把设备描述符一起算进去了），**待核**——249 别当配置描述符长度拿去做解析上限。② 播放侧 FORMAT_TYPE 描述符 `bLength=0x0E`＝**14 字节**、末 3 字节是 `00 00 00`，录音侧同款只有 **11 字节**（`tSamFreq` 那 3 字节后即结束），`lsusb` 对前者直接打 `junk at descriptor end: 00 00 00`。**含义**：自己写解析器时不能假设两侧 FORMAT_TYPE 等长，要按 `bLength` 走；内核能容忍这个尾巴，实测不影响枚举、放音与录音。 ^mcp-descquirk
- 电源管理：`power/control=on`、`autosuspend_delay_ms=2000`，开机 2 小时 40 分后 `runtime_suspended_time=0`、`runtime_status=active`——**从未自动挂起过**；`Keep Interface`（numid=8）当时是 off。做"常听"设备时这条比控件更要紧。2026-10-04 复核把这个窗口拉到 **2.80 天**，`runtime_suspended_time` 仍是 0（`^t21`）。 ^mcp-pm
- **它没有的空间**：4 个接口里没有存储类（08h）、没有 CDC/DFU、没有 vendor-specific 音频接口。本板读数一致——`/dev/sd*`、`/dev/sg*` 都不存在，`/dev/hidraw*` 也不存在（`.config` 里 `# CONFIG_HIDRAW is not set`，连 `CONFIG_USB_STORAGE` 主开关都没有）；`/dev/ptp0` 是网卡 `e0047000.ethernet` 的 IEEE 1588 硬件时钟，与本设备无关，别当 U 盘。 ^mcp-nofs
- HID 里唯一那块没主的地址空间：报告描述符末段 vendor-defined（usage page `ff00`，Report ID 1，1 字节 IN + 1 字节 OUT；这 170 字节描述符的原文在 2026-10-04 从 debugfs 限量读拿到了，`^t22`）。没有 hidraw 就没有 `/dev` 节点可写，root 只能经 `/dev/bus/usb/001/<devnum>` 下 HID 控制传输去碰它。**2026-10-04 写路径已试完（`^t23`），三条硬事实**：① 内核 usbfs 按请求类型拦——`bRequestType` 的 type 位是 CLASS(01) 时，只要 `usbhid` 还占着 IF#0 就直接 `EBUSY`、上不了总线；把 `1-1.2:1.0` 从 `usbhid` 解绑后 class 请求全部通，`bind` 回去即可恢复（**代价：input 序号递增、LED 名字跟着变，见 `^t23`**）。② 解绑后设备照收 `SET_REPORT`、也照答 `GET_REPORT`（IN/OUT/FEATURE 三份都回 1 字节 `00`），真正被设备拒绝的只有 `GET_DESCRIPTOR(HID Report)` 和 `SET_IDLE`／`GET_IDLE`——所以 `^t22` 那句“ep0 一律 STALL、只读门是关的”已作废（那批请求编码成了 vendor 型）。③ 九个位值逐个写下去，板上五个可观测面（三个 ALSA 控件、播放功能、LED、input 设备、报告回读）一个都不动。剩下的入口只有一个：解绑状态下抢 EP `0x82` 中断 IN，看设备会不会主动推报告。 ^mcp-vendor

### 2.1 采样格式

读数来自 `/proc/asound/card0/stream0`：

| 方向 | 格式 | 声道 | 采样率 | 同步方式 | ALSA 节点 |
|---|---|---|---|---|---|
| 播放 | S16_LE | 2 | 48000 | ADAPTIVE | `/dev/snd/pcmC0D0p` |
| 录音 | S16_LE | 1 | 48000 | ASYNC | `/dev/snd/pcmC0D0c` |

**只有 48000 Hz 这一个采样率**（描述符 `bSamFreqType=1 Discrete`），ASR 常用的 16 kHz 必须有人重采样：交给 `plughw:` 或自己写代码。**这里有一条我先前写错的**：原话是"`hw:` 直连必失败"，2026-10-04 实测**不失败**——`hw:` 会静默按 48k 跑、只留一行 stderr 警告、退出码仍是 0，代价是时长或音高出错，详见 `^t18`。录音侧原生单声道，与 ASR 要的单声道一致，**不存在下混这一步**。重采样落在板端、代价可忽略（`^t17`、`^t19`）。 ^mcp-fmt

## 三、ALSA 控件：按 numid 走

`amixer sset/sget` 按名字取不到控件——本板既没有 `Speaker` 控件，`amixer -c 0 sset 'Mic Capture Volume' 110` 也直接报 `Unable to find simple control`。原因是 UAC（USB Audio Class）设备只暴露原始控件，不进 `snd-usb-audio` 的 simple mixer 表。**只能 `amixer -c 0 cset numid=N <值>`**，归属已按描述符逐位核到（`bmaControls` 索引 0 = master、1..n = 各声道；bit0 = Mute、bit1 = Volume）： ^mcp-ctlmap

| numid | ALSA 名 | 来自 | 值数 | 归属 |
|---|---|---|---|---|
| 3 | `PCM Playback Switch` | FU#9 `bmaControls(0)` bit0 | 1 | 播放侧总静音——**0（off）＝静音、1（on）＝通**（她耳朵判的，`^t26-mute3`）；只管播放侧，静音时 `aplay` 仍 rc=0、采集流照常在跑 |
| 4 | `PCM Playback Volume` | FU#9 `bmaControls(1)/(2)` bit1 | 2（左右） | 每声道增益——**规格上是声道平衡，实测不作用于声音**，见 3.1 |
| 5 | `PCM Playback Volume`,index=1 | FU#9 `bmaControls(0)` bit1 | 1 | **主音量，实际响度看这条** |
| 6 | `Mic Capture Switch` | FU#10 master bit0 | 1 | 采集静音——**0＝静音、1＝通**，且静音是逐样本数字归零、不是衰减（`^t25-mute6`） |
| 7 | `Mic Capture Volume` | FU#10 master bit1 | 1 | 麦克风增益——**安静时底噪不随档位动**（六档 RMS 极差 0.8 dB，标称量程 28.3 dB，`^t25-gain`）；对说话电平的作用未判（要她） |
| 8 | `Keep Interface`（iface=CARD） | 驱动自加 | 1 | 防 USB 自动挂起 |

- 判据：`FU#10` 的 `bmaControls(1)=0x00`（声道位全灭）却仍有 1 个音量控件，而 `FU#9` 的 master+2 声道拆成 `values=2` 与 `values=1` 两条——**"只有一个值的那条音量来自 master"**。
- 刻度 0–151，`cget` 报 −28.37 dB..−0.06 dB（约 0.188 dB/步）；`numid=4` 给单值会同时写左右，**也能写成 `151,0` 分左右**（本板可写可回读，见 3.1），写法示例 `amixer -c 0 cset numid=5 38`。 ^mcp-ctluse

**控件值不保证保持**：本轮最后写入 `numid=7`=110，稍后复核读回 151（我没有写过 151），期间只可能是她按了机身键或设备自身改动。2026-10-04 又漂了一次：10-02 收口时 `7`=151，本轮开工现读已是 **`7`=38**，而同一刻 `4`=38,38、`5`=76 都原封不动——**漂的是麦克风增益这一条**（为什么漂没查，我不写机制）。代码里**别把音量/增益当成上电即已知的常量，要 `cget` 现读**；重插或重启会直接回设备默认。 ^mcp-ctlpersist

**非静音时读到的"安静"不是零**（2026-10-04，`^t25-floor`）：`numid=6`＝1 时，房间里没声音的那 3 秒流是 **RMS ≈ −64.5 dBFS 的一幅固定图样**——144,000 帧只有 82–105 个不同取值、幅度约 −117…+111、除开头 289 个零之外**每个样本都是奇数**。只有把 `numid=6` 写成 0 才拿到逐样本精确 0。**含义**：静默判定/VAD 的门限要落在 −64.5 dBFS 之上并留余量，**不能写成"样本==0 即无声"**；反过来，看到"整段精确 0"应当判为**采集静音位被置 0 或链路坏了**，而不是"房间很静"。另外这幅图样不随 `numid=7` 档位变，所以"比底噪"这条路在这台上判不了麦克风增益（`^t25-gain`）。 ^mcp-idlefloor

### 3.1 `numid=4` 到底是什么、为什么拧了没反应（2026-10-02 收口）

- **规格上它是"每声道增益"**。厂商侧一级依据＝USB-IF《USB Device Class Definition for Audio Devices》Release 1.0（1998-03-18，130 页，已整份取回存档 `S:\apps\llm\agentwork\audio10.pdf`）§3.5.5 原文：Feature Unit 对每个逻辑声道 *optionally provides* 一组控件，其中含 Volume；紧接着两句是要害——"**The master Controls are cascaded after the individual channel Controls.** This setup is especially useful in multi-channel systems where **the individual channel Controls can be used for channel balancing** and the master Controls can be used for overall settings."，以及"**The 'master' channel has channel number zero and is always virtually present.**" 表 4-7 给出位定义：`bmaControls(0)`＝master channel 0、`bmaControls(1..ch)`＝各逻辑声道，**D0 Mute、D1 Volume、D2 Bass、D3 Mid、D4 Treble、D5 Graphic Equalizer、D6 Automatic Gain、D7 Delay、D8 Bass Boost、D9 Loudness**。 ^mcp-ch4-spec
- **它不可能是"去噪开关"**：本设备 FU#9 每声道只报了 **D1（Volume）** 这一位（`^mcp-ctlmap`）。规范里音量控件的语义只有一种——增益，§5.2.2.4.3.2 明写它是 ±127.9961 dB、步进 1/256 dB 的 Volume Control（本设备实际报的分辨率是 48/256＝**0.1875 dB/步**，151 步＝28.3 dB，与 `cget` 的 −28.37..−0.06 dB 对得上）。真要暴露降噪/自动增益，得报 D6 或 D9，或者走 Processing Unit——**描述符里两者都没有**。判 **A 级**（规范原文 × 本板描述符）。
- **本板内核的读数是"真问设备"**：板子 `uname -r`＝**5.4.52**，该版本的 `mixer_ctl_feature_get()` 逐声道调用 `snd_usb_get_cur_mix_value()` 发 **GET_CUR 控制传输**，没有驱动侧缓存那条路（缓存/`get_cur_broken` 是主线 6.x 才加的）。所以 `cget` 反映的是设备自己应答的值，不是我方的影子。判 **A 级**（内核源码 `sound/usb/mixer.c` v5.4 与 master 两份均已取回对照）。
- **现象与机制分开说**。总线侧（实测，板钟 2026-10-02 19:36）：`cset numid=4 0` 与 `151` 均 rc=0；写 `151,0` 回读 `: values=151,0`，写 `0,151` 回读 `: values=0,151`，写回 `38,38` 回读 `38,38` → **控制传输这一层，设备为两个声道各存了一份值，SET_CUR 收下、GET_CUR 如实回答**。声学侧（她的判语）：151 与 0 交替四段"没差别"，此前 151/38 的 B/C 多轮她的外部声压与频率读数也一致（`^t12`）。**"音频层没接线"是我给这两条现象起的机制解释，不是读数本身**（B 级，见下一条）。 ^mcp-ch4-meas
- **她给的替代解释，以及它覆盖到哪**。她的说法："这是一个音箱，可能左右声道太近我听不出来"＋"不要放，我听不出来啊"，所以**非对称那一格（`151,0` vs `0,151`，即规范说的 channel balancing）按她的决定不测**。这条解释只顶得上非对称那种情形：**151 对 0 是两只一起到顶、一起到底**，只要这级增益真的作用在信号路径的任何一点，两边同时归零就把这级控件相对最大档拉低**满量程 28.3 dB**（该控件 0＝量程底 −28.37 dB、151＝−0.06 dB，见 7.3 第 3 条），这是人耳无论如何分得出来的量级，跟两只喇叭相距多远无关。所以"对称写法也无效"这一条维持，而"设备内部到底有没有可用的声道平衡"**记为不测、不作为依据**（`^mcp-gap-4`）。 ^mcp-ch4-alt
- **为什么会有这种控件**（推测，分级给）：
  - **B 级**：**"收请求但不出声"在 UAC 生态里是被点名的一类已知故障**，判据不是我这边的推测，而是 Linux 主线的注释。UAC 的合规只到"描述符自洽＋请求有正确应答"这一层，**没有任何测试要求增益真的乘到样本上**，所以固件把 GET_CUR/SET_CUR 挂到一张音量查找表上就能过，而表里每声道那格是否在音频图里连线——主机侧无法直接看见。主线 `sound/usb/mixer.c` 的 `check_sticky_volume_control()` 注释原文："Some devices' volume control mixers have sticky GET_CUR, which implies either stubbed SET_CUR or broken GET_CUR. **For the former case, the mixer accepts SET_CUR but do absolutely nothing**, so falling back to soft mixer is the only way to control the volume."，并且明确"we can't distinguish between stubbed SET_CUR and broken GET_CUR with simple read-back tests"。2026-04-09 还有补丁主张干脆把这类控件**不注册给用户态**（"ALSA: usb-audio: Do not expose sticky volume control mixers"）。**本板 5.4.52 没有这段代码，驱动不会替我们识别、也不会隐藏这条控件**——它就这么挂在 `numid=4` 上等人去写。 ^mcp-ch4-why
  - **C 级**：这台设备本体是炬芯 ATS2836 蓝牙音频 SoC（`^mcp-ident`），USB UAC 只是它兼任的一个外设角色，整机响度由它自己的系统音量与 DSP 管；per-channel 那两级很可能只存在于 USB 控制层的寄存器里，音频图里另一套（蓝牙侧）才有真正的声道增益。要证实得能读蓝牙侧或固件，本板做不到（`# CONFIG_BT is not set`）。
  - **C 级**：真能配置这台机器的入口更可能是 HID 里那段 vendor-defined（usage page `ff00`，Report ID 1，`^mcp-vendor`），不是 UAC 控件。**这条猜测 2026-10-04 实测不给支持**：vendor 报告写得进去（`SET_REPORT` ACK），但九个位值没有任何一个能改变板上可观测的东西（`^t23`）。留着是因为它没被证伪——设备内部可能确实变了什么，只是本板量不到（没有第二台机器、也没有电流表可看）。
- **对代码的含义**：**把 4 号当不存在**。响度只写 `numid=5`；需要左右独立增益时别指望设备，在板端对 PCM 数据自己乘系数（`plughw` 那层或代码里），或加 ALSA `softvol` 层。

### 7.1 §3.5.5 Feature Unit（原文第 23–24 页）

> The Feature Unit (FU) is essentially a multi-channel processing unit that provides basic manipulation of the incoming logical channels. For each logical channel, the Feature Unit optionally provides audio Controls for the following features:
> • Volume • Mute • Tone Control (Bass, Mid, Treble) • Graphic Equalizer • Automatic Gain Control • Delay • Bass Boost • Loudness
> In addition, the Feature Unit optionally provides the above audio Controls but now influencing all channels of the cluster at once. In this way, 'master' Controls can be implemented. **The master Controls are cascaded after the individual channel Controls.** This setup is especially useful in multi-channel systems where **the individual channel Controls can be used for channel balancing** and the master Controls can be used for overall settings.
> The logical channels in the cluster are numbered from one to the total number of channels in the cluster. **The 'master' channel has channel number zero and is always virtually present.**
> The Feature Unit Descriptor reports which Controls are present for every channel in the Feature Unit and for the 'master' channel. All logical channels in a Feature Unit are fully independent. There exist no cross couplings among channels within the Feature Unit. There are as many logical output channels, as there are input channels. These are grouped into one audio channel cluster that enters the Feature Unit through a single Input Pin and leaves the Unit through a single Output Pin.

**用途**：这一段定了三件事——各声道控件的**本职是声道平衡**；master 是**级联在各声道之后**（所以"4 与 5 不串联"那句旧推理错，见 `^t9`）；声道编号从 1 起、0 恒为虚拟 master。**注意 "optionally"**：FU 声明哪些控件由厂商自定，声明了就应答，规范层面没有"必须真的乘到样本上"的检验。 ^mcp-spec-fu

### 7.3 §5.2.2.4.3.1 Mute Control 与 §5.2.2.4.3.2 Volume Control（原文第 75–78 页）

> **5.2.2.4.3.1 Mute Control**
> The Mute Control is one of the building blocks of a Feature Unit. A Mute Control can have only the current setting attribute (CUR). The position of a Mute Control CUR attribute can be either TRUE or FALSE.
> […] The valid range for the Channel Number field is from zero (the 'master' channel) up to the number of logical channels in the audio channel cluster.
> Table 5-16: First Form of the Mute Control Parameter Block — Control Selector `MUTE_CONTROL`，wLength 1，offset 0：`bMute` 1 Bool "The setting for the addressed Mute Control's CUR attribute. **Muted when TRUE, not muted when FALSE**."
>
> **5.2.2.4.3.2 Volume Control**
> The Volume Control is one of the building blocks of a Feature Unit. A Volume Control can support all possible Control attributes (CUR, MIN, MAX, and RES). The settings for the CUR, MIN, and MAX attributes can range from **+127.9961 dB (0x7FFF) down to −127.9961 dB (0x8001) in steps of 1/256 dB** or 0.00390625 dB (0x0001). The range for the CUR attribute is extended by code **0x8000, representing silence, i.e., −∞ dB**. The settings for the RES attribute can only take positive values and range from 1/256 dB (0x0001) to +127.9961 dB (0x7FFF). **The Volume Control honors the request to the best of its abilities. It may round the wVolume attribute value to its closest available setting. It will report this rounded setting when queried during a Get Control request.**
> In the first form of the request, a particular Volume Control within a Feature Unit is addressed through the Unit ID and **Channel Number** fields of the Set/Get Feature Unit Control request. The valid range for the Channel Number field is from zero (the 'master' channel) up to the number of logical channels in the audio channel cluster.
> Table 5-18（第一形式的参数块）：Control Selector `VOLUME_CONTROL`，wLength 2，offset 0：`wVolume` 2 Number——0x7FFF＝+127.9961 dB … 0x0000＝0.0000 dB，0xFFFF＝−0.0039 dB … 0x8001＝−127.9961 dB，0x8000＝−∞ dB（仅 CUR 属性）。
> Table 5-19（第二形式）：Channel Number 置 **0xFF**，一次读写该 Feature Unit 内**全部**可用控件，wLength＝控件数 NrAv × 2。

**用途四处**：
1. **"honors the request to the best of its abilities"** 这句是规范自己留的余地——设备只需按自己的能力处理请求，**应答成功不等于增益真的被应用**。这正是 3.1 节那个现象在规范条文里的合法位置（`^mcp-ch4-why`）。
2. 同时"它会在 Get Control 时回报取整后的设定"说明 **GET_CUR 语义上应当反映设备实际应用的那一档**——本设备却把 `151,0` 与 `0,151` 分声道原样回读（`^mcp-ch4-meas`），所以它的 GET_CUR 更可能是寄存器回显而非真实状态。判 **B 级**。
3. `0x8000` 才是规范里的"静音/−∞ dB"码；本设备两条音量控件的量程是 0..151 ＝ −28.37..−0.06 dB（这个 dB 范围是驱动在解析阶段向设备发的 `GET_MIN`/`GET_MAX`/`GET_RES` 类请求要来的，见 v5.4 `sound/usb/mixer.c` 的 `get_min_max_with_quirks()`——`numid=4` 这种带声道掩码的控件它问的是**声道 1**，不是 master；拿不到才回落到默认值。所以 −28.37..−0.06 dB 出自设备自己的应答，判 **A 级**），**里面没有静音码**。所以"把音量写成 0"和"让它不出声"是两件事：前者＝照放，只是比最大档低 28.3 dB（衰减器语义，151 那一端是 0 dB 即"不衰减"，这套控件从不提升）；要真无声得靠 `numid=3` 的 Mute（§5.2.2.4.3.1 明写 TRUE＝静音，2026-10-04 已由 `^t26-mute3` 听测确认）或者根本没有流——没人 `aplay` 时 AudioStreaming 接口停在 alternate setting 0，等时端点不上总线，自然没样本可放。这条同时修正"4=0 应当完全无声"的想当然：**真接了线，0 档也只是降到 −28.3 dB，而 28.3 dB 的落差人耳一定分辨得出**（这就是 `^mcp-ch4-alt` 那条推理的量级依据）。
4. 静音极性的判据也在这段：`bMute` **TRUE＝静音**、FALSE＝不静音。两侧听测现在都做了——播放侧 `numid=3`（`^t26-mute3`）与采集侧 `numid=6`（`^t25-mute6`）**读数一致：这台把 ALSA 的 `off` 映射成 TRUE**，所以"写 0"就是真静音请求；但要注意这条静音在采集侧是逐样本数字归零、在播放侧连 `aplay` 的 rc 都不影响。 ^mcp-spec-vol

### 7.4 §3.3 音频同步类型（原文第 19 页）

> **3.3 Audio Synchronization Types**
> Each isochronous audio endpoint used in an AudioStreaming interface belongs to a synchronization type as defined in Section 5 of the USB Specification.
> **3.3.1 Asynchronous** — Asynchronous isochronous audio endpoints produce or consume data at a rate that is locked either to a clock external to the USB or to a free-running internal clock. These endpoints cannot be synchronized to a start of frame (SOF) or to any other clock in the USB domain.
> **3.3.2 Synchronous** — The clock system of synchronous isochronous audio endpoints can be controlled externally through SOF synchronization. Such an endpoint must do one of the following: • Slave its sample clock to the 1ms SOF tick. • Control the rate of USB SOF generation so that its data rate becomes automatically locked to SOF.
> **3.3.3 Adaptive** — Adaptive isochronous audio endpoints are able to source or sink data at any rate within their operating range. This implies that these endpoints must run an internal process that allows them to match their natural data rate to the data rate that is imposed at their interface.

**配对规则**（§3.7.2.2，原文第 33 页）："An adaptive audio source IN endpoint is accompanied by an associated isochronous synch OUT endpoint that carries Ff. An asynchronous audio sink OUT endpoint is accompanied by an associated isochronous synch IN endpoint."；§4.6.2 开头同口径："This descriptor is present only when one or more isochronous audio data endpoints of the adaptive source type or the asynchronous sink type are implemented."

**用途**：这两段合起来解释了 `^mcp-sync` 里那条"没有同步端点是正常的"——**要配同步端点的只有 adaptive source 与 async sink 两种**，而本设备播放是 adaptive **sink**、录音是 async **source**，四种组合里恰好落在不需要同步端点的那一半。所以"没有 synch endpoint"不是描述符缺件、也不该被当成枚举异常去查。 ^mcp-spec-sync

### 7.5 表 4-20／4-21 等时端点描述符（原文第 61–63 页）

> **Table 4-20: Standard AS Isochronous Audio Data Endpoint Descriptor** — offset 3 `bmAttributes`：D3..2 Synchronization type，`01 = Asynchronous`／`10 = Adaptive`／`11 = Synchronous`；D1..0 Transfer type，`01 = Isochronous`。offset 6 `bInterval`："Interval for polling endpoint for data transfers expressed in milliseconds. **Must be set to 1.**" offset 7 `bRefresh`："Reset to 0." offset 8 `bSynchAddress`："The address of the endpoint used to communicate synchronization information if required by this endpoint. **Reset to zero if no synchronization pipe is used.**"
>
> **Table 4-21: Class-Specific AS Isochronous Audio Data Endpoint Descriptor** — offset 3 `bmAttributes`："A bit in the range D6..0 set to 1 indicates that the mentioned Control is supported by this endpoint. **D0: Sampling Frequency、D1: Pitch、D6..2: Reserved**；Bit D7 indicates a requirement for wMaxPacketSize packets. **D7: MaxPacketsOnly**"；offset 4 `bLockDelayUnits`："0: Undefined、1: Milliseconds、2: Decoded PCM samples、3..255: Reserved"；offset 5 `wLockDelay`："Indicates the time it takes this endpoint to reliably lock its internal clock recovery circuitry."
>
> 同节末段：**"The bLockDelayUnits and wLockDelay fields are only applicable for synchronous and adaptive endpoints. For asynchronous endpoints, the clock is generated internally in the audio function and is completely independent. In this case, bLockDelayUnits and wLockDelay must be set to zero."**
> 以及 `bmAttributes` D7 的用法："This bit must be used by the Host software to determine if the driver should pad all potential short packets (except null packets) with zero bytes to wMaxPacketSize length before sending them to an OUT endpoint."

**用途**：这是 `^mcp-sync` 那几个读数的出处。三件直接可用的结论：① 播放侧 `MaxPacketsOnly=0` ⇒ **主机侧往 `0x02` 发短包是被允许的**，不必把每个包补满 192 B（写 UAC gadget／自己发等时包时按这条走）；② 录音侧 `bLockDelayUnits=wLockDelay=0` 是规范强制，**看到 0 别当设备没报**，也因此"录音端点的锁定期"这个概念在它身上不成立；③ 两个 `bInterval` 都是 1 ms，与描述符实读一致。 ^mcp-spec-ep

### 7.6 §5.2.1 请求布局（原文第 65–67 页）

> **5.2.1.1 Set Request** — `bmRequestType`：`00100001B` 给 AudioControl／AudioStreaming 接口，`00100010B` 给等时端点；`bRequest` 取 `SET_CUR`／`SET_MIN`／`SET_MAX`／`SET_RES`／`SET_MEM`；`wValue`＝"the Control Selector (CS) in the high byte"（Feature Unit 另在低字节放 Channel Number）；`wIndex`＝"the interface or endpoint to be addressed in the low byte and the Entity ID or zero in the high byte"。
> **5.2.1.2 Get Request** — 同构，`bmRequestType`＝`10100001B`（接口）／`10100010B`（端点）。
> **"In principle, all requests are optional. If an audio function does not support a certain request, it must indicate this by stalling the control pipe when that request is issued to the function. However, if a certain Set request is supported, the associated Get request must also be supported. Get requests may be supported without the associated Set request being supported."**
> **"If the request specifies an unknown or non-Entity ID or an unknown interface or endpoint number, the control pipe must indicate a stall."**

**用途**：**"不支持就 STALL"** 这一句是 `^t22`／`^t23` 那批 `EPIPE` 的规范依据——设备对 `GET_DESCRIPTOR(HID Report)`、`SET_IDLE` 回 `EPIPE`／STALL，在规范里是**合法应答**（"the request is optional"），不是设备坏了，所以那两条读不出来这件事到此为止、不值得再投时间。反过来也提醒：`^t23` 里 `SET_REPORT` 被 ACK 只证明"这条请求它接"，**接不接受参数、参数起不起作用，规范层面完全没保证**。另外这条给了报 bug 时的对照面：真违规的是"对已知 Entity 的未知 CS"或"SET 支持而 GET 不支持"。 ^mcp-spec-req

**用途**：`^t28` 那轮重解原始字节就是照这张表读的——原始描述符里的 `0x24/0x01`（AC 头）、`0x24/0x02`／`0x24/0x03`（进出终端）、`0x24/0x06`（两个 Feature Unit）、`0x24/0x05`（Selector）、`0x25/0x01`（CS 端点），全部对得上。
- **一个必须知道的歧义**：**子类型码的命名空间分两套**（A-5 给 AC、A-6 给 AS），所以字节对 `(0x24, 0x01)` 是**二义的**——在 If#1 里它是 AC `HEADER`，在 If#2／If#3 里是 AS `AS_GENERAL`；`(0x24, 0x02)` 同理（AC 里是 `INPUT_TERMINAL`，AS 里是 `FORMAT_TYPE`）。本设备的原始字节两处都出现过：偏移 **`0x32`** 的 `0a 24 01 00 01 4e 00 02 02 03`（AC 头，`bcdADC=0x0100`、`wTotalLength=0x004e`）与偏移 **`0x92`** 的 `07 24 01 01 01 01 00`（AS_GENERAL，`bTerminalLink=1`；If#3 那份在 `0xc7`，`bTerminalLink=4`）。**写解析器时只能先判"当前落在哪个接口"再解子类型**，光看 `0x24/0x01` 会解错结构、把长度字段读飞。
