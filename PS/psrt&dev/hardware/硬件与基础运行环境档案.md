## 读法：四种来源必须分开看

本档案每条数据都带来源标签，混用会把"标称"当成"实测"：

| 标签 | 含义 |
| --- | --- |
| 官方规格 | 厂商手册或板卡规格表给的标称值，**不等于本机实测** |
| 系统报告 | 运行中的系统自己报出来的（`/proc`、`/sys`、标准工具） |
| 工具报告 | 厂商工具链自己报的（icraft、ethtool 等） |
| 现场测量 | 这次采集时当场观察到的（链路协商、空闲空间、负载） |
| 未验证 | 没跟第二来源交叉核过，或平台根本没暴露这个字段 |

算力、带宽、FPGA 占用这类数字，本档案一律停在"官方规格"或"未测量"，没有拿规格冒充实测。

### CPU

4 核 ARM Cortex-A53（ARMv8-A，aarch64，小端），implementer 0x41 / part 0xd03 / stepping r0p4，1 socket，**物理核 4 / 逻辑核 4 / 当前可用 4**（无 SMT，无离线核）。指令集扩展 fp asimd evtstrm crc32 cpuid。

主频**现场取不到**：板上没有 cpufreq 接口、没有 `cpu_opp_table`、设备树里 `operating-points-v2` 是被注释掉的、`cpu@0` 也没有 `clock-frequency` 属性。手册标的"最高 1 GHz"是官方规格，不是实测。`lscpu` 给的 BogoMIPS 200.00 是内核估算值，**不能当频率读**（既不是 200 MHz 也不是 100 MHz）。

缓存结构现场可见、容量不可见：`index0` L1 Data、`index1` L1 Instruction（`shared_cpu_map=1`，每核私有），`index2` L2 Unified（`shared_cpu_map=f`，四核共享）。sysfs 的 `size` 属性缺失，根因是出厂 DTB 的 `l2-cache` 节点只带 `compatible` 和 `phandle`、没有 `cache-size`，内核因此无法公布容量。容量值（32KB+32KB / 1MB）取自官方规格。

温度、governor、功耗模式：平台不暴露（无 thermal zone、无 cpufreq），id 只能到 cpuidle governor = menu。

### MMC 控制器与 eMMC 数据通路

> 本节为 2026-10-29 专项排查补充，目的是回答"eMMC 数据怎么走、能不能走 DMA、性能瓶颈在哪"。原始证据在 `emmc_evidence/`，完整分析见 `../emmc/`。

两个 MMC 控制器都在 **PS 侧** `amba-apu@0` 下，**eMMC 的数据路径不经过 PL**：

| 控制器 | 地址 | 接的卡 | Linux IRQ | 传输模式 | 实测吞吐 |
| --- | --- | --- | --- | --- | --- |
| `e0043000.dwmmc` (mmc0) | `0xe0043000` | SD 卡 58.4 GiB | 23 | **外部 DMA** | 写 18.7 / 读 22.4 MB/s |
| `e0044000.dwmmc` (mmc1) | `0xe0044000` | eMMC Y2P032 29.1 GiB | 24 | **PIO（默认）；2026-10-30 实测可切外部 DMA，临时态** | 写 11.6 / 读 11.8 MB/s（PIO, 25MHz）；50MHz 实测写 22.9 / 读 23.7 MB/s |

来源：系统报告（设备树）+ 现场测量（2026-10-29，`dd` + `O_DIRECT`，64MB 顺序）。
IRQ 号取自 `/proc/interrupts` 的 `dw-mci` 两行（23=SD，24=eMMC），不是设备树里的 SPI 号 52/73。

**控制器寄存器对比**（`busybox devmem` 只读，2026-10-29，boot `72a8f941`）：

| 寄存器 | 偏移 | eMMC | SD | 说明 |
| --- | --- | --- | --- | --- |
| CTRL | 0x000 | `0x00000010`（默认）；`0x00000030`（2026-10-30 实测 DMA 临时态） | `0x00000030` | **bit5 DMA_ENABLE：eMMC 默认=0，实测可切 1；SD=1** |
| CLKDIV | 0x008 | `0x00000002` | `0x00000001` | |
| CTYPE | 0x018 | `0x00000001` | `0x00000001` | 均为 4-bit |
| TCBCNT/TBBCT | 0x048/0x04c | `0x00006906` / `0x200F0010` | 变动 | 累计字节计数器，**每次读都不同，别当状态用** |
| VERID | 0x06c | `0x5342220A` | `0x5342220A` | DW MSHC 2.20a |
| HCON | 0x070 | `0x07E52CC1` | `0x07E52CC1` | **两者完全一致** |

> 偏移 0x074 以上（到 0x0FC）全部读回 `0x07E52CC1`，说明该 IP 只解码到 HCON 为止，没有隐藏寄存器。
> `TMOUT`(0x014) / `STATUS`(0x034) / `FIFOTH`(0x038) / `CDETECT`(0x03C) 读出来都是全 1，是本 IP 未实现的
> 表现，**不可作为状态依据**。早期版本档案把这些字段当有效值记录，已更正。

**关键判断：eMMC 控制器硬件支持外部 DMA，不是硬件不支持。** `HCON[17:16] = 0b01 = DWDMA`（DesignWare 外部 DMA 接口），两个控制器这一位相同。驱动（`dw_mmc.c:2890-2960`）分两步判定：先读 HCON 确认硬件能力，再查设备树有没有 `dmas` 属性；eMMC 节点没有 `dmas`，所以落到 `no_dma` 分支退回 PIO。厂商源码注释 `/* mmc1 not support dma */` 指的应是 **SoC 集成时 mmc1 的 DMA 请求线未接到 dmahost0**——**这一点已于 2026-10-30 实测推翻**：在 eMMC 节点补 `dmas = <0x0a 0x01 0x00 0x00>`（req=1）后，驱动打印 `Using external DMA controller.`，CTRL `0x10 → 0x30`（bit5=1），读写正常。**本板 req=1 这条请求线确实接到了 dmahost0，vendor 注释是误注。**

**总线时钟：25MHz，已跑满 94%。** `sdio_div` 从 `iopll` 固定 /10 得到 100MHz，再经控制器 CLKDIV 分频（`ciu/(2×CLKDIV)`）：eMMC CLKDIV=2 → 25MHz，SD CLKDIV=1 → 50MHz。理论带宽 12.5 / 25 MB/s，实测 11.8 / 22.4，**两者利用率 94% / 90%，设备侧已饱和，瓶颈在总线时钟而非 CPU 或 DMA**。

**50MHz 已于 2026-10-30 运行时实测验证（boot `db887f8e-201b-47ca-bbc4-396c53a176a3`）**：用 configfs overlay + `unbind/bind` 把 CLKDIV 从 2 切到 1，实测写 22.9 / 读 23.7 MB/s（×2），16MB 随机写读回 md5 一致、dmesg 无错误。**当前板子运行在 50MHz（configfs 临时态，重启回 25MHz）**。来源：`emmc_evidence/50mhz-test-20261030-bootdb887f8e.txt`。

**eMMC 卡片能力（EXT_CSD 实测，`CMD8` 只读，2026-10-29）**：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `DEVICE_TYPE` [196] | `0x57` | bit0 HS52 **支持**，bit1 HS200 **支持**，bit2 HS400 **支持**，bit3 HS400ES 不支持 |
| `BUS_WIDTH` [183] | `1` | 当前 4-bit |
| `HS_TIMING` [185] | `1` | 当前 high speed |
| `EXT_CSD_REV` [192] | `8` | eMMC 5.1 |
| `SEC_COUNT` [212..215] | `61071360` | 29.1 GiB |
| `PRE_EOL_INFO` [267] | `0x01` | 正常 |
| `DEVICE_LIFE_TIME_EST_A/B` [268/269] | `0x01` / `0x01` | 已用 0~10%，几乎全新 |
| `RPMB_SIZE_MULT` [168] | `128` | 16 MiB |

**卡不是瓶颈，瓶颈是设备树钉死的上限**：

```dts
dwmmc@e0044000 {
    max-frequency = <0x17d7840>;   /* 25,000,000 */
    bus-width     = <0x04>;
    /* 没有 vmmc-supply / vqmmc-supply */
};
```

ciu 时钟源 100MHz，`CLKDIV = ceil(100MHz / (2 × max-frequency))`。当前 25MHz → CLKDIV=2；
改成 50MHz → CLKDIV=1，实际 50MHz，吞吐翻倍（**已于 2026-10-30 运行时实测 ✅，见上**）。
**HS200/HS400 虽然卡支持，但需要 1.8V 信号，本节点无 `vqmmc-supply`、板上未见 1.8V 切换电路，不可达。**
8-bit 总线能力在 EXT_CSD 中**没有对应字段**（规范未定义），只能改 `bus-width=<8>` 试。**已于 2026-10-30 运行时实测：驱动报 `switch to bus width 8 failed`，自动回退 4-bit、无损坏 —— 8-bit 在板上不可用（PCB 大概率只布线 DAT0~3 或颗粒仅 4-bit），提速路封死。**
来源：`/sys/class/mmc_host/mmc1/mmc1:0001/` + EXT_CSD 原始 dump（`emmc_evidence/probe-20261029-boot72a8f941.txt`）。

**时钟链分离（重要，防止误改 CPU 频率）**：

```
CPU  : armpll_int → armpll → armpll_clk                     1 GHz
外设 : iopl_int → iopl_clk → sdio_mux → sdio_div → sdio0/1   100 MHz
```

父节点链实测：`sdio1 → sdio_div → sdio_mux → iopl_clk → iopl_int`，**不经过 armpll**。CPU 侧另**无 `cpufreq` 接口**（`/sys/devices/system/cpu/cpu0/cpufreq` 不存在），频率由 ARM PLL 硬件锁定，软件无法调节，与本文档的 SDIO 总线调频方案互不相干。来源：系统报告（`/sys/kernel/debug/clk/clk_summary`、`clk_parent`）。

**CPU 开销实测**（`/proc/stat` 采样，`HZ=100`）：eMMC PIO 满速时额外占用约 4~11% 单核，占全系统 1~3%。开销**正比于字节数而非传输速度**，块越小每 MB 成本越高（1M 块 9.7 ms/MB → 4K 块 24.4 ms/MB）。**CPU 不是瓶颈。**

**设备树权威来源**：`mmcblk0p1/fmqlmp-verify.dtb`（16079 B）。注意 `../board_extract/` 与内核源码树里那份 `fmqlmp-verify.dts` **已过期**——源码写 `mmc0 max-frequency = 2500000`（2.5MHz），实际运行是 50MHz。改动前必须以 boot 分区 DTB 反编译结果为准。

**eMMC 芯片健康度**：`life_time = 0x01 0x01`（磨损 0~10%）、`pre_eol_info = 0x01`（正常）、生产日期 09/2023。CSD 的 `TRAN_SPEED` 显示 25MHz，但这是 eMMC 的兼容默认值，真实高速能力在 EXT_CSD 的 `DEVICE_TYPE` 字段（值 `0x57`，已于 2026-10-29 经 `CMD8` 读取，见上方 EXT_CSD 实测表）。

### 加速器

**NPU**——官方规格是 1 个 ZG330 iCore（8 TOPS @ INT8 / 4 TFLOPS @ FP16 / 2 TFLOPS @ TF32），在 PL 里。现场确认的是**它不在 ARM 侧**：把扁平化设备树全文搜 `npu`／`aiu`／`zhuge`／`icore`，**0 命中**（A：现读 `PS/board_extract/35_dtb_flattened_shipped.txt`）；没有内核模块、没有 `/dev` 节点。它只经 `axi://zg330aiu?npu=0x40000000&dma=0x80000000` 那两个 **PL 的 AXI 从端口窗口**摸到，用户态栈是那 12 件 ZG330 库（`libicraft_zg330backend.so` 等，见 `PS/hardware/software.json` 的 `npu_runtime_stack`）。算力数字只有官方规格，本次未跑任何负载，实测吞吐为空。

> **归属更正（2026-10-23，D-79）**：本段初版把下一条 `vpu: mve@F0020000` 的现场证据记成了 NPU 的——**判错了**，判错的那半句"厂商把 NPU 那块寄存器起名叫 VPU"一并作废。那个节点是 **VPU（视频编解码器）**，见下一条。判错来源是本档案第 5 行的采集口径本身：`PS/collect_followup.sh` 第 51 行注释写的是 `# 5. NPU (ZG330 / MVE) presence and driver state`，采集时就按 NPU 取样。原始日志一行没删，只改归属与标签。

**VPU（视频编解码器）**——设备树节点 `vpu: mve@F0020000`、`compatible = "arm china,linlon-v5"`、`reg 0xF0020000` size `0x10000`、`IRQ GIC_SPI 69`、`clock-names = "clk_vpu"`（A：`PS/board_extract/29_dts_fmqlmp-verify.dts` 第 708、709、713 行）。驱动在开机约 9.5 秒时打出 `MVX dev: Linlon v5276 identified. cores=2, nlsid=4, id=0`，平台设备 `f0020000.mve` 已绑定，内核线程 `mvx_sched` 在跑，内核模块 `amvx`（modinfo: "Tiube VPU Driver"）。V4L2 侧出口是 `/dev/video0`（2026-10-05 实测，[[板卡镜像实测取证#十五、VPU 硬编取证（D-31 队列第 ③ 项，2026-10-05）|板卡镜像实测取证——十五]]）。**它不是 NPU**：`/lib/firmware/linlon-v52_v76-80-2/` 那 17 个 `.fwb` 全是视频 codec 固件——`mpeg4dec`／`avs2dec`／`vp9dec`／`h264enc`／`h264enc.prot-ver`／`jpegdec`／`avsdec`／`mpeg2dec`／`vp8enc`／`hevcdec`／`rvdec`／`h264dec`／`vp8dec`／`vc1dec`／`hevcenc`／`jpegenc`／`vp9enc`（A：`PS/board_extract/58_rootfs_system_config.txt` 第 415–433 行）。本次未跑编码负载，吞吐读数只在 §15 那条旧档里。

**GPU**——板上另有一颗 Mali（设备树 `mali_gpu@f0000000`，`arm,mali-bifrost`），驱动 DDK `r31p0-01eac0`，GPU id 0x2、arch 7.4.0 r1p0，`/dev/mali0` 在位，coherency mode 31。驱动只报 arch 串不报型号名，"Mali-G52" 是按 arch 映射的解读，不是直接读数。显存容量 sysfs 未公布、debugfs gpuinfo 为空，标 unknown。**手册的规格表里没有这颗 GPU**，它不在官方规格范围内。

**FPGA**——`fpga_manager fpga0`，name `FMSH FMQL FPGA Manager`，device 指向 `e0040000.devcfg`，采集时 **state = operating**（bitstream 在我们开始之前就已加载，U-Boot 从 SD 卡 FAT 分区的 `download.bit` 载入 PL，本次采集没有动它）。器件容量按官方规格记：125K 逻辑、78,600 LUT、9.3 Mb BRAM、400 DSP、PCIe Gen2 x4、PL 侧 200 MHz。**实际占用量本档案留空**——没有厂商工具的 utilization 报告，拿设计占用当实测资源是 SOP 明令禁止的。

**DMA**——两个控制器各 8 通道（`dw_dmac e004b000.dma`、`dw_axi_dmac_platform f0010000.dma`），与官方规格的 8 通道对上。

**PCIe**——`/sys/bus/pci/devices` 为空、`/proc/bus/pci` 不存在、`lspci` 未安装：**板上没有任何 PCI 设备被枚举**。Gen2 x4 / x1 两条规格都无从确认。

### 外设

以太网 1 路（`fmql-dwmac`，Synopsys DWMAC1000），MAC `ae:59:f4:2d:3a:99`，IP `192.168.1.113/24`，网关 192.168.1.1，MTU 1500。**协商结果是 100 Mb/s Full**（dmesg `Link is Up - 100Mbps/Full`），MAC 支持并广播 1000baseT，但对端只广播 10/100。USB 2.0 控制器 `dwc2 e0045000` 在位、`e0046000` 被禁用；实挂 USB 集线器 0424:2514 与 USB 键盘 17ef:a03b。CAN 控制器 `e0005000` 启用、`e0006000` 禁用，`can0` 处于 down。串口控制器 `e0004000` 启用、调试口 ttyPS0 115200n8。QSPI 与 `dw-apb-ssi` 各一在位、另两个禁用；两路 I2C 都被禁用；4 组 GPIO 全部启用。

待确认九项（第 8 项 2026-10-29 确认；第 7 项 mmc1 DMA、第 9 项 8-bit 走线 2026-10-30 实测确认；其余 6 项未决）：

1. **型号不一致**——设备树自报 `FMQLMP FMQL100TAI`，手册写的是 `FMQL30TAI` / `JFMQL30TAI676H`。需向复旦微确认是芯片步进差异、SKU 改名还是不同产品线；确认前手册数字只作 FMQL30TAI 的规格。
2. **FPGA 占用量**——需要一份厂商工具的 utilization 报告才能填实。
3. **CPU 实际主频**——需要 OPP 表或固件侧频率方案。
4. **以太网为何协商到 100M**——MAC 支持并广播 1000baseT，对端只广播 10/100，要查链路 partner 侧。
5. **`/mnt/wcis-emmc` 挂载不稳定**——第一批挂载、第三批未挂载，放实验文件前先确认。
6. **NPU 设备节点形态**——icraft 的 config.toml 写法与所需权限要在部署前确认。
7. ~~**mmc1 到底支不支持 DMA**~~ **已确认（2026-10-30）**：控制器寄存器报支持（HCON=DWDMA），设备树没配 `dmas`，厂商注释 `/* mmc1 not support dma */` 称不支持——三者矛盾。**实测在 eMMC 节点补 `dmas = <0x0a 0x01 0x00 0x00>`（req=1）后驱动切 `Using external DMA controller.`、CTRL `0x10→0x30`，读写正常：本板 req=1 请求线接好了，vendor 注释是误注。** 但 DMA 不改吞吐（总线已饱和），仅省 CPU。方案与证据见 `../emmc/05-DMA启用方案.md`、`../emmc/04-性能实测.md`、`emmc_evidence/dma-test-20261030-bootdb887f8e.txt`。
8. ~~**eMMC 能否跑 52MHz**~~ **已确认（2026-10-29）**：`EXT_CSD.DEVICE_TYPE[196] = 0x57`，bit0 High Speed 52MHz = **支持**，HS200/HS400 也支持（但需 1.8V，板上无）。当前 25MHz 是设备树 `max-frequency` 钉的，不是卡的限制。读取工具 `../emmc/scripts/extcsd_read.c`。**进一步的 50MHz 运行时实测（2026-10-30）通过：CLKDIV 0x2→0x1，写 22.9/读 23.7 MB/s，md5 一致，无错误。**
9. ~~**eMMC 8-bit 总线走线是否连通**~~ **已确认不可用（2026-10-30）**：运行时把 `bus-width` 改 8，驱动发 CMD6 后卡返回 `switch to bus width 8 failed`，内核标准回退 4-bit、无损坏。说明 PCB 大概率只布线 DAT0~3 或颗粒仅 4-bit，这条提速路封死。证据 `emmc_evidence/8bit-test-20261030-bootdb887f8e.txt`。


### eMMC 挂载：机理与那次"没挂上"的真相

挂载**不由 fstab 管**——板上的 `/etc/fstab` 还是出厂残桩（`# UNCONFIGURED FSTAB FOR BASE SYSTEM`），只留一行注释指向真正的管理者。真正的管理者是 systemd 单元 `wcis-face-storage.service`：

- `Type=oneshot` + `RemainAfterExit=yes`，`After=local-fs.target`、`Before=wcis-face-photo.service`
- `ExecStart=/usr/bin/python3 /root/wcis-face/tools/storage-5df5f1c1e614/mount_face_store.py --device /dev/mmcblk1p1 --mount /mnt/wcis-emmc --uuid 67104a06-74a6-4268-a124-269d1b232a28`
- `ExecStop` 是同一脚本加 `--unmount`——所以**每次关机都会卸载、每次开机才会挂上**
- 挂载前校验 UUID，不符就拒挂；该分区 `LABEL=WCIS_FACE`、`TYPE=ext4`
- 开机约 11 秒完成挂载（`EXT4-fs (mmcblk1p1): mounted` @ 10.84 s）

**第三批采集时"没挂上"的真正原因不是挂载机制不稳**：那次采集（10-20 07:49:07Z）落在 boot -4（06:48:22–07:50:19）里，而**那一次启动整块 eMMC 都没被枚举**——

- 该 boot 里 `wcis-face-storage.service` **一条日志都没有**（其余每次启动都有 Starting / `Personnel eMMC filesystem mounted and verified` / Finished，关机各有 Stopping / Stopped）
- 该 boot 的内核日志里**没有 mmcblk1、没有 ext4 挂载行**，而 boot -5 与 boot -3 都有 `EXT4-fs (mmcblk1p1): mounted filesystem with ordered data mode`
- 同一次启动还丢了串口（`dev-ttyPS0.device` 超时失败）、`sshd` 每 10 秒被探一次连接、最后以 `FAT-fs (mmcblk0p1): Volume was not properly unmounted ... Please run fsck` 收尾——**硬复位，不是正常关机**

**更要紧的是：采集期间板子今早重启了 8 次**（journal boots -7..0，06:17 → 13:12）。eMMC 随每次重启卸载再挂上，所以"挂载在不在"取决于你落在哪一次启动里。板上此刻是挂着的（服务自 13:12:28 起 active，UUID 校验通过）。

**由此引出一条纪律**：这块板子当前处于他人作业中，状态跨会话不稳定。后续任何吞吐/性能测量都必须记录"取自哪一次启动"，否则数据不可比。

**另有一条待处理**：`FAT-fs (mmcblk0p1): Volume was not properly unmounted. Some data may be corrupt. Please run fsck.`——SD 卡的启动分区在上一次硬复位时没干净卸载，需要一次 fsck（rootfs 也在同一张卡上）。
