# 我方在板外设

> **本页回答什么问题**：**此刻物理接在这块板上的是什么设备**，它们和厂商资料里那套（厂商自家摄像头、自家显示器、自家 USB 声卡）**哪里不一样**；每台设备软件侧能看到什么、永远看不到什么。
> **为什么不照抄厂商口径**：我方没用厂商的任何外设。凡"厂商 Demo 能成"的结论都要落回**我接的这台设备上重认一遍**，本页就是这个重认的登记表。
> **判据等级**：A＝板上实测原文（本轮 2026-10-04 11:01 UTC＝北京 19:01，`uptime` 4 天 20 小时），B＝厂商手册原文，C＝推断。板卡侧规格见 [[板子（除芯片）]]，音频设备的详细实测见 [[音频]]。

## 四、板子本体的 SDI 电气侧（B 级，悟净开发板完整版硬件使用手册 V1.0_嵌赛）

这几条是**板上的器件**，与摄像头是不是厂商件无关，正好补掉"SDI 解串芯片型号"这个老悬念：

- **4 路 SDI 输入、1 路 SDI 输出**（手册第 2 节配置表原文）。
- **输入侧用自适应电缆均衡器 LMH0344，输出侧用自适应电缆驱动器 LMH0302**（§4.22 原文）。LMH0344 的数据率覆盖 **125 Mbps 到 2.97 Gbps**，LMH0302 面向 ST424/ST292/ST344/ST259 串行数字接口标准 → **我方这台 1.5G 摄像头落在均衡器的合法工作区间内**，"不是厂商摄像头所以不认"这个担心不成立。
- **整颗芯片只有一个 bank 的 GT（bank112）**，PCIE、SFP、SDI、SMA 四个接口**共用它**，靠 MUX 片选切换（§4.14 原文）。
- GT 的时钟是跳线选的：**J26 选 PCIE 的 100M 还是 SI570 的时钟进 bank112 的 CLK0；J27 选 SDI 用的 148.5M 还是 SMA 的时钟进 bank112 的 CLK1**（§"注意"段原文）。SDI 那侧靠 J26 的 `GTX_LANE_SEL0~3` 接高电平选中（§4.22）。
- **手册自身有一处标号不一致**：§4.14 说各接口片选"通过 J12"，§4.22 说 SDI 片选"当 J26 的 GTX_LANE_SEL0~3 接高电平"。**动任何跳线之前必须对照原理图**，别拿这一页当施工依据（这是厂商文档缺陷，可作反馈项）。
- 手册第 4/2 节的其他板级规格：主芯片 **FMQL30TAI**、PS DDR 1 GB、**PL DDR 2 GB**、eMMC 32 GB、TF 32 GB、USB2.0 4 路、CAN 2 路、SFP 2 路、HDMI 1 路输出、XADC 5 路、LED＝1 路 PS MIO＋4 路 PL、KEY＝1 路 PS MIO＋2 路 PL、PL 侧 16 路 GPIO HEADER。**PL 侧那几组（LED/KEY/GPIO header）要有位流里的逻辑才有意义**，与"DT 里有没有节点"无关。
- 口径提醒：设备树自报的 `FMQLMP FMQL100TAI` **不是贴片芯片的证据**（D-30 已把那条推理作废），别拿它反驳本节的手册原文。

## 五、由此产生的判据边界（写代码前要遵守的）

1. **摄像头身份不可软件获取** → 任何"自动识别摄像头型号/制式"的想法在这块板上没有入口（PS 的 I2C 适配器一个都没注册，A）。换摄像头的风险只在**电气与制式**两层，判据回到第三节。
2. **帧率按 30 fps 记账**，不写 60：吞吐、延迟、带宽预算全部按 30.06 fps（A）。
3. **多路输入这条不做**（我方只有一路摄像头；板子虽有 4 路 SDI 输入，但没有第二个设备，接不上）。
4. **MCP01 的控件值不保证保持**，音量/增益必须现读现用，别当上电常量（这条正本在 [[音频]]）。
5. `can0` 存在但从未验证过收发；要用车载总线类功能前得单独取证，本页不背书。
6. **编码能力已确认存在，但现役直播没换**（10-05 改判，CPU 成本与率控当夜补测完）：厂商 API 硬编 H.264／HEVC 出流且 ffprobe 认，**实时档很省**——1080p@30 只占 21.5% 单核、每帧 7.4 ms CPU，而现役软 JPEG 单帧 67.9 ms ⇒ **同档硬编省约 3 倍 CPU**；**卡点仍是率控＝带宽不可预算**（驱动没有 `bitrate_mode`，把 `video_bitrate` 压到 10 kbps 时输出与不设逐字节相同、md5 一致，证据见 7.3 表末列与 7.4），而『直播不许挤掉 SSH』是硬约束；软路对照数也测过（1080p x264 约 7.4 fps、每帧 0.535 CPU-s；JPEG 67–89 ms/帧）。**换不换是产品决策，不是能力问题**，见 [[板卡镜像实测取证#十五、VPU 硬编取证（D-31 队列第 ③ 项，2026-10-05）|十五 15.4c／15.6]]。
7. **存储只见到一个 mmc 块设备、容量读数与手册不符**（读数 A、归属 C）：任何"这份数据写 eMMC、那份写 TF"的分区规划在这块板上**没有可依据的区分**，只能按"一个 26 GB 根分区"来记账。

### 7.2 两侧队列的格式面（10-05 分侧枚举，A）

`v4l2-ctl` 这个 1.18 版**没有** `--stream-type`，必须 capture 侧用 `--list-formats-ext`、output 侧用 `--list-formats-out-ext` 各跑一次（`-t` 是 tuner，不是 type）。两侧数量不同：**capture-mplane 20 条、output-mplane 34 条**，全部 `Stepwise 2×2 – 8192×8192 step 2/2`。

| 类别                                        | 条数与清单                                                                                                           |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 码流格式（capture 侧＝这颗能**编**哪些）                | **7**：`H264` `M264`(H.264 MVC) `AVC1`(无起始码 H.264) `HEVC` `VP80` `VP90` `JPEG`                                   |
| 码流格式（output 侧＝这颗能**解**哪些）                 | **15**：上面 7 条 **＋** `AVS1` `AVS2` `H263` `MPG2` `MPG4` `RV00` `VC1G` `VC1L`                                     |
| 双向（两侧都有）                                  | 就是那 **7** 条 ⇒ **H.264／H.265／VP8／VP9／JPEG／MVC／AVC1 可编可解**；`AVS1/AVS2/H263/MPEG-2/MPEG-4/RealVideo/VC-1` **只解不编** |
| 裸 YUV（capture 侧，＝解出来的像素格式）                | 13：`Y0A8` `Y0AA` `Y2A8` `Y2AA`（AFBC 压缩）`YM12` `NV12` `NV21` `Y0P1`(P010) `Y0YL` `Y0AB` `YUYV` `UYVY` `Y210`     |

| **不在清单里**                                 | **`RGB565`／任何 16-bit packed**——我方 SDI 交付的正是 RGB565（第三节），所以它**不能直灌硬编**，得由 PL 出 `UYVY`/`YUYV`，或 CPU 转成 `NV12`     |

**判据**：以上"能编／能解"都是**驱动声明**（A）。硬编那 7 条里 **H.264 与 HEVC 已实跑出码流、并被 ffprobe 认**（A，10-05：`v_h264.bit` 17,161 B／`v_h265.bit` 16,862 B，各解出 `Main` 档 1280×720 `yuv420p`）；**`JPEG` 也在 10-15 实跑通了**（A，见 7.8：960×540 与 1080p 都真出 JFIF 图、`ffprobe` 认成 `mjpeg/yuvj422p`，且 quality 档真生效）；**`VP80`／`VP90`／`M264`／`AVC1` 四条没实跑**（C）；**硬解 15 条一条都没实跑**（C，ffmpeg 那条解码路必崩，见 7.6），别当已验证。

### 7.4 缺什么（这三条缺项决定了率控，A）

`bitrate_mode`（`0x009909cc`）、`gop_size`、`header_mode` 这三个控制 ID 在本驱动 **`VIDIOC_QUERYCTRL` 直接 EINVAL＝不存在**；`VIDIOC_S_PARM`（存 `v4l2_streamparm` 的帧率）也**没有 handler**（ENOTTY）。

⇒ 结论：**没有任何用户态开关能把编码器切进 CBR/VBR**，"率控设了不生效"的根因是**码率模式选择项根本没实现**，不是我调用方式不对。

### 7.5 吞吐与 CPU 成本（10-05 干净窗口实测，A）

窗口条件：直播链已停、`loadavg` 0.5、源放 `/dev/shm`（**放 rootfs 会被 eMMC 的 23 MB/s 读速压死**，同一命令下 720p 从 255 fps 掉到 17.7 fps，跟编码无关）、取样器 `cpu_run.py` 每 0.02–0.05 s 读 `/proc/<pid>/stat`。

| 档位 | 稳态 fps | 每帧 CPU | 平均单核占用 |
|---|---|---|---|
| 720p H.264 不限速 | **255.5** | 6.6 ms | **101.6%** |
| 720p H.264 限速 30 | 31.6 | 4.0 ms | 11.7% |
| 720p H.265 限速 30 | 31.8 | 3.8 ms | 11.4% |
| 1080p H.264 不限速 | **119.1** | 10.0 ms | **89.4%** |
| 1080p H.264 限速 30 | 33.7 | 7.4 ms | 21.5% |
| 1080p H.264 限速 15 | 16.8 | 7.4 ms | 11.0% |

判读：
1. **CPU 成本是"搬运"不是"计算"**：每帧 4–10 ms 基本等于 NV12 那 1.4／3.1 MB 的用户态 memcpy ＋ QBUF/DQBUF 系统调用；不限速时**单核被吃满**（89–102%），所以 **255／119 fps 这两个上限是 CPU 复制带宽，不是 VPU 的**。
2. 真按实时跑就**很省**：1080p@30 只要 **21.5% 单核**（4 核之一），而现役直播的软 JPEG 单帧 67.9 ms（1080p q80）⇒ **同档硬编省约 3 倍 CPU**，且码流是标准 H.264 Annex-B。
3. 想再往下压 CPU 只有两条：让 PL 直接出 `UYVY`（省掉 CPU 转色），或改零拷贝（`enqueueDataPtr` 之外走 `VIDIOC_EXPBUF`/dmabuf）。**都没测**。

### 7.6 三条使用坑（A，都踩过）

1. **流已经开始后再设 codec 类控制会打死会话**：喂 8 帧后再设 `0x0099201b` → `EINVAL`，随后两侧队列一起 `EIO`，150 帧只出 2 帧。控制必须在 `vpu::Encoder` 构造完、喂第一帧之前设完。
2. `S_EXT_CTRLS` 只对 `0x00990000`（MPEG/legacy 类）有效；`0x009d0900` 那批（`compression_quality`、`restart_interval`）走 S_EXT 报 `EINVAL`，只能用 `S_CTRL`。V4L2 控制是 **per-file-handle**，外部 `v4l2-ctl` 设不进编码器自己的会话。
3. `buffer_count` 用默认 6，更大触发内核 `MMU ABORT`——但驱动声明 `min_number_of_output_buffers=1`，所以**这是内存侧的**（993 MB 无 swap、CMA 256 MB 下拿不到足够连续物理页／MMU 映射），不是协议约束（机制判级 B）。ffmpeg 的 `*_v4l2m2m` 在这颗上必崩或出 0 字节，原因在十五 15.3（它对不存在的控制 ID 不判返回值）。

### 7.7 官方 YOLOv5 流程与这颗 VPU 的关系：**完全不碰**（A，源码级）

她问的是"官方 yolov5 的流程是不是完全不走 VPU 硬解、完全 FPGA 实现"。按源码逐条落：

| 环节 | 实现在哪 | 证据 |
|---|---|---|
| 取图 | **PL 寄存器**，不是 V4L2：写 `0x50`/`0x04`、轮询 `0x58` 等帧就绪，落点是 PS DDR 的 udma chunk | `pipeline/io/input/sdicamera.hpp:249-254,263-293`；设备是 `axi://zg330aiu?npu=0x40000000&dma=0x80000000`（`configs/ZG/sdicamera+yolov5+hdmi.yaml:3`→`src/sdicamera+yolov5+hdmi.cpp:182,188-192`），**全路径没有一个 `/dev/video*`** |
| 缩放／裁切 | **两条都是 PL 逻辑**：`resizePS`（寄存器 `0x5c`–`0x6c`）与 `hardResizePL`（`defaultRegRegion().write`），再加 ImageMake 硬 op（基址 `0x80000400`） | `sdicamera.hpp:77-143,145-231`、`et_device.hpp:791-807,862`、`sdicamera_input_actor.hpp:161-169`；`sdicamera+yolov5+hdmi.cpp:234` 的注释写明这一步是必需的 |
| 色彩／格式 | **PL**：格式选择寄存器 `0x78`（RGB565 与 YUV422 二选一），PL 有 YUV2RGB 模块；`et_device.hpp:148` 那个 `yuv2rgb()` 全树没人调用 | `sdicamera.hpp:202-227`、`C++_API_reference.md:827-847` |
| 推理 | NPU 硬化核（icore，`npu=0x40000000`），不是 VPU | `sdicamera+yolov5+hdmi.cpp:213-220` |
| 检测后处理＋画框 | **CPU**：`post_detpost_plin`，再用 OpenCV 往 RGB565（`CV_8UC2`）帧上画框 | `sdicamera+yolov5+hdmi.cpp:289,396-404` |
| 送显 | **PL**：`RGB565HDMIDisplay::show` 写 `0x40080054` | `pipeline/io/output/hdmi_display.hpp:38-48,88` |

所以口径要这么写：**"像素操作全在 PL"成立，"完全 FPGA 实现"要打一半折**——后处理和画框是 CPU，推理是 NPU。

**而且这里根本没有"硬解"可言**：SDI 进来的是裸帧（PL 直接交付 1920×1080 RGB565），没有任何码流需要解，VPU 在这条链上**无事可做**。厂商树里 VPU 的代码是齐的（`pipeline/vpu/vpu.h`、`actor/vpu_encoder_actor.hpp`、`actor/webcam_decoder_actor.hpp`、`io/input/webcam.hpp`、`io/output/stream2rtsp_server.hpp`＋`stream2rtmp.hpp`），但**没有一个 example 把它们 include 进来**（本 demo 的 include 列表在 `sdicamera+yolov5+hdmi.cpp:32-53`，没有任何一条链走到 `vpu/`），`message_router.hpp:328-339` 里那个 `VPUEncoderActor` 只活在一具废弃的 `int main()` 测试脚手架里（`:322`），**没有一个 yaml 引用 vpu/encoder/rtsp**。**结论：这些是厂商留着、demo 没接的通路**——把硬编接进直播链要我方自己写 actor，不是"打开某个配置"。

> 例外提醒：现役二进制里唯一的 CPU 侧像素操作（`cv::resize`＋`cv::imwrite` 的 LivePump，`actor/hdmi_display_actor.hpp:135-230`）是**我方 09-30 插桩加进去的**（该文件 mtime 2026-09-30，其余厂商头都是 2026-04-07），不是厂商 HDMI 通路的一部分。
