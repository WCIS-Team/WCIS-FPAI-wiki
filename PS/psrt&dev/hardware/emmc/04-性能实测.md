# 04 · 性能实测

> **测量环境**：boot `dace9468-2d7d-4d71-8767-b001caf6267a`（2026-10-29 12:49:13 – 13:42:58 UTC）。
> 这块板子当天重启了 8 次，跨启动的数据不可比，引用时必须带 boot ID。

## 测试方法

- 工具：`dd` + `O_DIRECT`（`oflag=direct` / `iflag=direct`），绕过页缓存，测的是真实设备速度
- 单次 64MB（第一轮 128MB），顺序读写
- 计时：`/usr/bin/time -f "W=%e U=%U S=%S"` + `date +%s%N`
- **CPU 采样**：读 `/proc/stat` 的 `cpu` 行前后差值

  ```
  busy = 所有字段之和 − idle − iowait
  cpu% = busy_delta / (HZ × wall) × 100     # HZ = 100, nproc = 4
  ```
  注意：`time dd` 报的 `user/sys` **不可用**——PIO 搬运在硬中断上下文，不计入 dd 进程。

- 每个测试前单独采 3 秒基线，因为机上有常驻负载（`wcis_camera_owner` 约 33% 单核）

### 第一次踩的坑（记录在此避免重犯）

把 `/proc/stat` 所有字段（含 idle）相加当 busy，算出 350%+ 的假数据——那是总时间不是忙时间。必须减去 `idle` 和 `iowait`。

### 基线复测（2026-10-29 boot `72a8f941`，环境干净）

机器空闲时的干净基线（`wcis-face-recording --mode off`，eMMC 无 I/O，
`irq24` 10 秒内增长 0）。这是后续对比 overlay 效果的**基准值**：

| 项目 | 耗时 | 吞吐 | CPU（4 核总计） |
|---|---|---|---|
| 写 128M (buffered) | 11.805 s | 11.4 MB/s | 0.59% |
| 写 128M (O_DIRECT) | 11.605 s | 11.6 MB/s | 0.57% |
| 读 128M (O_DIRECT) | 11.409 s | 11.8 MB/s | 0.55% |
| 读 128M (buffered) | 11.273 s | 11.9 MB/s | 0.57% |

> `O_DIRECT` 和 buffered 几乎一样，说明**根本没走页缓存**——瓶颈在 eMMC 总线，
> 缓存再怎么优化也没用。CPU 0.57% 是 4 核总和，折合**单核 2.3%**。
> 这个数字比上一轮的 46~57% 低得多，因为那次相机服务在跑、基线没扣干净。
> **以本节数据为准**，它的基线是真·零。

### 总线利用率

| 设备 | 时钟 | 位宽 | 理论带宽 | 实测 | 利用率 |
|---|---|---|---|---|---|
| eMMC | 25 MHz | 4 | 12.5 MB/s | 11.84 | **94%** |
| SD | 50 MHz | 4 | 25.0 MB/s | 22.37 | **90%** |

**两者都贴着总线上限，说明设备侧已经饱和，瓶颈在总线不在控制器。**

**这条 94% 是整件事的关键**：总线已经跑满，所以任何软件层优化（DMA、队列、块大小、
文件系统参数）都不会让吞吐再涨 1%。**唯一有效的动作是把总线本身变快**——
也就是时钟 ×2 或位宽 ×2。

### 50MHz 时钟实测（2026-10-30 boot `db887f8e`）

在不动 DTB、不重启的前提下，用 configfs overlay 把 eMMC 时钟从 25MHz **实时切到 50MHz**，
`unbind/bind` 驱动重新 probe。环境：eMMC 挂载正常，录播 `--mode off` 无写入，直播未碰 eMMC。

步骤（见 [03-test-overlay.sh](../emmc/scripts/03-test-overlay.sh)）：

1. `systemctl stop wcis-face-recording`  （录播当时 off，无影响）
2. `systemctl stop wcis-face-storage`    （顺带卸 eMMC 挂载）
3. 注入 `mmc1-clock.dtbo`（dtbo 二进制接口，非 path）
4. `echo e0044000.dwmmc > dw_mmc/unbind && bind`
5. `systemctl start wcis-face-storage` 重挂载

结果：

| 项目 | 25MHz 基线 | 50MHz 实测 | 变化 |
|---|---|---|---|
| 写 128M O_DIRECT | 11.6 MB/s | **22.9 MB/s ×3** | ×1.94 |
| 读 128M O_DIRECT | 11.8 MB/s | **23.7 MB/s ×3** | ×2.01 |
| 数据完整性 | — | 16MB 随机写 → 读回 md5 一致 | 无损坏 |
| 控制器 CLKDIV | 0x2 | **0x1** | 50MHz |
| dmesg 错误 | — | 无 CRC/timeout/IO error | 干净 |

dmesg 关键行：

```
[13127.347956] mmc_host mmc1: Bus speed (slot 0) = 100000000Hz (slot req 50000000Hz, actual 50000000HZ div = 1)
[13127.348951] mmc1: new high speed MMC card at address 0001
```

**实测吞吐与上方"预期 ×2"完全吻合，且数据完整性校验通过。** 此配置为 configfs 临时态，
板子重启即回 25MHz；要固化见 [05-DMA启用方案.md](../emmc/05-DMA启用方案.md)。
证据：`../hardware/emmc_evidence/50mhz-test-20261030-bootdb887f8e.txt`

### 8-bit 总线实测（2026-10-30 boot `db887f8e`）—— 不可用 ✅

在同一套 overlay + rebind 流程上，把 `bus-width` 从 4 改成 8（叠加 50MHz），验证 8-bit 是否可用。
结果：**不可用**，驱动安全回退 4-bit。

dmesg 关键行：

```
[14511.485419] mmc1: switch to bus width 8 failed
[14511.486489] mmc1: new high speed MMC card at address 0001
```

完整过程：

| 步骤 | 结果 |
|---|---|
| 注入 `bus-width=8` + `max-frequency=50M` overlay | ✅ applied |
| `unbind/bind` 重 probe | 驱动发 CMD6 切 8-bit → **卡返回失败** |
| 驱动行为 | **自动回退 4-bit**（`ios` 仍 `bus width: 2 (4 bits)`） |
| 32MB 测速 | 写 22.8 / 读 23.7 MB/s（= 4-bit 速度，证明回退生效） |
| 数据完整性 | 16MB 随机写读回 md5 **一致**，无损坏 |
| dmesg 错误 | 仅 `switch to bus width 8 failed`，无 CRC/timeout/IO error |

**结论**：8-bit 在这块板子上跑不了，原因大概率是 PCB 只布线 DAT0~3（DAT4~7 未接）或该 eMMC 颗粒
仅 4-bit。属于硬件限制，软件无解。内核的回退是标准行为，全程安全。
证据：`../hardware/emmc_evidence/8bit-test-20261030-bootdb887f8e.txt`

### DMA 启用实测（2026-10-30 boot `db887f8e`）—— 可用 ✅，vendor 注释是错的

在已生效 50MHz overlay 之上，再叠加 `mmc1-dma.dtbo`（`dmas = <0x0a 0x01 0x00 0x00>`，req=1），
`unbind/bind` 重新 probe。结果：**DMA 成功启用**，推翻厂商 `/* mmc1 not support dma */` 注释。

关键证据（dmesg 时间线，同一 boot 多次 rebind）：

```
[13127.276623] dw_mmc e0044000.dwmmc: Using PIO mode.        <- 50MHz 时钟测试（无 dmas）
[14511.413282] dw_mmc e0044000.dwmmc: Using PIO mode.        <- 8-bit 测试（无 dmas）
[15873.620238] dw_mmc e0044000.dwmmc: Using external DMA controller.  <- DMA 测试 ✅
```

CTRL 寄存器（0xe0044000）：叠加前 PIO `0x00000010` → 叠加后 `0x00000030`（bit5 DMA_ENABLE 置位）。

**结论**：本板 eMMC 控制器 req=1 这条 DMA 请求线确实接到了 dmahost0，"mmc1 not support dma" 是误注。
但需强调——**DMA 不改变吞吐**（总线已 ~94% 饱和，PIO 也跑满），它只把 PIO 在硬中断里逐字节拷贝的
CPU 开销卸载掉（实测 eMMC PIO 读 1M 块 4.6 ms/MB → SD DMA 读 0.1 ms/MB）。对这块板子，DMA 是"锦上添花"，
不是提速主因。证据：`../hardware/emmc_evidence/dma-test-20261030-bootdb887f8e.txt`

### 50MHz + DMA 稳定性压力测试（2026-10-30 boot `db887f8e`）—— 稳定 ✅

在 `50MHz + 4-bit + DMA`（CTRL=0x30）配置下，跑 ~2.4GB 写 + 对应读 的持续负载，验证提总线后是否稳：

| 项目 | 结果 |
|---|---|
| 配置 | clock=50000000Hz, 4-bit, CTRL=0x00000030 |
| 数据完整性 | 64M 随机写 → 读回 md5 **一致** ✅ |
| 8 轮 200M O_DIRECT 顺序读写 | 写 21.6~21.7 / 读 22.3 MB/s，**全程稳定无抖动** |
| 512M buffered 大文件 | 写 21.8 MB/s，writeback 路径无错误 |
| 错误扫描 | 压测前=1，压测后=1，**增量=0**（那 1 条是早先 8-bit 测试的旧日志，非本次） |
| 挂载 | YES，全程有效 |

**结论：把 eMMC 总线从 25MHz 提到 50MHz（叠加 DMA）在持续 ~3.7GB 负载下稳定，无 CRC/超时/数据丢失，
直播与存储服务不受影响。提总线是安全的。**
证据：`../hardware/emmc_evidence/stress-50mhz-dma-20261030-bootdb887f8e.txt`

## CPU 开销是否与速度线性？

### 直接回答

**不是与"速度"线性，而是与"字节数"线性。**

- PIO 模式下 CPU 逐字节搬运，成本 = 字节数 × 每字节开销 + 中断次数 × 每次中断开销
- 传同一个文件，无论快慢，**总 CPU 时间基本不变**
- 提高时钟让传输变快后：**单位时间的 CPU 占比上升，但每 MB 的 CPU 成本不变**——正比关系，不是超线性
- 真正让每 MB 成本变化的是**块大小**

### 数据验证

eMMC 写，固定 64MB，只改块大小：

| 块大小 | 吞吐 | 每 MB CPU | 趋势 |
|---|---|---|---|
| 1M | 11.55 MB/s | 9.7 ms | 基准 |
| 64K | 11.20 MB/s | 14.3 ms | +47% |
| 4K | 8.41 MB/s | 24.4 ms | +152% |

块变小 → 吞吐下降 **且** 每 MB 成本上升。因为传输次数变多，每次的中断/命令开销摊到更少字节上。

**所以"搬得越快占的 CPU 越多"这个说法要修正为：同样的数据量，CPU 总开销固定；想更快就要么提高总线能力（时钟/位宽），要么让 CPU 不参与搬运（DMA）。**

### CPU 是不是瓶颈？

不是。

- eMMC PIO 满速 11.8 MB/s 时，额外 CPU 开销约 35~110 ms-CPU/s ≈ **单核的 4~11%**
- 4 核总共 400%，也就是说传输只占全系统 **1~3%**
- 相机服务常驻约 46% 单核，系统仍有大量余量

**即使把时钟翻倍到 50MHz，PIO 的 CPU 占用也只是翻到单核 8~22%，依然不是问题。**

### DMA 能省多少

对比 SD 卡（DMA）和 eMMC（PIO）在读方向的每 MB 成本：

- SD DMA 读 1M 块：**0.1 ms/MB**（几乎不占 CPU，DMA 引擎搬）
- eMMC PIO 读 1M 块：**4.6 ms/MB**

DMA 确实能把 CPU 成本压到接近 0。但对**吞吐**没有帮助——SD 卡快是因为它跑 50MHz，不是因为它用 DMA。

## 复现方法

```bash
# 上传脚本
scp scripts/02-bench-mmc.sh root@192.168.1.113:/tmp/
ssh root@192.168.1.113 "sed -i 's/\r$//' /tmp/02-bench-mmc.sh && bash /tmp/02-bench-mmc.sh"
```

脚本会在 `/mnt/wcis-emmc/ddtest.bin` 和 `/root/ddtest_sd.bin` 建临时文件，跑完自动删除。
**注意**：`/mnt/wcis-emmc` 上有 `recording_service.py` 在跑，脚本只写根目录下的独立文件，不碰它的 `wcis-face/recordings/`。

跑之前先记 boot ID：

```bash
cat /proc/sys/kernel/random/boot_id
```
