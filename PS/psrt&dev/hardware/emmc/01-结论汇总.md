# 01 · 结论汇总

## 核心结论（六条）

### 1. eMMC 控制器硬件支持 DMA，是设备树没启用

两个 MMC 控制器的 `HCON` 寄存器**完全相同**，都是 `0x07E52CC1`，其中 `HCON[17:16] = 01 = DWDMA`（DesignWare 外部 DMA 接口）。

差异出在 `CTRL` 寄存器的 `bit5 (DMA_ENABLE)`：

| 控制器 | CTRL | bit5 DMA_ENABLE |
|---|---|---|
| SD 卡 `e0043000` | `0x00000030` | **1（已开）** |
| eMMC `e0044000` | `0x00000010` | **0（未开）** |

驱动判定逻辑（`drivers/mmc/host/dw_mmc.c:2890-2960`）分两步：

```c
host->use_dma = SDMMC_GET_TRANS_MODE(mci_readl(host, HCON));  // 读硬件能力
if (DWDMA || GDMA) host->use_dma = TRANS_MODE_EDMAC;
else goto no_dma;

// 第二步：EDMAC 模式下必须再有 dmas 属性
if (!device_property_present(dev, "dmas")) goto no_dma;      // ← eMMC 卡在这里
host->dma_ops = &dw_mci_edmac_ops;
```

eMMC 节点没有 `dmas`，所以落到 `no_dma` → PIO。

厂商在源码里留的注释 `/* mmc1 not support dma */` 指"SoC 集成时 mmc1 的 DMA 请求线没接到 dmahost0"。
**这一点已于 2026-10-30 实测推翻**：在 eMMC 节点补 `dmas = <0x0a 0x01 0x00 0x00>`（req=1）后，
驱动打印 `Using external DMA controller.`，CTRL bit5 置 1（`0x10 → 0x30`）——**本板 req=1 这条请求线确实是接好的，vendor 注释是错的**。

> 注意：DMA 不影响吞吐（总线已 ~94% 饱和），只省 CPU。详见 §5 与 [04-性能实测.md](04-性能实测.md)。

### 2. 频率 25MHz，总线已经跑满

> **这里的"频率"是 eMMC 控制器的 SDIO 总线时钟，不是 CPU 主频。**
> CPU 走 `armpll`（1GHz，无 cpufreq，硬件锁定）；SDIO 走 `iopll → sdio_mux → sdio_div`，两条链完全独立。改总线时钟不影响 CPU 分毫。

| 项 | eMMC (mmc1) | SD (mmc0) |
|---|---|---|
| ciu 时钟源 | 100MHz | 100MHz |
| CLKDIV | 2 | 1 |
| 实际时钟 | **25MHz** | **50MHz** |
| 总线宽度 | 4-bit | 4-bit |
| 理论带宽 | 12.5 MB/s | 25 MB/s |
| 实测吞吐 | **11.8 MB/s** | **22.4 MB/s** |
| 总线利用率 | **94%** | **90%** |

时钟源上限就是 100MHz（`iopll` 1GHz → `sdio_mux` 1GHz → `sdio_div` 100MHz，`sdio0`/`sdio1` 都是 100MHz）。所以 **eMMC 最高只能到 50MHz**（CLKDIV=1），理论 25MB/s。

**为什么现在只有 25MHz？** 不是芯片限制，是设备树钉死的：

```dts
dwmmc@e0044000 {
    max-frequency = <0x17d7840>;   /* = 25,000,000 */
    bus-width     = <0x04>;
};
```

改成 `<50000000>` 后，驱动算 `CLKDIV = DIV_ROUND_UP(100MHz, 2×50MHz) = 1` → 实际 50MHz，**吞吐直接翻倍**。

### 2.1 卡的能力（EXT_CSD 实测，2026-10-29）

`CMD8` 读出来的 `DEVICE_TYPE[196] = 0x57`：

| bit | 能力 | |
|---|---|---|
| 0 | High Speed 26/52 MHz | **支持** |
| 1 | HS200 | **支持** |
| 2 | HS400 | **支持** |
| 3 | HS400 Enhanced Strobe | 不支持 |

**卡完全不是瓶颈。** 52MHz 是稳的。HS200/HS400 虽然卡支持，但需要 1.8V 信号，
DTB 里这个节点没有 `vqmmc-supply`，板上也没看到 1.8V 切换电路，**这条路走不通，别惦记**。

健康度：`PRE_EOL_INFO=0x01`（正常），`LIFE_TIME_A/B=0x01`（已用 0~10%）。
这块盘基本没写过，不用担心磨损。

### 2.2 50MHz 已在运行时实测验证 ✅（2026-10-30 boot `db887f8e`）

用 configfs overlay（`mmc1-clock.dtbo`）+ `unbind/bind` 驱动，把时钟从 25MHz **实时切到 50MHz**，不重启、不改 DTB。结果：

| 项目 | 25MHz（原） | 50MHz（实测） | 变化 |
|---|---|---|---|
| 写吞吐 | 11.6~11.8 MB/s | **22.9 MB/s**（128M ×3 一致） | ×1.94 |
| 读吞吐 | 11.8 MB/s | **23.7 MB/s**（128M ×3 一致） | ×2.01 |
| 数据完整性 | — | 16MB 随机写 → 读回 md5 **一致** ✅ | 无损坏 |
| dmesg | — | 无 CRC/timeout/IO error | 干净 |

控制器寄存器 **CLKDIV = `0x00000001`**（硬件确实 50MHz），`CTRL=0x10` 仍是 PIO，
`CTYPE=0x1` 仍是 4-bit。直播（`wcis-sdi-vpu-view`）全程未受影响；录播（`wcis-face-recording`）
当时是 `--mode off` 没写盘，停服测试后已恢复。

**结论：50MHz 完全可行、安全，预期 ×2 已兑现，是性价比最高的提速。**
当前是 configfs 临时配置（板子重启会自动回到 25MHz），要长期生效见 [05-DMA启用方案.md](05-DMA启用方案.md) 的永久改 DTB 流程。
证据：`../hardware/emmc_evidence/50mhz-test-20261030-bootdb887f8e.txt`

### 2.3 8-bit 总线已实测：不可用 ✅（2026-10-30 boot `db887f8e`）

同样用 configfs overlay 把 `bus-width` 从 4 改成 8（叠加在 50MHz 上），`unbind/bind` 重新 probe。
驱动发 CMD6 让 eMMC 卡切 8-bit 时，**卡返回失败**：

```
[14511.485419] mmc1: switch to bus width 8 failed
```

驱动**自动回退到 4-bit**（`ios` 仍 `bus width: 2 (4 bits)`），后续 32MB 测速仍是 22.8/23.7 MB/s，
16MB 随机写读回 md5 一致 —— **没有数据损坏，内核标准回退行为，安全**。

**结论：8-bit 在这块板子上不可用**，原因大概率是 PCB 只走了 DAT0~3（DAT4~7 没布线）
或该 eMMC 颗粒本身 4-bit only。无论哪种，都改不了（硬件层面）。这条提速路封死。
证据：`../hardware/emmc_evidence/8bit-test-20261030-bootdb887f8e.txt`

### 3. CPU 开销不与速度成正比，而与字节数成正比

- PIO 是逐字节拷贝，CPU 成本按**字节数**线性增长，与传得多快无关
- 同一个文件，无论快慢，**总 CPU 时间一样**
- 提高时钟后：单位时间的 CPU 占比上升，但**每 MB 成本不变**——不是超线性
- 真正影响每 MB 成本的是**块大小**：块越小，中断次数越多，成本越高

实测每 MB 的 CPU 开销：eMMC PIO 写 `1M` 块约 9.7 ms/MB，换成 `4K` 块涨到 24.4 ms/MB。

**关键：PIO 满速只占单核 6~12%（4 核里占 2~3%），CPU 远不是瓶颈。**

### 4. eMMC 数据完全不经过 PL

`e0044000.dwmmc` 挂在 PS 侧 `amba-apu@0` 上，数据路径是：

```
CPU (PIO) → e0044000.dwmmc → eMMC 芯片
```

全程在 PS 的 AMBA 总线上，**不跨 AXI 到 PL**。PS↔PL 的通路是另外两套：AXI DMA `f0010000.dma` 和 `udmabuf@0`。

### 5. 提速优先级：时钟 > 总线宽度 > DMA

| 措施 | 预期收益 | 难度 | 风险 | 卡是否支持 |
|---|---|---|---|---|
| **SDIO 时钟 25→50MHz** | 吞吐 ×2（实测 22.9写/23.7读 MB/s） | 改 DTB 一个值 | **低**（✅ 已运行时实测，无错误） | ✅ 确认支持 |
| **总线 4→8bit** | ❌ **已实测：不可用**（卡/PCB 拒绝 8bit，驱动安全回退 4bit） | 改 DTB/overlay 一行（已试） | 中（试了即知，无损坏） | ❌ `switch to bus width 8 failed` |
| **PIO→DMA** | 吞吐 ≈0 提升，仅省 0.6% 总 CPU | 改 DTB 加 `dmas` 一行 | **低**（✅ 已实测 req=1 线接好，vendor 注释错） | ✅ 已确认可用 |

**结论：DMA 对吞吐几乎没帮助（因为瓶颈是总线不是 CPU），真正有价值的是把 SDIO 总线时钟翻倍。**

- 只提频：25MHz → 50MHz，11.8 → **约 23MB/s（已实测 ✅）**
- 提频 + 8bit：**不可行** —— 2026-10-30 运行时实测，驱动报 `switch to bus width 8 failed`，卡/PCB 不支持 8bit，自动回退 4bit，无损坏
- 再加 DMA：吞吐不变，只是把 PIO 那 0.6% 的 CPU 省掉

**再强调一次：全程不碰 CPU 频率。** CPU 没有 cpufreq 接口，硬件锁定在 `armpll` 1GHz，任何 DTB 改动都影响不到它。

### 6. 系统盘紧张与 eMMC 无关

系统盘是 SD 卡 `mmcblk0p2`（26G，曾 90% 满，**2026-10-31 重刷后：用 19G／剩 5.9G／76%**），eMMC 是独立的 `/mnt/wcis-emmc`（30G，仅用 3%，挂载带 `nosuid,nodev,noexec`）。**注意 `/mnt/data`（`mmcblk0p3`，30G）是同一张 SD 卡上的第三个分区、不是独立盘**——旧版这句只写了两个分区，容易让人以为"SD 卡只有系统盘那 26G"；要缓解 `/` 的压力，能挪的落点是 `/mnt/data`（它没有 `noexec`）而不是 eMMC。清 eMMC 不影响系统盘。详见 [06-磁盘清理清单.md](06-磁盘清理清单.md)。
