# 02 · 硬件与数据通路

## 平台识别

```
model       = "FMQLMP FMQL100TAI"
compatible  = "fmsh,fmsh-fmqlmp"
CPU         = ARM Cortex-A53 ×4 (part 0xd03, ARMv8)
内存        = 1GB (cmdline: mem=1024M)
内核        = linux-5.4.52-fmsh
```

## 存储布局

| 设备 | 容量 | 挂载点 | 物理接口 | 角色 |
|---|---|---|---|---|
| `mmcblk0` | 58.4G | `/`（p2 26G）、`p1` 1G 为 boot | SD 卡，`e0043000.dwmmc`（mmc0） | **系统盘** |
| `mmcblk1` | 29.1G | `/mnt/wcis-emmc` | eMMC `Y2P032`，`e0044000.dwmmc`（mmc1） | **数据盘** |
| `mtd0` | 4M | — | "bootloader" | |
| `mtd1` | 16M | — | "kernel" | |
| `mtd2` | 0 | — | "rootfs"（未使用，root 在 SD 上） | |

`mmcblk0p1` 内容（boot 分区，FAT/ext4）：`Image`（13MB 内核）、`fmqlmp-verify.dtb`（16KB 设备树）、`BOOT.bin`（FSBL+u-boot）、`u-boot`、若干 `.bit` 比特流、多个历史 `.BAK`。

> **注意**：`/boot` 目录是空的，真正的启动文件在 `mmcblk0p1` 分区，需要手动 mount 才能看到。

## PS / PL 分区

这台 SoC 是 PS（Processing System）+ PL（Programmable Logic）结构，Linux 跑在 PS 侧的 A53 上。

### PS 侧外设（`amba-apu@0`，地址空间 `0xe000_0000`）

```
serial@e0004000     串口 (console=ttyPS0)
gpio@e0003000~3400  4 组 GPIO
i2c@e0002000 / e0022000
spi@e0000000 / e0001000 / e0020000 / e0021000
can@e0005000 / e0006000
nfc@e0042000        NAND 控制器
dwmmc@e0043000      ← SD 卡 (mmc0), irq 20, 用外部 DMA
dwmmc@e0044000      ← eMMC  (mmc1), irq 41, PIO
usb@e0045000        dwc2, host_dma enabled
ethernet@e0047000 / e0049000
dma@e004b000        ← dmahost0, snps,dma-spear1340, 8ch/16req
devcfg@e0040000     FPGA 比特流加载器 (fmql_fpga_manager)
mali_gpu@f0000000
dma@f0010000        ← AXI DMA, snps,axi-dma-1.01a, 8ch（跨 PS-PL）
mve@f0020000        arm china linlon-v5 媒体/向量引擎
```

### PL 侧

- FPGA 状态 `operating`（`/sys/class/fpga_manager/fpga0/state`）
- 通过 `e0040000.devcfg`（`fmql_fpga_manager`）加载比特流
- PS→PL 有两条通路：**AXI DMA `f0010000.dma`** 和 **`udmabuf@0`** 共享 DDR 缓冲

## 三条关键数据路径

### 路径 A：SD 卡读写（走 PS DMA）

```
CPU → 页缓存 → e004b000.dma (dmahost0 chan0, req=0)
                    ↓ 硬件握手
              e0043000.dwmmc → SD 卡
```

dmesg：`dw_mmc e0043000.dwmmc: Using external DMA controller.`

### 路径 B：eMMC 读写（PIO，不经过 PL）

```
CPU 逐字搬运 → e0044000.dwmmc FIFO → eMMC 芯片
```

dmesg：`dw_mmc e0044000.dwmmc: Using PIO mode.`

**全程在 PS 侧 AMBA 总线上，不跨 AXI，不碰 PL。** 这是本次排查最需要澄清的一点。

### 路径 C：PS → PL 传数据（和 eMMC 无关）

```
PS DDR ──AXI──→ f0010000.dma ──→ PL 用户逻辑
  或
PS DDR ──udmabuf@0 共享物理页──→ PL 侧 AXI master 直接读写
```

如果需求是"把数据送给 FPGA 处理"，走的是路径 C，和 eMMC 完全是两套东西。

## 关于"eMMC 是 PL 操作后才找到的"

如果观察到 PL 加载比特流后 eMMC 才出现，可能的解释：

1. **PL 里的 IP 通过 AXI master 访问了 PS 侧的 eMMC 控制器**——但这样 Linux 看到的仍然是 mmc1 这个 PS 外设，数据路径还是路径 B
2. **PL 参与了 eMMC 的上电/复位/时钟使能时序**（例如某个 GPIO 或电源使能信号由 PL 输出）——这属于板级设计，需要在原理图层面确认
3. 纯属时间上的巧合

**待确认**：这一点本次没有拿到直接证据，需要在 PL 工程（Vivado/FPGA 侧）里查是否有 eMMC 相关信号。建议后续补查。

## DMA 控制器参数

```
dma@e004b000 (dmahost0)
  compatible       = "snps,dma-spear1340"
  phandle          = 0x0a (10)
  dma-channels     = 8
  dma-requests     = 16
  dma-masters      = 1
  #dma-cells       = 3
  chan_allocation_order = 1
  chan_priority    = 1
  block_size       = 0xfff
```

`#dma-cells = 3` 的含义（`drivers/dma/dw/of.c:25-31`）：

```c
slave.src_id  = dma_spec->args[0];   // 外设请求线号
slave.dst_id  = dma_spec->args[0];   // 同一个值！收发共用一条请求线
slave.m_master = dma_spec->args[1];  // 内存 master 号
slave.p_master = dma_spec->args[2];  // 外设 master 号
```

所以 `dmas = <&dmahost0 REQ 0 0>`，mmc0 用的是 `REQ = 0`。
**mmc1 必须用一条不同的请求线**（否则和 mmc0 抢同一条握手信号）。候选值 1~15，需要逐个试。

当前通道占用：

```
dma0chan0  in_use=1   ← 被 mmc0 (SD) 占用
dma0chan1~7 in_use=0  ← 空闲
```
