# 07 · 踩坑与注意事项

这次排查踩过的坑，以及动手前必须知道的事。

---

## A. 测量类的坑

### A1. `/proc/stat` 把所有字段相加是错的

第一版脚本这么算的：

```bash
# 错！把所有字段加起来（含 idle）等于总时间，不是忙时间
tot=0; for(i=2;i<=NF;i++) tot+=$i
```

结果算出 `cpu=352%` 这种没有意义的值——因为 `user+nice+system+idle+iowait+irq+softirq+...` 恒等于 `nproc × HZ × 秒数`，跟忙不忙无关。

**正确做法**：

```bash
busy = 总和 - idle($5) - iowait($6)
cpu% = busy_delta / (HZ × wall) × 100     # 满核 = nproc × 100%
```

`HZ` 用 `getconf CLK_TCK` 取，本机是 100。

### A2. `time dd` 的 user/sys 测不到 PIO 的 CPU 开销

128MB 传输，`time` 报 `U=0.00 S=0.09`——几乎为零。

原因：**PIO 的数据搬运发生在硬中断上下文**，这部分 CPU 时间不计入 `dd` 进程的 user/sys，而是记在被中断的任务或 ksoftirqd 上。

所以必须用 `/proc/stat` 测全系统，或者看 `top` 里的 `si`（softirq）列。

### A3. 机上有常驻负载，基线会跳

`wcis_camera_owner` 常驻约 33% 单核，加上录像服务，基线在 **463~1513 ms-CPU/s** 之间波动（单核 46%~150%）。

后果：单次测量的每 MB CPU 成本有 **±50% 噪声**，会出现 `net=0` 甚至 `net=-63`（负数）这种荒谬值。

**对策**：每个测试前单独采 3 秒基线，多次重复取中位数，只看趋势不看绝对值。

### A4. `dd` 加 `O_DIRECT` 才准

不加 `oflag=direct` 的话，数据先进页缓存就返回了，测出来是内存速度不是设备速度。

`bs` 必须是 512 的整数倍（本机用 4K/64K/1M 都没问题）。

## B. 命令行的坑

### B1. SSH 默认用户名不对

本机 SSH 默认用户是 `takomi`，那台机器上没有这个账号：

```
takomi@192.168.1.113: Permission denied (publickey,password).
```

必须显式写 `root@192.168.1.113`。免密已配好。

### B2. `| head` 会把 dtc 掐死

```bash
# 错！head 提前关闭管道，dtc 收到 SIGPIPE 被杀，输出文件不生成
dtc -I dtb -O dts /tmp/cur.dtb -o /tmp/cur.dts 2>&1 | head -5
```

症状：看到警告输出，但 `/tmp/cur.dts: No such file or directory`。

**正确做法**：

```bash
dtc -I dtb -O dts /tmp/cur.dtb > /tmp/cur.dts 2>/dev/null
```

### B3. Windows 上传的脚本有 CRLF

从 Windows 写到 S 盘的 `.sh` 带 `\r`，在 Linux 上会报 `bad interpreter: /bin/bash^M`。

**每个上传的脚本都要先转换**：

```bash
sed -i 's/\r$//' /tmp/xxx.sh
```

### B4. 目标机没有 `dtc`

`dtc` / `fdtput` / `fdtget` / `mmc-utils` 全都没有。但**有 gcc / make / flex / bison**，所以可以从内核源码现编：

```bash
cd /root/home/lili/linux-5.4.52-fmsh
make ARCH=arm64 fmsh_fmqlmp_defconfig   # 必须先有 .config，否则报错
make scripts_dtc
# 产物: scripts/dtc/dtc
```

注意 `make scripts_dtc` 直接跑会失败，报 `Configuration file ".config" not found!`。

## C. 设备树相关的坑

### C1. 源码里的 DTS 和实际用的 DTB 不一致 ⚠️

`/root/home/lili/linux-5.4.52-fmsh/arch/arm64/boot/dts/fmsh/fmqlmp-verify.dts` 里写着：

```dts
mmc0: dwmmc@e0043000 {
    max-frequency = <2500000>;   /* 2.5 MHz */
```

但**实际运行的设备树是 50MHz**（`0x2faf080`）。

**结论：不要相信这份源码 DTS，它已经过期。权威来源是 boot 分区上的 `fmqlmp-verify.dtb`。**

改配置时应该：
```bash
mount -o ro /dev/mmcblk0p1 /mnt/bootmnt
cp /mnt/bootmnt/fmqlmp-verify.dtb /tmp/cur.dtb
dtc -I dtb -O dts /tmp/cur.dtb > /tmp/cur.dts    # 这才是真的
```

### C2. `/boot` 是空的

`ls /boot` 什么都没有。真正的 `Image`、`fmqlmp-verify.dtb`、`BOOT.bin`、`u-boot` 都在 **`/dev/mmcblk0p1`**（FAT/ext4，1G 分区），需要手动 mount。

### C3. 运行中的 DTB 没有 `__symbols__`

overlay 里想用 `&dmahost0` 这种标签引用会失败——因为没有符号表。

**只能用裸 phandle**。本机 `dmahost0` 的 phandle 是 `0x0a`（10），已核实。

```bash
xxd /proc/device-tree/amba-apu@0/dma@e004b000/phandle   # 0000 000a
```

dtc 编译 overlay 时会警告：

```
Warning (dmas_property): cell 0 is not a phandle reference
```

**这个警告可以忽略**——我们就是故意硬编码的，反编译核对过值是对的。

### C4. `#dma-cells = 3` 的三格含义

`drivers/dma/dw/of.c:25-31`：

```c
slave.src_id  = dma_spec->args[0];   // 请求线号
slave.dst_id  = dma_spec->args[0];   // 同一个值！收发共用
slave.m_master = dma_spec->args[1];
slave.p_master = dma_spec->args[2];
```

所以 `dmas = <&dmahost0 REQ 0 0>`。**mmc0 已经占了 `REQ=0`，eMMC 必须换一条。**

### C5. dtc 往返编译可能改变 DTB

`dtb → dts → dtb` 有风险：phandle 可能被重编号、属性可能被重排。

**本机验证结果是安全的**（diff 只有 3 处预期变化，phandle 0x0a 保持不变），但每次改都必须做 diff 校验，不能盲信。

### C6. `0xe004b1e8` 读出来是 0

想读 DW DMA 的硬件参数（DWC_PARAMS），按 0x1e8 偏移读是 `0x00000000`——这个偏移在本机不适用（`DW_DMA_MAX_NR_CHANNELS` 不同）。

**参数以设备树为准**：8 通道 / 16 请求线 / 1 master。

### C7. configfs 的 `path` 属性不吃绝对路径，而且失败不报错 ⚠️

`/sys/kernel/config/device-tree/overlays/<名字>/` 下有三个属性：`dtbo`、`path`、`status`。

**`path` 走的是内核固件加载器（`request_firmware`），只能写相对 `/lib/firmware` 的文件名。**

```bash
# ❌ 错：绝对路径，加载失败
echo /root/emmc-overlays/mmc1-clock.dtbo > .../overlays/x/path
#   → dmesg: Direct firmware load for /root/... failed with error -2
#   → 但 echo 返回码是 0！max-frequency 根本没变，极易误判成功

# ✅ 对法一：先把文件放进 /lib/firmware，再写裸文件名
cp /root/emmc-overlays/*.dtbo /lib/firmware/
echo mmc1-clock.dtbo > .../overlays/x/path

# ✅ 对法二（推荐，脚本用这个）：直接把二进制喂给 dtbo 属性
cat /root/emmc-overlays/mmc1-clock.dtbo > .../overlays/x/dtbo
```

**判断是否真的加载成功，只能看两处**，不能看返回码：

```bash
cat .../overlays/x/status          # 期望 applied
od -An -tu4 --endian=big /sys/firmware/devicetree/base/amba-apu@0/dwmmc@e0044000/max-frequency
```

另外每次替换已有属性都会打一条 `memory leak will occur if overlay removed` 警告，
是内核不释放被替换的旧字符串导致的，**几十字节，无害，忽略**。

## D. 硬件操作的坑

### D1. 千万不要热写 HCON / CLKDIV 寄存器 ⚠️

有人会想"直接 `devmem 0xe0044070 0x...` 把 DMA 位改掉不就行了"——**绝对不行**。

- 驱动内部维护 `host->use_dma` 状态，硬件和软件状态会不一致
- 改 CLKDIV 会让驱动以为还跑 25MHz，实际 50MHz，时序参数全错
- 已挂载的 ext4 会因数据错误直接损坏
- 控制器可能挂死，只能断电

**正确路径只有一条：改设备树 + rebind 驱动，让驱动自己重新初始化。**

读寄存器（`devmem <addr>` 不带值）是安全的，可以随便读。

### D2. rebind 前必须 umount

```bash
echo e0044000.dwmmc > /sys/bus/platform/drivers/dw_mmc/unbind
```

这条命令会让 `mmcblk1` 整个消失。如果 `/mnt/wcis-emmc` 还挂着，ext4 会立刻报 I/O 错误并 remount-ro，**在途数据丢失**。

顺序必须是：停服务 → umount → unbind。

### D3. 停服务清单

```bash
systemctl stop wcis-face-recording.service    # 必须停，它用 /mnt/wcis-emmc
```

其他三个服务（`wcis-face-photo`、`wcis-heartbeat`、`wcis-sdi-vpu-view`）不碰 eMMC，可以不停。

### D4. `/mnt/wcis-emmc` 是 nosuid,nodev,noexec

```
/dev/mmcblk1p1 on /mnt/wcis-emmc type ext4 (rw,nosuid,nodev,noexec,noatime,errors=remount-ro)
```

- 可以在上面存数据、放模型
- **不能直接执行上面的程序**（`noexec`）
- `errors=remount-ro`：一旦出错自动转只读，这是好事，能防止进一步损坏

### D5. root 在 SD 卡上 —— 这是安全垫

`root=/dev/mmcblk0p2`，系统盘是 **SD 卡（mmc0）**，eMMC 只是数据盘。

所以**即使 eMMC 配置改错，系统照样能启动**，最坏是 `/mnt/wcis-emmc` 挂不上。可以放心试错，不会有变砖风险。

### D6. "提频"不是提 CPU 频率 ⚠️

文档里说的 25MHz→50MHz **是 eMMC 的 SDIO 总线时钟**，不是 CPU 主频。别被"频率"两个字误导。

```
CPU  : armpll_int → armpll → armpll_clk                     1 GHz
外设 : iopl_int → iopl_clk → sdio_mux → sdio_div → sdio0/1   100 MHz
```

- 两条链从 **PLL 层就分开**，SDIO 挂在 `iopll` 上，不经过 `armpll`
- CPU 侧**没有 `cpufreq` 接口**（`/sys/devices/system/cpu/cpu0/cpufreq` 不存在），频率硬件锁定，软件改不了
- 改 `max-frequency` 只影响 `sdio_div`/`sdio1` 这一支

实测父节点链：`sdio1 → sdio_div → sdio_mux → iopl_clk → iopl_int`。

### D7. 卸载 eMMC 不能用 `umount`

`/mnt/wcis-emmc` 由 systemd 单元 `wcis-face-storage.service` 管理（`Type=oneshot` + `RemainAfterExit=yes`，`ExecStop` 跑 `--unmount`）。

直接 `umount` 会让 unit 状态和实际挂载脱节——之后 `systemctl start` 因为 `RemainAfterExit=yes` 认为"已经挂好了"，**实际却没挂上**。

正确做法：

```bash
systemctl stop wcis-face-recording.service   # 先停使用者
systemctl stop wcis-face-storage.service     # 它自己会 --unmount
# ... 操作 ...
systemctl start wcis-face-storage.service    # 重新挂载（自带 UUID 校验）
systemctl start wcis-face-recording.service
```

### D8. 板子会自己重启

2026-10-29 当天重启了 **8 次**（boot -7 到 boot 0，UTC 12:12 → 13:43）。有的正常有的硬复位。

后果：

1. **`/tmp` 里的东西会丢** —— overlay dtbo 编译产物必须放持久目录（已固化到 `/root/emmc-overlays/`）
2. **测量数据必须记 boot ID**，否则不同启动间的数据不可比

```bash
cat /proc/sys/kernel/random/boot_id
uptime -s
journalctl --list-boots | tail -5
```

本次所有测量数据取自 boot `dace9468-2d7d-4d71-8767-b001caf6267a`（12:49:13 – 13:42:58 UTC）；
后续探测与基线取自 boot `72a8f941-237d-4679-aa9d-1184783b734e`（13:43 UTC 起）；
**50MHz 实测取自 boot `db887f8e-201b-47ca-bbc4-396c53a176a3`（2026-10-30）**。

### D9. 录播服务可能 active 但其实没写盘（看 `--mode`）

`wcis-face-recording.service` 的 `ExecStart` 里硬编码了 `--mode off` 和
`--storage /mnt/wcis-emmc/wcis-face/recordings`。**off 模式下它不会真的写 eMMC**，
即使服务是 active 状态。

实测验证（boot `db887f8e`）：`lsof +D /mnt/wcis-emmc` 无任何进程打开 eMMC 文件、
`find /mnt/wcis-emmc -newermt "-10 min"` 无新文件、`/proc/diskstats` 自启动仅 56 扇区写入。
所以停录播服务做测试**不会丢任何录像数据**。

**教训**：别一看到 `recording` 是 active 就当成"正在写盘"。动手前用 `lsof` / `diskstats`
确认它到底有没有 I/O，再决定要不要停它。直播 `wcis-sdi-vpu-view` 同样不碰 eMMC，全程不用停。

### D10. 8-bit 总线实测不可用 —— 卡/PCB 拒绝，驱动安全回退

2026-10-30 用 overlay 把 `bus-width` 从 4 改 8（叠加 50MHz）+ `unbind/bind`，dmesg 直接报：

```
mmc1: switch to bus width 8 failed
```

驱动**自动回退 4-bit**（`ios` 仍 `bus width: 2 (4 bits)`），后续测速回到 4-bit 速度，16MB 随机写读回 md5 一致，**无数据损坏**。

大概率原因：PCB 只布线了 DAT0~3（DAT4~7 没接），或该 eMMC 颗粒本身 4-bit only。
无论哪种都是**硬件限制，软件无解**，8-bit 提速路封死。

**教训**：overlay 试错是安全的——即使给的配置不合理（比如 8-bit 接不通），内核会回退而不是崩。
所以"走线未知有风险"这种事，先用临时 overlay 试，坏了重启就回来，比直接改 DTB 安全得多。

## E. 尚未确认的问题

### E1. "eMMC 是 PL 操作后才找到的" —— 未证实

本次没有拿到直接证据。可疑线索：

- 系统里有 `pwrseq_emmc` 驱动（eMMC 上电时序），说明 eMMC 有独立的复位/上电序列
- `devcfg@e0040000` 负责加载 PL 比特流

**可能的原因**（都需要进一步查证）：

1. PL 里有 IP 通过 AXI master 访问 eMMC 控制器
2. eMMC 的电源/复位使能信号由 PL 的 GPIO 输出
3. 纯属时间上的巧合

**下一步**：去 Vivado / FPGA 工程里搜 eMMC 相关信号（`sdmmc1`、`emmc_rst`、`EMMC_*`），或查原理图。

### E2. mmc1 的 DMA 请求线到底接没接 —— 未证实

- 控制器说支持（HCON = DWDMA）
- 设备树没配
- 厂商注释写 "mmc1 not support dma"
- `dmahost0` 有 16 条请求线，**mmc0 用 0**（实测其 `dmas` 原始字节 `<0x0a 0x00 0x00 0x00>`），其余空闲

所以 mmc1 只能用 **1~15** 里的某一条，最可能是 1（overlay 里就是这么写的）。
但"接没接"取决于 SoC 集成时的连线，软件读不出来。

**已确认 overlay 能把 `dmas = <0x0a 0x01 0x00 0x00>` 注进实时 DT**（2026-10-29 预检通过），
剩下的只是 rebind 之后会不会真的走 DMA。方案见 [05-DMA启用方案.md](05-DMA启用方案.md) 阶段二。

### E3. ~~eMMC 芯片是否真支持 52MHz~~ —— ✅ 已证实支持

2026-10-29 用 `scripts/extcsd_read.c`（`CMD8` 只读）读到了 EXT_CSD：

```
DEVICE_TYPE[196] = 0x57
  bit0 High Speed 26/52 MHz : 支持
  bit1 HS200                : 支持
  bit2 HS400                : 支持
  bit3 HS400ES              : 不支持
BUS_WIDTH[183] = 1 (4-bit)    HS_TIMING[185] = 1 (high speed)
PRE_EOL[267]   = 0x01 (正常)  LIFE_TIME_A/B = 0x01/0x01 (已用 0~10%)
```

**卡完全不是瓶颈。** 现在跑 25MHz 纯粹是设备树 `max-frequency = <25000000>` 钉的。
HS200/HS400 卡支持但需要 1.8V 信号，DT 无 `vqmmc-supply`，不可达。

> 顺带记一个坑：`/usr/include/linux/mmc/ioctl.h` **不导出** `MMC_RSP_R1` / `MMC_CMD_ADTC` 这些宏
> （它们在 mmc-utils 自己的头里），直接编译会报 undeclared。要自己按内核
> `include/linux/mmc/mmc.h` 的位定义补：`MMC_RSP_R1=0x07`、`MMC_RSP_SPI_R1=0x80`、`MMC_CMD_ADTC=0x20`。
> 补完 `gcc -Wall` 零警告。

### E4. 板子是否走了 8 根数据线 —— 未知，且**读不出来**

`bus-width = 4` 是软件配置，硬件实际走线要查原理图或实测。

**eMMC 规范里没有"最大总线宽度"这个字段**，`EXT_CSD.BUS_WIDTH[183]` 只反映当前设置，
不是能力上限。所以**再怎么读寄存器也读不出来**，别浪费时间。
唯一办法：改 DTB `bus-width = <8>`，重启看 dmesg 和数据校验。方案见 05 阶段三。
