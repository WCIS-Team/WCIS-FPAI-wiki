# 校机（WIN11-HV1）有界基准读数

- 采集时间：2026-10-19 06:17 起（UTC+8）
- 环境档案：同目录 `device.json`、`system.json`、`resources.json`、`toolchains.json`（v1.1）
- 原始读数：`raw_logs/bench_run1.json`、`bench_run2.json`、`bench_run3.json`（2026-10-19 三次）；`raw_logs/bench.json`（2026-10-20 复测单次）

## 目的与边界

这是一组固定规模、一次性、可重复的轻量基准，用来给后续模型实验提供“这台机器大概什么水平”的参照。不跑压力/长稳测试，不做量化或模型推理，也不把这里的数字当成硬件标称性能。

## 测试环境

- Hyper-V 虚拟机，24 个 vCPU（CPU 型号串是宿主机的 AMD EPYC 9654 96-Core），125 GiB 内存。
- 系统盘 C:，测试盘 D:（虚拟 SAS 盘，2 TB，采集时空闲 1708 GiB）。
- 采集时后台有明显负载：`fdtd-solutions` 常驻约 12.6 GB 内存，`Get-CimInstance Win32_Processor` 的 `LoadPercentage` 快照为 100。所有读数都在这种共享、有背景负载的条件下取得。

## 方法

`bench_cpu.c`，用校机自带的 `D:\yzd\MSYS2\mingw64\bin\gcc.exe -O2 -fopenmp` 编译，OpenMP 默认 24 线程，连续跑 3 次：

- CPU：512×512 双精度矩阵乘，计 2·512³ 次浮点运算，分别测单线程与 24 线程。
- 内存：256 MB 的 a/b/c 三个数组做 triad（`c[i]=a[i]+b[i]*3`），重复 20 次，按读写 3 路字节数折算 GB/s。
- 磁盘：D: 上 256 MB 顺序写，再顺序读回；读之前刚写过，属于热缓存读。

## 解读与限制

- 24 线程只有约 7.9× 加速，说明这个 512×512 的负载已经碰到内存带宽和 vCPU 调度的上限，不是纯算力受限。
- 读带宽高于写、且接近内存 triad 的量级，印证这是页缓存命中，不是冷盘读；不能当磁盘顺序读性能。
- 单线程 6.66 GFLOPS、24 线程 52 GFLOPS 都远低于裸机 EPYC 9654 的理论峰值，符合“共享虚拟机 + 后台 FDTD 负载”的条件，只能作量级参照。
- 早期一次未开 OpenMP 的构建曾测得单线程 12.2 GFLOPS（0.0220 s），与这三次的 6.66–6.70 相差约 1.8×。那次只跑了一遍、编译参数也不同，不作为结论，仅记录在此说明单发读数的波动有多大。
- 所有数字都是现场测量（field_measurement），不是官方规格，也不能外推成模型推理性能。

## 复现步骤

1. 把 `bench_cpu.c` 传到校机 `D:\yzd\bench_cpu.c`。
2. 用绝对路径编译（PATH 里加上 mingw64 的 bin）：
   ```
   set PATH=D:\yzd\MSYS2\mingw64\bin;%PATH%
   gcc -O2 -fopenmp -o D:\yzd\bench_cpu.exe D:\yzd\bench_cpu.c
   ```
3. 运行（同样要先设 PATH，否则 `libgomp-1.dll` 找不到会挂起）：
   ```
   D:\yzd\bench_cpu.exe D:\yzd\bench.json D:\yzd\bench_tmp.bin
   ```
4. 把 `bench.json` 取回。要多次采样就重复第 3 步，换输出文件名。

原始 `gcc` 编译日志与各次 JSON 在 `raw_logs/` 下。
