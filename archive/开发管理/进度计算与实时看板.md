## 1. 进度计算规则

不搞燃尽图，不搞主观百分比。

```
分组完成率 = 该分组 ✅ 任务卡数 / 该分组计划任务卡总数
总进度     = 全部 ✅ 卡数 / 全部计划卡数
```

| 规则 | 内容 |
|---|---|
| 计数单位 | **任务卡**，不是人时、不是代码行、不是 RTL 文件数 |
| 数据源 | §3.1 总账表，一行一卡；§3.2 的数字由 `tools/progress.py` 从该表推导，**不手填** |
| 计入分子 | 只有状态为 ✅ 且证据列写了 `E_` + 可核查指向的卡 |
| 不计入 | 🔄 进行中、⛔ 阻塞、"预研下阶段"——**一律按 0 计**，没有部分分 |
| 剔除 | ➖ 不适用（如 A9 全程未触发）不计入分母，须在备注指到一条决策记录 |
| 不加权 | 各分组等权计入分母。**阶段加权已随决策 D-12 取消**——权重是为门禁评审设计的，没有门禁就没有意义 |
| 分母变更 | 计划任务卡集合变更时，必须在 [[状态源与决策记录]] 留一条决策记录，并回填历史百分比 |
| 条件通过 | 带着 ⛔ 项推进下游（条件通过）**不改变**卡的计数，只允许推进其无板可推进子集 |

> 设计意图：宁可显示"0% 但有一项 E3 资产"，也不显示"看起来做了三成"。**进度虚高是两人团队最早崩塌的信号。**

#### 列规则（脚本按这些规则校验，违反会报错）

| 列 | 允许的值 | 规则 |
|---|---|---|
| 卡号 | `P0`–`P4`、`M1`、`M2`、`GOLD`、`A1`–`A9`、`V`、`DEP`、`DOD` | 全表唯一；新增卡先走决策记录再加行 |
| 分组 | 准备 / 基线 / 加速 / 交付 | 决定 §3.2 的分组行 |
| 路线 | ① / ② / ③ / ④ / — | 对应 [[实施路线]] 四步 |
| 状态 | ⬜ 未开工 / 🔄 进行中 / ⛔ 阻塞 / ✅ 完成 / ➖ 不适用 | **只放一个符号**，解释写进备注；没有部分分 |
| 证据 | `E0`–`E6` + 空格 + 可核查指向，或 `—` | 状态为 ✅ 时**必填**，缺则脚本报错；指向要具体到文件、tag 或台账行 |
| 更新 | `YYYY-MM-DD` | 这一行最后一次变动的时间；§3.2 的「最近刷新」取全表最大值 |
| 无板 | 是 / 部分 / 否 | 「是」＝不等板就能 ✅；「部分」＝有等板子项，须同时出现在 §4 |
| 实际 | `__d` 或 `—` | 完成时回填，用于事后估时校准，不进进度公式 |
| 详情 | 一个 `[[页面名]]` | 这张卡的完成判据所在页；[[清单]] 的链接与流程图由它生成。写多页只留最主要的一页 |

其中**卡号唯一、状态取值合法、日期格式、✅ 必带证据、➖ 必指决策编号、⛔ 必在阻塞清单**这六条由 `tools/progress.py` 强制；其余靠人自觉。

> **不在这张表里的东西**：误差容限、黄金参考版本、运行时开关状态、实测误差与加速比——那些是**台账**：容限与参考来源在 [[3-FPGA组件下沉#6. 下沉范围与误差容限预置（按子模块，第 ① 步冻结）|3-FPGA组件下沉——6. 下沉范围与误差容限预置（按子模块，第 ① 步冻结）]]预置，每次实测追加到 [[任务卡与台账规范#4.2 下沉台账（第 ③ 步，每组件每次比对一行）|任务卡与台账规范——4.2 下沉台账（第 ③ 步，每组件每次比对一行）]]，本表只在备注里指一句。同一数据不写两处。

## 6. 看板的历史留痕

本页的看板区是**滚动覆盖**的（当前真值只看最新一次刷新），不堆积历史。历史靠三个机制保留：

| 需求 | 去哪里看 |
|---|---|
| 某个决定为什么改 | [[状态源与决策记录]] 决策日志（追加式） |
| 某一周的进度数字 | 本文件的 git 历史：`git log -p -- md/开发管理/进度计算与实时看板.md` |
| 某个组件的实测数据演变 | [[任务卡与台账规范]] 台账（追加行，不删行） |

§3.1 的**更新日期列**是廉价的最近史：不查 git 也能看出哪张卡两周没动过。要查更早的状态变化再用 `git log -L`。

## 7. 进度异常的诊断顺序

总进度两周不动时，按此顺序自查，不要第一反应是"加人力/加班"：

1. **是不是全卡在同一个外部依赖？** → 看阻塞清单是否有共同解锁条件。**2026-09-28 之前是**（板卡）；**现在不是了**——四条板端阻塞项的解锁条件已经各自独立，若进度仍不动，原因在我们自己没排板时，不在外部依赖。别再往"等板"上归因。
2. **是不是分母设错？** → 任务卡集合变更没走决策记录？
3. **是不是卡在评审而非工作本身？** → 每周五有没有真的投屏本页逐卡过一遍？两人团队最常漏这一步。
4. **是不是范围在偷偷长？** → 对比当前卡集合与上期，任何新增行必须能指到一条决策记录。
5. **是不是单点卡住？** → 某张卡的备份人在两周内没有接触过该领域 → bus factor 风险 #11。
